# SSL証明書の仕組みと certbot がやっていること

work-hub を Let's Encrypt で HTTPS 化したときの「裏側で何が起きているのか」をまとめた解説ドキュメント。
実際の作業手順は [vps-deploy-commands.md](./vps-deploy-commands.md) の「14. Let's Encrypt によるSSL化」を参照。

---

## 0. 前提：SSL証明書とは何か

SSL証明書は、**「通信に使う公開鍵」**と**「サイトの持ち主（ドメイン）の情報」**を結びつけ、
「この公開鍵は本当にこのドメインの正規のものか？（＝なりすましでないか）」を保証するもの。

証明書に載っている主な情報：

| 載っているもの | 内容 | 役割 |
| --- | --- | --- |
| **Subject（サブジェクト）** | ドメイン名 `work-hub.arumako-matsumoto.com` | 持ち主を証明する情報 |
| **公開鍵** | 暗号通信に使う公開鍵 | 通信相手が暗号化に使う |
| **Issuer（発行者）** | 誰が発行したか（例: Let's Encrypt R10） | 発行した認証局（CA） |
| **有効期限** | 例: 2026-09-11 まで（90日） | 期限切れ後は無効 |
| **CAのデジタル署名** | CAが「この内容は本物」と保証する印章 | **「正しい」と証明する核心** |

### 重要：証明書を発行（署名）するのは「サイトの持ち主」ではなく「認証局（CA）」

もし持ち主が自分で「私は本物です」と証明書を作れてしまうと、攻撃者も同じように
「私が本物の銀行です」と自作でき、証明の意味がなくなる。
そのため、**誰もが信頼する中立の第三者（CA = Certificate Authority）が、身元を確認したうえでお墨付きを与える**形をとる。
今回でいうと **Let's Encrypt が CA**。

```
あなた（サイトの持ち主）   … 鍵ペアを作り「証明書ください」と申請する人
Let's Encrypt（認証局/CA）  … 身元を確認して証明書に署名する人 ← 発行はこっち
ブラウザ（クライアント）    … CAの署名を検証して信頼する人
```

> 例え：証明書は**運転免許証**。顔写真・名前（＝ドメイン情報と公開鍵）は本人のものだが、
> 「これは本物だ」と保証する発行・印章は本人ではなく**公安委員会（＝CA）**が押す。
> 自分で印刷した「自称・免許証」が信用されないのと同じ理屈。

## 1. CAの署名を、ブラウザはどう「正しい」と検証するのか

### ステップ1：デジタル署名＝「秘密鍵で封印、公開鍵で確認」

公開鍵暗号の性質：

> **CAの秘密鍵で「封印」したものは、ペアであるCAの公開鍵でしか「開けられない」。**
> 逆に、公開鍵で開けられたなら「確かにその秘密鍵の持ち主＝本物のCAが封印した」と分かる。

CAが署名するとき：

```
① CAが証明書の中身（ドメイン名＋公開鍵など）を要約（ハッシュ）する
        ↓
② その要約を、CAの「秘密鍵」で封印する  ← これが「デジタル署名」
        ↓
③ 署名を証明書に貼り付けて発行
```

ブラウザの検証：

```
① 証明書に貼られた署名を、CAの「公開鍵」で開ける
        ↓
② 開けて出てきた要約 と、証明書の中身を自分で計算し直した要約 を比べる
        ↓
   一致する → 「中身は改ざんされておらず、本物のCAが署名した」と確定 ✓
   開けられない/一致しない → 警告 ⚠️
```

攻撃者は **CAの秘密鍵を持っていない**ため、CAの公開鍵で正しく開ける署名を偽造できない。
だから「なりすまし証明書」は作れない。

### ステップ2：「ではCAの公開鍵は本物か？」→ ルート証明書

「CAの公開鍵も偽物かもしれない」という疑問への答え：
**ブラウザとOSには、信頼できるCAの公開鍵が出荷時から組み込まれている**。これを**ルート証明書（信頼の起点）**と呼ぶ。

```
PC/ブラウザの中に、出荷時から
「これらのCAは信頼してよい」というリスト（ルート証明書の束）が入っている
  例: ISRG Root X1（Let's Encryptの大元）、DigiCert、Google Trust Services …
```

これが**信頼の「錨（いかり）」**。誰かを信じるには最初に無条件で信じる起点が必要で、
それをOS/ブラウザの開発元（Microsoft, Apple, Google, Mozilla等）が厳格な審査のうえ事前に組み込んでいる。

### ステップ3：信頼の連鎖（チェーン）

実際は安全のため、ルート証明書を直接使わず**中間CA**を挟んだ数珠つなぎになっている：

```
あなたのサイト証明書（work-hub...）
   ↑ 署名したのは…
Let's Encrypt の中間CA証明書（例: R10）
   ↑ 署名したのは…
ISRG Root X1（ルート証明書）← PC/ブラウザに最初から入っている＝信頼の起点
```

ブラウザは下から上へ署名を辿り、**「最初から信頼している起点（ルート）」に到達できれば証明書全体を信頼**する。
これが鍵マーク（🔒）の正体。

### なぜ自作証明書（オレオレ証明書）は警告が出るのか

自作証明書は鎖の頂点が**ブラウザに登録されていない自分自身**になる。
信頼の起点に辿り着けないので、ブラウザは「この発行元は信用できない」と警告を出す。
Let's Encrypt の証明書が鍵マークになるのは、**鎖の頂点がPCに最初から入っている信頼済みルートに繋がるから**。

## 2. その「ボタン1つ」で certbot が代行したこと

歴史的に証明書取得は手作業で何ステップもある面倒な作業だった。
certbot は **ACME** という自動化プロトコルでこれを全部やってくれる。

| # | certbotがやったこと | 補足 |
| --- | --- | --- |
| 1 | **鍵ペアを生成**（公開鍵＋秘密鍵） | **秘密鍵はサーバーから一切出ない**。`privkey.pem` に保存。これが漏れなければ安全 |
| 2 | **CSR（証明書署名要求）を作成** | 「このドメインに、この公開鍵で証明書ください」という申請書。公開鍵とドメイン名が入る |
| 3 | **ACMEアカウント登録** | 入力した**メール・利用規約同意**のステップがこれ |
| 4 | **ドメイン所有確認（チャレンジ）** | Let's Encryptが「本当に持ち主か」テストを出す（後述） |
| 5 | **証明書を受け取る** | 確認が通ると、Let's Encryptが**自分の秘密鍵で署名した証明書**を返す（＝1章の②③） |
| 6 | **Nginxへ自動設定** | `listen 443 ssl` ブロック追加、証明書パス記入、HTTP→HTTPSリダイレクト設定 |
| 7 | **自動更新タイマー登録** | 90日ごとに 1〜5 の更新を無人で繰り返す `certbot.timer` |

### ステップ4「所有確認」の中身（HTTP-01チャレンジ）

```
Let's Encrypt:「君が本当にこのドメインの持ち主なら、
  http://work-hub.arumako-matsumoto.com/.well-known/acme-challenge/（ランダム文字列）
  に、私が指定する合言葉ファイルを置けるはずだ。置いてみて」
        ↓
certbot が、そのファイルを一時的にサーバーに配置
        ↓
Let's Encrypt が ポート80 経由で実際にそのURLにアクセスし、合言葉を確認
        ↓
一致 → 「確かにこのサーバー＝このドメインの持ち主だ」と認定 → 証明書発行
```

> **設定作業との関係**：SSL化の最初に基本認証を `server` 直下から `location /` の中へ移動したのは、
> まさにこの瞬間のため。認証がサーバー全体にかかったままだと、Let's Encrypt が
> `/.well-known/...` の合言葉を取りに来たときに**パスワード要求でブロックされ、所有確認に失敗**する。
> だから先に避けておいた。`certbot renew --dry-run` が成功したのは、
> 90日後の自動更新でもこの確認が**ちゃんと通る**ことを意味する。

## 3. まとめ：1枚の絵

```
【発行時】
あなた(certbot) ──CSR(公開鍵+ドメイン)──> Let's Encrypt(CA)
あなた(certbot) <──所有確認テスト───────  Let's Encrypt
あなた(certbot) ──合言葉ファイル設置────> （ポート80で確認）
あなた(certbot) <──署名済み証明書─────── Let's Encrypt（CAの秘密鍵で署名）

【アクセス時（ブラウザ）】
ブラウザ <──証明書(公開鍵+署名)── あなたのサーバー
ブラウザ：署名をCAの公開鍵で検証 → ルート証明書まで辿れる → 信頼 🔒 → 暗号通信開始
```

「ボタン1つ」の正体は、**この発行時の左側（申請者の作業）を certbot が丸ごと自動化した**こと。
検証の仕組み（右側）は、ブラウザとOSに組み込まれた信頼の連鎖が支えている。

## 4. 関連ファイルの場所（VPS上）

| パス | 内容 |
| --- | --- |
| `/etc/letsencrypt/live/work-hub.arumako-matsumoto.com/fullchain.pem` | サイト証明書＋中間CA証明書（チェーン） |
| `/etc/letsencrypt/live/work-hub.arumako-matsumoto.com/privkey.pem` | **秘密鍵。絶対に外部へ出さない** |
| `/etc/letsencrypt/renewal/work-hub.arumako-matsumoto.com.conf` | 自動更新の設定 |
| `/etc/nginx/sites-enabled/work-hub` | certbotが443設定とリダイレクトを追記したNginx設定 |

確認コマンド：

```bash
# 証明書の一覧・期限確認
sudo certbot certificates

# 自動更新タイマーの確認
sudo systemctl list-timers | grep certbot

# 自動更新のリハーサル（本番同様にシミュレート）
sudo certbot renew --dry-run
```

## 5. さらに深掘りするなら（参考トピック）

- **TLSハンドシェイク**：証明書の公開鍵は通信の最初だけ使い、その後は高速な共通鍵に切り替わる仕組み。
  （公開鍵暗号は遅いので、鍵交換だけに使い、本体の暗号化は共通鍵で行う）
- **秘密鍵 `privkey.pem` の管理**：漏れると証明書がなりすましに悪用されうる。
  ファイル権限（root のみ読める）で保護されている。バックアップ時も取り扱い注意。

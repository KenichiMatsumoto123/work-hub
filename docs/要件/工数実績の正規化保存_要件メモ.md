# 工数実績の正規化保存 要件メモ

- 作成日: 2026-08-13
- 深掘り: 簡易深掘り実施（grilling skill 未導入のため、grilling の手法に準拠して司令塔が実施。1問ずつ・推奨案つきで9問）

## 目的・背景

現在、日報の保存先は `daily_reports` テーブル 1 本のみで、取引先・プロジェクト・タスク・工数といった内訳はすべて `raw_data`（JSONB）に格納されている。正規化されているのは日単位の情報（`date` / 始業・終業・休憩 / `total_work_hours`）だけで、工数の内訳は SQL で集計できない。

一方、スキーマには正規化された受け皿が定義済みだが、アプリからは一切参照されていない：

- `clients`（取引先マスタ）／ `projects`（プロジェクトマスタ、`client_id` は notNull）
- `tasks`（`client_id` / `project_id` / `category_id` を持つ）
- `time_entries`（コメントに「工数記録（実績の唯一のマスター）」と明記）
- `schedule_entries`（予定工数）／ `effort_budgets`・`weekly_effort_budgets`（工数予算）

本開発の目的は、**日報を保存すると `time_entries` に ID 紐づきの実績が正しく積み上がる状態**を作ること。集計の見せ方（画面・帳票）は本開発のゴールに含めず、後続機能として切り出す。

## 利用者

- 本アプリの利用者本人（日報を入力する開発者）。
- ログインは better-auth + メール許可リスト（`AUTH_ALLOWED_EMAILS`）で制御されている。
- ただし DB 構造は単一ユーザー前提（`daily_reports.date` が unique、`user_id` を持たない）。本開発でもこの前提を維持する。

## 主要ユースケース

1. 利用者が日報入力画面でタスク行（取引先名 / プロジェクト名 / タスク名 / 予定h / 実績h）を入力し、保存する
2. 保存時、同一トランザクション内で以下が実行される
   - `daily_reports` の upsert（現行動作の維持。`raw_data` が引き続き正本）
   - 取引先・プロジェクト・タスクのマスタ解決（既存があれば再利用、無ければ作成）
   - 当該日付の `time_entries` を削除し、日報の内容から再挿入
3. 結果として、取引先別・プロジェクト別・タスク別の実績工数が SQL で集計できる

### 現在の入力構造（UI 実装より）

| 日報の項目 | UI 上の意味 | 対応先 |
|---|---|---|
| `Project.name` | 取引先（placeholder「取引先」・`ProjectBlock.tsx:41`） | `clients.name` |
| `Task.label` | プロジェクト（placeholder「プロジェクト」・`TaskRow.tsx:22`） | `projects.name` |
| `Task.name` | タスク名 | `tasks.title` |
| `Task.actualHours` | 実績工数 | `time_entries.hours` |
| `Task.plannedHours` | 予定工数 | 本開発ではスコープ外 |

## 決定事項

深掘りで確定した設計方針。

| # | 論点 | 決定 |
|---|---|---|
| 1 | ゴール | 集計基盤の構築そのもの。画面・帳票の変更は含めない |
| 2 | 過去データ | バックフィルしない。新規保存分のみ対象 |
| 3 | 再保存時の同期 | 当該日付の `time_entries` を全削除してから再挿入する |
| 4 | 取引先・PJ の名寄せ | `trim` ＋ 連続空白の圧縮のみ。残った文字列の完全一致で既存を再利用し、無ければ自動作成。大文字小文字・全角半角は別物として扱う |
| 5 | 欠損行の扱い | 実績h が 0・空・不正な値の行はスキップ。`h > 0` の行は必ず記録し、取引先・PJ が空なら `type='adhoc'` のタスクとしてマスタ紐づけなしで記録する |
| 6 | 予定工数 | スコープ外（`schedule_entries` / `tasks.estimated_hours` は書かない） |
| 7 | 失敗時の扱い | 日報 upsert・マスタ upsert・`time_entries` の削除＋挿入を 1 トランザクションで包み、いずれか失敗したら全体をロールバックして保存失敗を返す |
| 8 | マルチユーザー | `user_id` は持たせない。現行の単一ユーザー前提を踏襲する |
| 9 | タスクの名寄せ | 同一プロジェクト内で同名なら同一タスクとして再利用する（PJ が無い場合は `title` と `type` をキーにする） |

### 付随して必要になる変更

- `clients.name` および `projects.(client_id, name)` にユニーク制約を追加する（現状は nullable な `code` 側にのみ unique index があり、名前の一意性が DB レベルで担保されていない。同時保存時の二重作成を防ぐため）

## スコープ外（やらないこと）

- 既存 `daily_reports.raw_data` から `time_entries` への一括バックフィル
- 予定工数（`schedule_entries`）および `tasks.estimated_hours` への書き込み
- `user_id` の追加・マルチユーザー対応
- 月次工数管理表・勤怠管理表の読み取り側の差し替え（`MonthlyTimesheetTable.tsx:42` の `p.name === projectName` による名前一致は当面そのまま）
- 取引先・プロジェクト・タスクのマスタ管理画面
- `effort_budgets` / `weekly_effort_budgets` との予算対比
- タスクカテゴリ（`task_categories`）・技術タグ（`technology_tags`）・目標（`goals`）との紐づけ

## 受け入れ条件の種

テストで検証できる形の候補。Phase 1〜3 で設計書の受け入れ条件として確定させる。

1. 日報を保存すると、実績h > 0 の各タスク行につき `time_entries` が 1 件作成される
2. 同じ日報を 2 回保存しても `time_entries` の件数・合計が変わらない（二重計上しない）
3. 保存後、当該日付の `time_entries.hours` の合計が、日報の実績h の合計と一致する
4. 同じ取引先名を含む日報を 2 日分保存しても `clients` は 1 件のままである
5. 同じプロジェクト内の同名タスクを 2 日分保存すると、`tasks` は 1 件・`time_entries` は 2 件になる
6. 前後の空白や連続空白のみが異なる取引先名は、同一の `clients` レコードに解決される
7. 大文字小文字のみが異なる取引先名は、別の `clients` レコードとして扱われる
8. 取引先名・プロジェクト名が空のタスク行は、`type='adhoc'` のタスクとして記録される
9. 実績h が空・0・数値でない文字列の行は、`time_entries` が作成されない
10. タスク行を削除して再保存すると、対応する `time_entries` も消える
11. `time_entries` の書き込みに失敗した場合、`daily_reports` も更新されない（ロールバックされる）
12. 未ログイン状態では保存できない（既存の `requireSession` による保護が維持される）
13. `raw_data` の内容は現行と同一のまま保存される（既存の読み出し経路が壊れない）

## 未決事項

Phase 1〜3（設計書作成・敵対的レビュー・人間承認）で解消する。

1. **中間ケースの扱い**：取引先名はあるがプロジェクト名が空の行をどう記録するか。`projects.client_id` は notNull のためプロジェクトを作れず、`tasks.type='project'` には `project_id` が必須（`tasks.ts:80`）。`tasks.client_id` は nullable で存在するため、`type='adhoc'` かつ `client_id` のみ紐づける案が有力
2. **同一日・同一タスクに複数行**が入力された場合、`time_entries` を複数行にするか合算して 1 行にするか
3. **ユニーク制約追加時の既存データ衝突**：`clients.name` / `projects.(client_id, name)` に制約を足す際、既に重複行が存在した場合の対処（マイグレーション手順）
4. **名寄せ先タスクの状態**：再利用しようとした既存タスクの `status` が `completed` / `archived` だった場合、再利用するか新規作成するか
5. **`tasks.type` の判定ルール**の正式な定義（`project` / `adhoc` / `routine` のどれをどの条件で付けるか）
6. **削除経路の整合**：`deleteReportFn` で日報を削除したとき、対応する `time_entries` も削除するか

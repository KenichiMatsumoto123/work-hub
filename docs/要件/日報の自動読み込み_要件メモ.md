# 日報の自動読み込み 要件メモ

- 作成日: 2026-08-16
- 深掘り: 簡易深掘り実施（grilling skill 未導入のため、grilling の手法に準拠して司令塔が実施。1問ずつ・推奨案つき）

## 目的・背景

日報の永続保存先は PostgreSQL になっているが、日報入力画面（`/`）は DB を読まない。初期化は `sessionStorage`（オートセーブ）→ `localStorage`（テンプレート）の順で、日付を変えても日付欄以外は残る。保存した内容を、画面を開き直したときや日付を切り替えたときに入力画面へ戻せない。

本開発の目的は、**日報入力画面を開いたとき、および日付を切り替えたときに、その日付の PostgreSQL 保存済み日報をフォームへ自動反映する**こと。データ源は DB のみとする。

## 利用者

- 本アプリのログイン済み利用者（日報を入力する人）。既存の日報入力と同じ。
- `daily_reports` に `user_id` は無く、日付が unique。複数人が使う場合は同一データを共有する（既存のデータモデル。本機能で変えない）。

## 主要ユースケース

1. 利用者が `/` を開く。日付は日本時間の今日。その日の DB 行があればフォーム全体に載る。無ければ空の初期値。
2. 利用者が日付欄を別の日に変える。未保存が無ければ確認なしで、その日の DB 行があればそれに置き換わる。無ければ空の初期値（日付欄はその日のまま）。
3. 未保存の入力がある状態で日付を変える・工数管理／勤怠管理へ行く・リロードやタブを閉じる／サイトを離れると、確認が出る。キャンセルなら現状を維持する。
4. 読み込み中はフォームを操作できない。読み込み失敗（401 以外）では操作不可のままエラーと再試行。401 ならログイン画面へ行く。

## 決定事項

深掘りで確定した方針。

| # | 論点 | 決定 |
|---|---|---|
| 1 | データ源 | その日付の DB 行があればそれを正としてフォーム全体を置き換える。無ければ空。オートセーブ・テンプレートは使わない |
| 2 | オートセーブ・テンプレ | 廃止する。読まない・書かない。「テンプレ保存」ボタンも無くす |
| 3 | 「空」の中身 | 現行の初期値（始業 9:00、終業 18:00、休憩 1:00、空の取引先 1 件）。時刻まで真っ白にはしない。日付欄は、画面オープン時は今日、日付切替時は選んだ日付、空にしたときは空 |
| 4 | 未保存確認 | リロード／タブを閉じる／サイトを離れるは `beforeunload`。工数管理・勤怠管理への遷移と日付変更は `window.confirm`。入力画面内のタブ切替（入力／日報／PJ稼働／勤怠）は確認しない |
| 5 | 「入力が行われている」 | 最後に DB から読んだ内容、または最後に「日報保存」した内容と、今のフォームが違うとき。開いた直後の空フォームのまま何も触っていなければ確認しない。「日報保存」成功後は未保存ではない |
| 6 | 読み込み中 | 完了までフォーム操作不可。入力も保存もしない |
| 7 | 読み込み失敗（401 以外） | 操作不可のままエラー表示＋再試行。成功するまで編集も保存もしない（空に見せて上書きする事故を防ぐ） |
| 8 | 読み込み 401 | ログイン画面へ飛ばす（既存の未ログインと同じ） |
| 9 | 日付が空・不正 | DB は呼ばない（失敗扱いにもしない）。空フォーム（日付欄は空）。操作可能。保存時は現行どおり「日付を入力してください」 |
| 10 | 画面オープン時の日付 | 日本時間の今日。その日の保存済みがあればそれを載せる |
| 11 | 「今日」の定義 | 日報入力の日付初期値を日本時間にする（現行の `toISOString()`＝UTC をやめる）。工数管理・勤怠管理の年月はもともとローカル時刻なので本機能では触らない |

### 実装上の帰結（判断ではなく事実）

- 日付変更は画面遷移ではないが、新仕様ではフォームが DB／空に置き換わるため、未保存確認の対象に含める
- `beforeunload` の文言はブラウザが決める（カスタム不可）。SPA のヘッダー遷移は `beforeunload` だけでは出ないため `window.confirm` が別途必要
- 現行の初期化は `apps/web/src/routes/index.tsx` の `sessionStorage` → `localStorage`。日付変更は日付欄だけ更新している
- 取得 API は `getAllReportsFn` / `getReportsByMonthFn` があり、日付 1 件取得の専用関数は無い（設計で新設するか既存を使うかは Phase 1〜3）
- 「テンプレ保存」を無くすと、`savedMsg` のテンプレ保存イベントは日報入力から呼ばれなくなる（既存の reducer を残すかは設計）

## スコープ外（やらないこと）

- 工数管理・勤怠管理の画面や API の変更（読むのは日報入力 `/` だけ）
- 前日コピーや「昨日を複製」
- 複数タブ・複数人の同時編集の排他ロック（既存どおり後から保存した方が勝つ）
- オフライン対応、DB と入力の差分マージ
- オートセーブ・テンプレ保存の復活
- 独自モーダル（未保存確認はブラウザ標準のみ）

## 受け入れ条件の種

テストで検証できる形の候補。Phase 1〜3 で設計書の受け入れ条件として確定させる。

1. `/` を開くと日付は日本時間の今日。その日の DB 行があればフォーム全体がそれと一致する。無ければ空の初期値（9:00〜18:00、休憩 1:00、空の取引先 1 件）
2. 日付を保存済みの日に変えると、フォーム全体がその日の保存内容に置き換わる
3. 日付を保存が無い日に変えると、空の初期値になり、日付欄はその日のまま
4. 日付を空にすると DB を呼ばず、空フォーム（日付も空）で操作可能。保存すると現行どおり「日付を入力してください」
5. 読み込み中はフォーム操作不可。終わるまで入力も保存もしない
6. 読み込み失敗（401 以外）では操作不可のままエラーと再試行。成功するまで編集・保存しない
7. 読み込みが 401 ならログイン画面へ遷移する
8. 未保存ありでリロード／タブを閉じる／サイトを離れると、ブラウザの離脱確認が出る
9. 未保存ありで工数管理・勤怠管理へ行くと `confirm`。キャンセルなら `/` に残る
10. 未保存ありで日付を変えると `confirm`。キャンセルなら日付も内容も変わらない
11. 未保存が無ければ、遷移も日付変更も確認しない
12. 入力画面内のタブ切替では確認しない
13. 「日報保存」成功後は未保存ではなくなる
14. 「テンプレ保存」ボタンは無い。オートセーブもテンプレも読まない・書かない
15. 日本時間 0:00〜8:59 に `/` を開いても、日付は日本の今日であり UTC の前日ではない

## 未決事項

Phase 1〜3（設計書作成・敵対的レビュー・人間承認）で解消する。

1. **日付 1 件取得の API**：`getAllReportsFn` を使うか、日付指定の取得関数を新設するか
2. **読み込み中・失敗時の UI 文言と配置**（「読み込み中」「読み込みに失敗しました」の出し方。ボタンの有無）
3. **`window.confirm` の文言**
4. **「今日」の実装箇所**：`getToday()` を日本時間にして `defaultDailyReport` から使うか、日報入力側だけ変えるか
5. **dirty 比較の単位**：JSON 文字列比較か、フィールド単位か。デフォルト値の正規化（空文字と未定義など）
6. **テンプレ廃止に伴う `savedMsg` のテンプレ経路**：残すか、日報入力から削除するか

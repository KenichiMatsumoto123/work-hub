# ブランチ運用方針

- **作成日**：2026-07-12（ドラフト・人間レビュー待ち）
- **位置づけ**：10フェーズフローにおける git ブランチ運用のルール。Phase 4（実装計画書作成）の「実装スコープの決定」ステップの判断基準として参照される
- **背景**：AI駆動TDDにおける人間レビューのボトルネックを軽減する目的で検討。ブランチ構造そのものを変えてもレビューゲートの「数」は減らないが、**1回あたりのレビュー対象を小さくする**ことでスループットを上げられる、という観点から設計した

---

## 1. 基本モデル

developから機能ブランチ（`add/<機能名>`）を1本切り、そのブランチ内でPhase 1〜10を完走してdevelopへマージするのが基本形（現行どおり）。

## 2. 大規模機能の分割運用

対象機能のボリュームが大きく、1ブランチでの実装〜developマージまでが長期化しそうな場合に適用する。**設計（Phase 1-3）は機能全体を対象に一度で行うが、実装（Phase 4以降）は安全にマージできる単位に分割し、複数回に分けてdevelopへ直接マージしてよい。**

### 2.1 検討して却下した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| 入れ子ブランチ | `add/<機能名>` の中からさらにサブブランチを切り、`add/<機能名>` へマージ、最後に developへ | (1) `add/<機能名>` が第2の統合ポイントになり、長生きするほどdevelopとの乖離が蓄積する (2) サブブランチのPRには既存CIが発火しない（`ci.yml` は develop/main/staging 宛のPRのみトリガー） (3) 最終的な「featureブランチ→develop」マージが最も統合リスクの高いマージになり、小さく統合する狙いに反する |
| 小PRをfeatureブランチへ集約 | WBSタスクごとに `add/<機能名>` 宛の小さいPRを作り、最後に一括でdevelopへ | 入れ子ブランチと同じCIトリガーの穴がある。加えて `add/<機能名>` 自体が長生きするブランチになる点は解消されない |
| 真のトランクベース開発（フィーチャーフラグ） | 小さい変更を継続的に直接developへマージし、未完成部分はフラグで隠す | フィーチャーフラグの実装基盤が存在せず新規構築コストが発生する。また認可・PIIへの配慮が重要なプロジェクトで「フラグの裏に隠したつもりが直接アクセス可能」という露出事故のリスクがある。MVP1検証段階の投資として過剰 |

### 2.2 採用モデル：安全な単位への垂直分割

```
develop
  └ add/<機能名>（Phase 1-3：機能全体の設計を確定）
       ↓ Phase 4：実装スコープの決定（本ブランチで実装する範囲を決める）
       ↓ 決定したスコープのみ Phase 5-10 を実施
       ↓ develop へ直接マージ
  └ （後続スコープが残る場合）develop から新たにブランチを切り、
     同じ設計書を参照して次のスコープを実装（Phase 1-3 は再実施不要）
```

- 全てのブランチが直接developへマージされるため、途中に長生きする中間ブランチが存在しない
- 各スコープのPRは既存の `ci.yml` のトリガー（develop/main/staging 宛PR）でそのままCIが機能する。**追加のCI設定変更は不要**

### 2.3 スコープ分割の安全基準

| 種別 | 先行マージの可否 |
|---|---|
| 新規追加のみで完結する部分（既存機能から参照されない・依存されない） | 安全。優先して先行スコープにする |
| 既存の挙動・レスポンス形式・DBスキーマを変更する部分 | 危険。依存先が揃うまで後続スコープに回すか、変更元と同一スコープにまとめる |

「バックエンド先行・フロント後続」は分割の一例に過ぎない。画面単位・エンドポイント単位など、機能の性質に応じて柔軟に判断する。**安全性の最終判断は人間が行う**（AIは分割案を提案するのみ）。

新規追加スコープを先行マージする場合も、認可・バリデーション等のセキュリティ要件は完全な状態で実装する（「配線されていないから安全」は認可の代わりにはならない。URLを直接叩けば到達可能なため）。

### 2.4 ブランチ命名

> **本リポジトリ（work-hub）での運用**
> ベースブランチが `develop` である点は本書のとおり。命名は `add/<機能名>` を基本としつつ、AI エージェントが作業する場合は `claude/<作業名>` 形式のブランチが指定されることがある（例: `claude/effort-tracking-spec-r06xxh`）。その場合は指定されたブランチ名を優先し、本節のリネーム提案は行わない。


機能全体を指す名前（`add/<機能名>`）で作成した後、Phase 4でスコープが機能全体でないと確定した場合、スコープを反映した名前にリネームすることをユーザーに提案する（例：`add/<機能名>_一覧API`）。リネームは対象ブランチの作業量がまだ小さいうちに行うことを推奨する（プッシュ済みの場合はローカルでリネーム→リモートの旧ブランチ削除→新ブランチをプッシュ）。

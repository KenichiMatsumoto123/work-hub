#### F-001: 0 < 実績h < 0.005 の行が丸めで 0.00 になり、`chk_hours_positive` 違反で保存全体が失敗する
- **観点 / レーン**: 境界値・DB制約との衝突（レーンC）
- **該当箇所**: 「R-2 対象行の抽出とスキップ条件」判定2／「R-3 実績h の丸め」／「例外系 E-4」／AC-01・AC-02。制約実体は `apps/web/src/server/schema/tasks.ts:109`
- **問題**: R-2 判定2 は「変換結果が 0 以下」のみをスキップ対象とするため、`0.001` / `0.004` / `0.0049` は「対象行」として通過する。R-3 でこれを小数第2位に丸めると `0.00` になり、`time_entries.hours` へ `0.00` を INSERT することになる。`chk_hours_positive`（`hours > 0`）はこれを拒否する。仮にアプリ側で丸めなくても、`hours` は `numeric(4,2)` であり PostgreSQL は列型へキャストしてから CHECK を評価するため、`0.001` を渡しても同じく `0.00 > 0` で違反する（アプリ実装では回避不能）。設計書 E-4 の「本設計では 0 以下の行を事前にスキップするため到達しない想定」は**事実として誤り**である。
- **影響**: 実績h に `0.001` のような微小値を 1 行でも入力すると、T-1 のトランザクション全体がロールバックし、**日報そのものが保存できなくなる**。利用者には `保存エラー: <PostgreSQL の制約違反メッセージ>` という原因の分からない文言だけが 2 秒表示される。従来は `raw_data` に何でも保存できていたため、これは本変更が持ち込む新規の保存不能パスである。さらに AC-01 と DB 制約が直接矛盾しており、Phase 5 のテストがこの矛盾をそのまま実装不能な期待値として固定するおそれがある。
- **失敗シナリオ**: 実績h に `0.004` を入力 → R-2 判定1(数値)・判定2(>0)・判定3(≤24) をすべて通過 → R-3 で `0.00` → INSERT → `chk_hours_positive` 違反 → トランザクション全体ロールバック → 日報が 1 行も保存されない。
- **推奨対応**: R-2 のスキップ条件を「**丸め後の値が 0 以下ならスキップ**」に改める（判定順を「変換 → 丸め → 0以下判定 → 24超判定」に再定義する）。あわせて E-4 の記述を修正し、AC-19 に「実績h が 0.004 のように丸めると 0.00 になる行は `time_entries` が作成されない」を追加して境界を受け入れ条件として固定する。
- **仕様決定の要否**: 不要

#### F-002: 対象行が 0 件のときの `time_entries` 一括 INSERT の挙動が未定義（空配列 INSERT で保存が失敗する）
- **観点 / レーン**: 空状態（レーンC）＋ 非機能要件と T-1 の食い違い（レーンA・F-A-015 を統合）
- **該当箇所**: 「非機能要件 > 性能」の「`time_entries` の INSERT は 1 回の複数行 INSERT にまとめる。」／「T-1 保存」手順3／E2E候補カタログ C-2
- **問題**: 設計は `time_entries` の INSERT を 1 回の複数行 INSERT にまとめることを実装制約として指示しているが、**対象行が 0 件になった場合に INSERT 自体を発行しない**という規定がない。Drizzle の `insert().values([])` は例外を投げる（`node_modules/drizzle-orm/pg-core/query-builders/insert.js:31-33` — `throw new Error("values() must be called with at least one value")`）。この例外はトランザクション内で発生するため、`daily_reports` の upsert ごとロールバックされる。加えて、非機能要件の「1 回の複数行 INSERT にまとめる」と T-1 手順3 の「対象行ごとに…`time_entries` を INSERT」は文面として食い違っており、どちらが正かが決まっていない（レーンA F-A-015）。
- **影響**: 対象行 0 件は例外的な入力ではなく**通常運用で頻発する状態**である。(a) `defaultDailyReport()` はタスク行 1 件・実績h 空で始まるため、朝に予定だけ入れて保存する運用が該当する。(b) 設計書自身の E2E 候補 C-2「実績h を空欄のままタスク行を残して保存する → **エラーにならず保存され**、その行は工数として記録されない」と正面から矛盾する。(c) タスク行をすべて削除して保存し直す運用（AC-07 の極端形）も該当する。つまり、この規定不足のまま実装されると**日報の初期保存が壊れる**。
- **失敗シナリオ**: 実績h を 1 つも入力せずに「日報保存」を押す → 対象行 0 件 → 空配列で複数行 INSERT → 例外 → トランザクションロールバック → `保存エラー: values() must be called with at least one value` が表示され、日報が保存されない。
- **推奨対応**: T-1 の手順3に「**対象行が 0 件の場合は `time_entries` の INSERT を発行しない**（削除のみ行い、日報の保存は成功させる）」を明記する。非機能要件と T-1 の文面を「対象行が 1 件以上ある場合、1 回の複数行 INSERT にまとめる」に統一する。あわせて「実績h が有効な行が 1 件も無い日報を保存しても成功し、当該日付の `time_entries` は 0 件になる」を AC として追加する（現状の AC 群にこのケースが 1 件も無い）。
- **仕様決定の要否**: 不要（C-2 の期待結果として既に「エラーにならず保存される」と要件側の答えが出ている）

#### F-003: 「削除範囲が当該日付に限定されること」を検証する受け入れ条件が存在しない
- **観点 / レーン**: 要件の網羅性（レーンB）
- **該当箇所**: 受け入れ条件 AC-01〜AC-27 全体／「トランザクション設計 T-1」（`DELETE FROM time_entries WHERE date = <対象日>`）／「テストレベル判定 > 影響度トリガー > 不可逆操作」の理由欄
- **問題**: 設計書は不可逆操作トリガー該当の理由として「**削除範囲の指定を誤ると他日付の実績を消す**」と自ら明記している。にもかかわらず、27 件の AC のいずれも「**他日付の `time_entries` が影響を受けないこと**」を規定していない。AC-03/06/07/08 はすべて「当該日付の」件数・合計のみを対象にしており、AC-09 も「当該日付の `time_entries` も削除される」までしか言っていない。`deleteReportFn` 側についても同様に他日付の残存を規定した AC がない。
- **影響**: 設計書は「実装承認ゲートをスキップする設定のため、Phase 5 のテスト観点はこの条件を**唯一の根拠**として起案される」と宣言している。したがって AC に無い性質はテスト化されない。結果として、`WHERE date = ...` を書き落とした実装（`DELETE FROM time_entries` 全件削除）や、範囲を月単位で誤指定した実装が、**AC-01〜AC-27 の全件を PASS したまま通過する**。AC-03 も AC-06 も全件削除実装で成立してしまう。過去の全工数実績が失われる不可逆なデータ消失であり、`time_entries` は「実績の唯一のマスター」であるため復旧手段がない（バックフィルは非ゴール）。
- **失敗シナリオ**: 4/1〜4/28 の日報を保存済み → 4/28 の日報を再保存 → 実装の DELETE に日付条件が欠落 → 4/1〜4/27 の `time_entries` が全消失 → 4/28 分だけ再挿入されるため AC-01〜AC-09 はすべて PASS → 誰も気づかない。読み取り側は非ゴールで `time_entries` を表示する画面が存在しないため、消失は SQL を直接叩くまで発覚しない。
- **推奨対応**: 以下の AC を追加する。①別日付の `time_entries` が存在する状態で対象日の日報を保存しても、別日付の件数・合計は変化しない。②別日付の `time_entries` が存在する状態で `deleteReportFn` を実行しても、別日付の `time_entries` および `daily_reports` は残る。あわせてテストレベル判定の「不可逆操作」欄が挙げた理由と AC の対応関係を明示し、結合(DB込み)テストの必須観点に組み込む。
- **仕様決定の要否**: 不要

#### F-004: R-1 の空白圧縮ルールが本文内で矛盾し、全角スペース単独の扱いが一意に決まらない
- **観点 / レーン**: 仕様の曖昧性（レーンA）
- **該当箇所**: 「R-1: 名前の正規化」手順2と直後の補足
- **問題**: 手順2は「**連続する**空白を半角スペース 1 つに圧縮する」と書き、補足は「全角スペースも「空白」として扱い**半角スペース 1 つに畳む**」と書いている。実装者は2通りに読める。(a) 長さ2以上の連続だけを畳む＝`"A　社"`（単独の全角スペース）はそのまま残る、(b) 長さ1以上のすべての空白列を半角スペース1つに置換＝`"A　社"` → `"A 社"`。前者では `"A　社"` と `"A 社"` が別の `clients` レコードになり、後者では同一になる。

- **仕様決定の要否**: 不要

#### F-005: R-1 の「空白文字」の集合が未定義で、`.trim()` 実装と列挙正規表現実装で結果が割れる
- **観点 / レーン**: 仕様の曖昧性（レーンA）
- **該当箇所**: 「R-1: 名前の正規化」（「半角スペース・全角スペース・タブ・改行」の列挙）
- **問題**: 列挙は4種だが、JS の `String.prototype.trim()` / `\s` はこれより広い集合（NBSP `U+00A0`、`\r`、垂直タブ `\v`、フォームフィード `\f`、`U+2000`〜`U+200A`、`U+FEFF` 等）を空白として扱う。実装者Aが `name.trim().replace(/\s+/g, ' ')` と書き、実装者Bが列挙どおり `/[ 　\t\n]+/` と書くと、`"A社 "`（Excel/Web からのコピペで頻出）に対して A は `"A社"`、B は `"A社 "` を返す。「改行」が LF のみか CRLF を含むかも未定義。
- **影響**: F-004 と同じくマスタの二重化を招く。さらに、この差は Phase 5 のテストでも露見しない — テスト作成者も同じ曖昧な記述から出発するため、実装と同じ空白集合を仮定したテストになりトートロジー化する。
- **失敗シナリオ**: 取引先名を業務システムからコピペして末尾に NBSP が混入 → 実装Bでは「A社」と別レコードになり、以後の集計が分裂する。ユニーク制約は文字列が異なるため発火しない。
- **推奨対応**: 「JS の `String.prototype.trim()` が空白とみなす文字集合＋`U+3000`」のように正規表現・API レベルで一意に規定する（例：`s.replace(/[\s　]+/gu, ' ').trim()` を仕様として明記）。
- **仕様決定の要否**: 要

#### F-006: 実績h の数値解釈が `Number()` の実挙動と乖離し、かつ既存 UI の集計（`parseFloat`）とも食い違う
- **観点 / レーン**: 仕様の曖昧性（レーンA F-A-003）＋ 異常系・型変換（レーンC F-C-004）＋ 分類の食い違い（レーンA F-A-011）を統合
- **該当箇所**: 「R-2 対象行の抽出とスキップ条件」判定1・判定2および直後の補足／「データ項目マッピング表」No.4／AC-03／AC-19
- **問題（レーンA）**: 判定1は「`Number()` で変換できない（**数値以外の文字列を含む**）」という2つの基準を等価であるかのように並記しているが、両者は等価でない。`Number('1e2')` = **100** → 判定3に落ち保存全体がエラー。`Number('0x10')` = **16** → 判定4に落ち16時間の実績として記録される。`Number('Infinity')` = Infinity → 保存全体エラー。`Number('１.５')`（全角数字）= NaN → 無言でスキップ。`Number('1,5')` = NaN → スキップ。どの基準を実装の正とするかで結果が3通りに分かれる。さらに判定1は空文字・空白のみを「変換できない」に分類する一方、直後の補足は「`Number('')` は `0` を返すため判定2でスキップ」と書いており分類が食い違う（F-A-011）。
- **問題（レーンC）**: 本設計は `Number()` を指定しているが、**既存アプリの実績h 集計はすべて `parseFloat` である**（`ProjectBlock.tsx:30`、`routes/index.tsx:142`、`lib/report-generator.ts:11-12,38,40`）。両者は末尾に非数字を含む入力で結果が食い違う（`parseFloat('7.5h') === 7.5` / `Number('7.5h') === NaN`、`parseFloat('3時間') === 3` / `Number('3時間') === NaN`）。設計書にはこの差分への言及が一切ない。
- **影響**: 「16時間」の誤記録は集計を直接汚染する。全角数字の無言スキップは、実績h 入力欄が `type` 指定のないテキスト入力で IME が有効なため現実に起こりうるが、利用者へのフィードバックが一切ない。`'1e2'` の保存全体エラーは打ち間違いで日報そのものが保存できなくなるクリティカルパス障害である。`parseFloat` との乖離では、利用者は画面ヘッダの「合計: … → 7.5h」や日報テキスト出力でその工数が計上されているのを見ているのに `time_entries` には 1 件も作られない — **無警告のサイレントな工数欠落**であり、正規化データが「集計基盤」として信頼できなくなるという本機能の目的そのものを損なう。また AC-03 は「日報の実績h の合計」の定義が `Number()` 基準か `parseFloat` 基準（＝利用者が画面で見ている値）かで結論が変わるため、受け入れ条件として一意に検証できない。
- **失敗シナリオ**: 実績h に `7.5h` と入力 → 画面合計は 7.5h、日報テキストにも 7.5h と出力 → 保存 → `time_entries` は 0 件 → 月次集計で 7.5 時間が消える。エラーも警告も出ない。／実績h に全角で「１．５」と入力 → 「保存しました ✓」が出るがその行の 1.5h は残らない。
- **推奨対応**: 判定1を機械的基準1本に統一する（例：`/^\d+(\.\d+)?$/` にマッチしない文字列はスキップ、と規定して `1e2`/`0x10`/`Infinity` を明示的にスキップ側へ寄せる）。`Number()` と `parseFloat` のどちらを正とするかを明記し、既存 UI 側との差分を「許容する／揃える」いずれかで決める。AC-03 の「日報の実績h の合計」を「R-2 で対象行と判定された行の丸め後の合計」と定義し直す。「数値として解釈できないのに空でない実績h」を黙って捨てるか検証エラーとして返すかを決める。
- **仕様決定の要否**: 要

#### F-007: 丸め仕様が実装依存で、丸め境界（x.xx5）と 24 判定のタイミングが未定義
- **観点 / レーン**: 仕様の曖昧性（レーンA F-A-004）＋ 境界値（レーンC F-C-005・F-A-014）を統合
- **該当箇所**: 「R-3 実績h の丸め」／「R-2」判定3／AC-02／AC-03／AC-21
- **問題**: (1) 「小数第 3 位以下を四捨五入」としか書かれておらず、丸めの実行系が未定義。実績h は文字列として入力され `Number()` を経由すると2進浮動小数の誤差が入るため、手段ごとに結果が食い違う：`Math.round(2.675 * 100) / 100` = **2.67**（`2.675*100` が `267.49999999999994` になるため）、`(2.675).toFixed(2)` = **"2.67"**、文字列 `'2.675'` をそのまま `numeric(4,2)` に渡す = **2.68**（PostgreSQL の numeric は10進で half-away-from-zero）、人間が「四捨五入」と聞いて期待する値 = **2.68**。つまり設計書の日本語の規定（2.68）を、最も素直な JS 実装（2.67）が満たさない。同様に `Math.round(1.005 * 100) / 100 === 1`、`(1.005).toFixed(2) === '1.00'`。(2) R-2 判定3 の「24 を超える」が、`Number()` の結果（丸め前）に対する判定なのか、R-3 で丸めた後の値に対する判定なのかが明記されていない。`24.004` は丸め前判定ならエラー、丸め後判定なら `24.00` として正常保存となり、結論が正反対になる。
- **影響**: AC-02・AC-03・AC-21 の期待値が一意に決まらない。Phase 5 のテスト作成者は自然な解釈で `2.675 → 2.68` を期待値に書き、Phase 8 の実装者は `Math.round` を書く可能性が高く、Green にならずに Phase 8↔5 の往復が発生する。本フローは Phase 7 でテストが人間承認・凍結されるため、凍結後にこの衝突が出ると承認済み成果物の変更＝人間エスカレーションになる。
- **失敗シナリオ**: テスト側が「`1.005` → `1.01`」を期待し、実装が `Math.round(x*100)/100` を使って `1.00` を返す → Phase 8 でテストを通すために実装ではなくテストを直す圧力がかかる（Phase 8 はテスト修正禁止のため収束ループが空転する）。
- **推奨対応**: R-3 に丸めのアルゴリズムを一意に規定する。R-2 判定3 には丸め前・丸め後のどちらで判定するかを明記し、`24.004` の期待挙動を AC に追加する。
- **仕様決定の要否**: 不要（レーンC 判定）／要（レーンA 判定）→ **司令塔の裁定: 不要**。丸めの実行系は業務判断ではなく設計者が決めてよい技術的選択であり、決めて書けば解消する（レーンC の判定を採用）。ただし決めた内容は Phase 3 の人間承認の対象に含める。

#### F-008: M-3 の「NULL も値として一致判定する」の実現方法が未定義で、素直な実装では adhoc タスクが永久に解決できない
- **観点 / レーン**: 仕様の曖昧性（レーンA）
- **該当箇所**: 「M-3: タスク（`tasks`）」／「解決の共通方針」
- **問題**: M-3 は検索キーを「`project_id`・`client_id`・`title` の 3 つ組（NULL も値として一致判定する）」とだけ書き、SQL レベルでどう実現するかを規定していない。SQL の `=` は NULL に対して常に UNKNOWN を返すため、Drizzle で素直に `and(eq(tasks.projectId, null), eq(tasks.clientId, null), eq(tasks.title, t))` と書くと、既存の adhoc タスクは**決してヒットしない**。設計書の共通方針は「見つからなければ `ON CONFLICT DO NOTHING` で挿入 → 再 SELECT」なので、挿入は S-3（`NULLS NOT DISTINCT`）に弾かれて 0 行、再 SELECT も同じ `= null` で 0 行となり、**`task_id` が確定できないまま `time_entries` の INSERT に到達して NOT NULL 違反 → 保存全体がロールバック**する。
- **影響**: AC-16（取引先・プロジェクトともに空）と AC-17（プロジェクトのみ空）は要件メモ決定5で明示された主要ケースであり、そのユーザーが日報を**一切保存できなくなる**。設計書だけを根拠に実装する Phase 8 の `impl-builder` は、この落とし穴を回避する根拠を設計書から得られない。
- **失敗シナリオ**: 取引先欄を空にしたまま実績h を入力して保存（E2E 候補 C-3 とまったく同じ操作）→ 2回目の保存以降 NOT NULL 違反で保存失敗。
- **推奨対応**: M-3 に「検索条件は `IS NOT DISTINCT FROM` を用いる（Drizzle では `sql` テンプレートで明示する）」と実現手段まで書く。あわせて `ON CONFLICT` のアービタが S-3 のインデックスに一致することも明記する。
- **仕様決定の要否**: 不要

#### F-009: 取引先が空の行では、異なるプロジェクトの同名タスクが S-3 により 1 タスクへ統合される
- **観点 / レーン**: 重複・衝突（レーンC F-C-007）＋ 仕様の曖昧性（レーンA F-A-006）を統合
- **該当箇所**: 「R-4 `tasks.type` の判定」（特に「取引先名が空の場合、プロジェクト名が入力されていてもプロジェクトマスタは作成しない」）／「S-3」／「R-5 タスク名の既定値」／AC-16
- **問題**: 取引先名が空の行は `client_id = NULL` / `project_id = NULL` の adhoc タスクになる。S-3 は `UNIQUE NULLS NOT DISTINCT (project_id, client_id, title)` であるため、**`title` が同じなら全期間・全プロジェクトにまたがって同一タスク 1 件に統合される**。日報の入力欄では取引先が空でもプロジェクト欄（`Task.label`）とタスク名は入力でき、「実装」「調査」「MTG」「定例」といった汎用的なタスク名は複数のプロジェクトで重複するのが常態である。R-4 は帰結として「プロジェクト名は正規化テーブルに残らない」とだけ書いているが、真の帰結は「取引先が空の行どうしは、プロジェクト名が異なっていてもタスク名さえ同じなら同一の集計単位に融合する」ことであり、これが設計書のどこにも書かれていない。S-3 の副作用の記述は「同一プロジェクト内に同名タスクを 2 件作れない」ことにしか触れていない。R-5 の既定値 `(名称未設定)` はこれをさらに悪化させ、タスク名も取引先も空の全行が**単一のタスクレコード**に集約される。

- **失敗シナリオ**: 取引先欄を空にしたまま、プロジェクト「請求書改修」タスク「調査」に 2h、プロジェクト「認証改修」タスク「調査」に 3h を入力して保存 → `tasks` は「調査」1件、`time_entries` は 2 件で合計 5h。SQL でプロジェクト別に分けることは永久にできない。
- **推奨対応**: 少なくとも設計書に本挙動を明示する。そのうえで (a) 取引先が空でプロジェクト名がある行の扱いを再検討する（「取引先未設定」相当の既定 client を作る／保存時に検証エラーとする／プロジェクト名をタスク名に連結して `title` を一意化する 等）、または (b) 非ゴールとして「取引先が空の行はタスク単位集計の対象外である」ことを受け入れ条件と非ゴールの双方に明記し、AC-16 に既知の帰結として書き足す。
- **仕様決定の要否**: 要

- **影響**: 要件メモを承認根拠として Phase 3 の人間レビューに臨む人間が、確定済みと思っている名寄せ方針が変わっていることに気づけない。取引先ごとに adhoc タスクが分かれると、「取引先横断の共通作業（定例会議・社内作業）」の累計工数が取引先数だけ分割され、本機能の目的である横断集計が意図と異なる粒度になる。
- **推奨対応**: 写像表を「要件メモの決定事項からの変更点」も含む形に拡張し、決定事項 #9 の変更と理由を明記する。Phase 3 の人間承認で明示的に確認する項目として未決事項表に上げる。対応する AC を追加する。
- **仕様決定の要否**: 要

#### F-016: 名前が 255 文字を超える入力に対する規定がなく、保存全体が失敗する（従来は保存できていた）
- **観点 / レーン**: データ量・文字列長／DB制約との衝突（レーンC F-C-003）＋ 要件の網羅性（レーンB F-B-004）＋ レーンA F-A-013 を統合
- **該当箇所**: 「データ項目マッピング表」No.1-3／「R-1 名前の正規化」／「エラー処理」。実体は `apps/web/src/server/schema/master.ts:16,38` と `tasks.ts:23`（いずれも `varchar(255)`）
- **問題**: 取引先名・プロジェクト名・タスク名は正規化後そのまま varchar(255) の列へ書き込まれるが、長さの検証・切り詰め規定が設計書のどこにもない。入力欄（`TaskRow.tsx` / `ProjectBlock.tsx`）には `maxLength` が無く、貼り付けで容易に 255 文字超が入る。R-1 の正規化は空白圧縮のみで長さを縮めない。マッピング表にも桁数欄がない。エラー処理表も「検証エラー＝実績h 24 超」しか列挙していない。
- **影響**: 255 文字超の名前が 1 つでもあると `value too long for type character varying(255)`（22001）が発生し、トランザクション全体がロールバックして**日報が保存できなくなる**。本変更前は `raw_data`（JSONB）に長さ無制限で保存できていたため、これは既存機能のデグレードであり、クリティカルパス業務（日報保存）の停止に直結する。しかも利用者に出るのは PostgreSQL の英語メッセージであり、「どの欄を削ればよいか」が分からない（設計書のエラー処理方針「利用者が入力を修正できる情報を含める」に反する）。
- **失敗シナリオ**: メールから会社名込みの長い件名をタスク名欄に貼り付け（300文字）→ 保存 → `保存エラー: value too long for type character varying(255)` → 当日の日報が一切保存されない。利用者はどの行が原因か分からない。
- **推奨対応**: R-1 に桁数ルールを追加する。(a) 256 文字以上を検証エラーとして実績h 24 超と同様にトランザクション前で落とし、対象欄と入力値を含む日本語メッセージを返す、または (b) 正規化後 255 文字で切り詰めて保存する（切り詰めると別名寄せになる副作用を明記）。あわせて対応する AC（境界 255／256）とデータ項目マッピング表への桁数欄追加を行う。
- **仕様決定の要否**: 要

#### F-017: 並行保存の扱いが未定義（デッドロック・分離レベル・再SELECT 空振り・同一日付の二重計上）
- **観点 / レーン**: 並行（レーンC F-C-006）＋ 非ゴールの明確性（レーンB F-B-005）＋ レーンA F-A-016 を統合
- **該当箇所**: 「マスタ解決ロジック仕様 > 解決の共通方針」／「T-1」／「T-3 原子性の担保」／「例外系 E-3」／「非ゴール」／「自己レビューチェック」
- **問題（レーンC）**: (1) **デッドロック**：異なる日付の保存が同時に走り、双方が同じ新規マスタ群を**異なる順序で**作ろうとすると（TX1 が 取引先A→取引先B、TX2 が B→A）、追加する UNIQUE 制約（S-1〜S-3）の未コミットタプル同士で相互待機となりデッドロック（40P01）になる。設計に処理順序の固定も再試行もなく、E-3 は「ロールバックして例外を伝播」とだけ書くため、利用者には原因不明の `保存エラー: deadlock detected` が出て日報が失われる。(2) **分離レベル依存の明記なし**：「挿入を無視して再検索し既存行の ID を採用する」は、文ごとに新しいスナップショットを取る READ COMMITTED でのみ成立する。REPEATABLE READ 以上では再SELECT が競合相手のコミット行を見られず 0 件を返す。T-3 は `db.transaction()` を使うとだけ述べ、分離レベルを既定から変えてはならないという前提を記していない。(3) **再SELECT が 0 件だった場合の挙動が未定義**：M-1〜M-3 は「見つかればその ID」「無ければ作成」しか定義しておらず、再SELECT 空振り時に何を返すかが無い。NULL のまま進むと `projects.client_id`（NOT NULL）や `time_entries.task_id`（NOT NULL）で NOT NULL 違反になる。
- **問題（レーンB）**: 設計書内で並行性に触れているのはマスタ解決の 1 文のみで、これは**マスタ行の重複作成**しか防がない。本設計の中核である「日付単位で `time_entries` を DELETE してから INSERT する」方式そのものの並行性は一切扱われていない。READ COMMITTED では、同一日付に対する 2 つのトランザクションが互いの未コミット行を DELETE 対象として認識しないため、両者がコミットすると当該日付の `time_entries` が二重に残る（AC-06「二重計上しない」が並行時に破れる）。それにもかかわらず**自己レビューチェックは「並行保存を扱った」と主張**し、非ゴール節にも限定がない。加えて「単一ユーザーだから同時保存は起きない」という前提も、`AUTH_ALLOWED_EMAILS` が複数メール・ドメイン指定を受け付け未設定時は無制限であるため担保されていない。
- **影響**: 実装者・レビュワー・Phase 3 の承認者が「並行性は検討済み」と誤認し、誰も設計判断を求めない。受け入れる場合であれ対処する場合であれ方針が文書化されていないため、Phase 8 の実装者が場当たりに決める。本アプリは複数タブでの操作が容易（オートセーブ付きの単一画面）であり、二重送信で発現しうる。
- **失敗シナリオ**: 8/12 の日報と 8/13 の日報を別タブでほぼ同時に保存。どちらも新規取引先 A・B を含み、ブロックの並び順が逆 → デッドロック検出で片方が中断 → その日の日報が保存されない。
- **推奨対応**: (a) T-1 に「マスタは正規化後の名前でソートした順に解決する」等、ロック取得順序を固定する規定を追加する。(b) T-3 に分離レベル（READ COMMITTED）の前提を明記する。(c) M-1〜M-3 に再SELECT 空振り時の終端条件を定義する。(d) 同一日付の同時保存について、非ゴールとして受け入れる（二重計上の可能性を明記）か、`SELECT ... FOR UPDATE` 等で直列化するかを決める。(e) 自己レビューチェックの「並行保存を扱った」を実際の記述内容と一致するよう修正する。
- **仕様決定の要否**: 要

#### F-018: E2E 候補カタログ C-5「保存済みの日報を削除する」は UI から実行不能
- **観点 / レーン**: テストレベル判定の妥当性（レーンB）
- **該当箇所**: 「E2E 候補カタログ」C-5／「業務フロー > 例外系」E-5／AC-09
- **問題**: `deleteReportFn` および `reportStorage.delete` を呼び出している UI コードは**リポジトリ内に一切存在しない**（参照は `server/functions/reports.ts:103`（定義）と `lib/storage.ts:6,69`（ラッパ）のみ。`routes/` からの呼び出しは 0 件で、画面に削除ボタンが無い）。E2E 候補カタログはトリガー表 5 章の定義上「画面操作シナリオを人間が手動実施する」ための一覧であり、C-5 は誰も実施できない。同様に例外系 E-5 も、実在しない画面操作を前提にした記述になっている。（司令塔が `grep` で確認し、この指摘が正しいことを検証済み）

- **仕様決定の要否**: 不要

### Critical

#### F2-001: R-3 の丸め規定式が NaN を返す入力で R-2 の判定2・判定3 を同時にすり抜け、`hours = NaN` が保存される
- **観点 / レーン**: 境界値・DB制約との衝突（レーンA F2-A-001 ＋ レーンC F2-C-001。**2レーンが独立に同一の Critical を検出**）
- **該当箇所**: 「R-3」規定式／「R-2」判定表（判定2・判定3 がいずれも丸め後の値に対する判定であること）／例外系末尾「`chk_hours_positive` に違反する経路は存在しない」／AC-01・AC-02・AC-03。制約実体は `apps/web/src/server/schema/tasks.ts:96,109`
- **問題**: 規定式 `Number(\`${Math.round(Number(\`${n}e+2\`))}e-2\`)` は `String(n)` が最短往復表現を返す性質に依存するが、**`String(n)` が指数表記を返す領域で壊れる**。JavaScript は絶対値が 1e21 以上、または 1e-6 未満の数値を指数表記で文字列化する。
  - `n = 1e-7`（入力 `"0.0000001"`）→ `"1e-7e+2"` → **NaN**
  - `n = 1.2345678901234567e19`（入力 `"12345678901234567890"`＝20 桁の貼り付け）→ `"12345678901234567000e+2"` = 1.2345678901234568e21 → `"1.2345678901234568e+21e-2"` → **NaN**
  - `n = 1e23`（入力 `"99999999999999999999999"`）→ `"1e+23e+2"` → **NaN**

  R-2 の判定は「1: `parseFloat` が有限か（`1e19` も `1e-7` も有限なので通過）→ 2: 丸め後が 0 以下か（`NaN <= 0` は **false**）→ 3: 丸め後が 24 超か（`NaN > 24` も **false**）→ 4: 対象行」であるため、**NaN は判定2 と判定3 の両方を素通りして「対象行」に分類される**。これは Round 1 の F-001 修正（判定を丸め前から丸め後へ移した）が直接生んだ経路であり、丸め前判定であれば `1e19` は判定3 でエラーになっていた。
- **影響**: `time_entries.hours` に `NaN` が書き込まれる。PostgreSQL の `numeric` は特殊値 `NaN` を受理し、かつ**比較において NaN を全ての非 NaN 値より大きい**として扱うため、`chk_hours_positive`（`hours > 0`）は**通過する**。`numeric(4,2)` の精度・位取りも NaN には適用されないため 22003 も出ない。すなわち設計書が「到達しない」と断言した唯一の防波堤が機能せず、**無警告で NaN が永続化される**。以後 `SUM(hours)` を含む全ての集計（本機能のゴールそのもの）が期間全体で NaN になり、どの行が原因かは SQL を直接叩くまで分からない。読み取り側の画面は非ゴールで存在しないため発覚が遅れ、バックフィルも非ゴールのため復旧は手動 SQL のみ。仮に実装が数値 NaN をドライバに渡して型エラーになる経路を通った場合でも、結果は「トランザクション全体ロールバック＝日報が保存できない」という新規の保存不能パスであり、いずれの分岐でも設計目標に反する。AC-29〜AC-36 のいずれもこの入力を扱っていないため、Phase 5 のテストは全件 PASS する。
- **失敗シナリオ**: 実績h 欄に別セルからコピーした 20 桁以上の数字列を誤って貼り付けて保存 → 判定1 通過（有限）→ 丸めが NaN → 判定2・3 を通過 → `time_entries` に `NaN` を INSERT → `chk_hours_positive` 通過 → コミット成功、画面には「保存しました ✓」。翌月、取引先別集計の SUM が全て NaN になる。
- **推奨対応**: (a) R-2 に「丸め結果が有限の数値でない場合」の判定を追加する、(b) R-3 を指数表記に依存しない実装で規定し直す、(c) 判定1 を安全域（`Math.abs(n) < 1e15` 等）に強化する、のいずれか。**PostgreSQL の numeric が NaN を受理し `NaN > 0` が真になる事実**も設計書に明記し、「DB 制約が最後の砦にならない」ことを前提として書くこと。`"0.0000001"` と `"12345678901234567890"` を AC に追加して境界を固定する。
- **仕様決定の要否**: 不要（レーンA）／要（レーンC）→ **司令塔の裁定: 不要**。丸めの実行系は設計者が決めてよい技術的選択（Round 1 F-007 の裁定と同じ扱い）。ただし決定内容は Phase 3 の承認対象に含める

#### F3-008: 成功保存の直後に失敗が起きると、キャンセルされていない `setTimeout` がエラーメッセージを消すため AC-61 の「自動的に消えない」が成立しない
- **観点 / レーン**: 状態管理の異常系（レーンC F3-C-006）
- **該当箇所**: 「UI の変更（エラー表示）」変更内容表／AC-61／E2E-4。実体は `apps/web/src/routes/index.tsx:48`（`savedMsg` state）、`:102-106`（`saveTemplate`）、`:108-121`（`saveReport`）
- **問題**: 現行実装は `savedMsg` という単一の state を `saveTemplate` と `saveReport`（さらに日付未入力パス）が共有し、いずれも `setTimeout(() => setSavedMsg(''), 2000)` を**タイマー ID を保持せずに**発火する。設計書は「失敗時は自動消去しない」とだけ規定し、**先行して発火済みのタイマーをキャンセルする規定を置いていない**。したがって、成功保存の 2 秒以内に次の保存が失敗した場合、先行タイマーが満了して `setSavedMsg('')` を実行し、表示したばかりのエラーメッセージが消える。「テンプレ保存 → 2 秒以内に日報保存が失敗」でも同じ。

- **仕様決定の要否**: 不要

#### F3-009: 並行系 AC（AC-45・AC-54・AC-55）が非決定的で違反実装を落とせず、「解決の順序固定」「テーブル間ロック順序」「分離レベル」「終端条件」には AC が 1 件もない
- **観点 / レーン**: 要件の網羅性・テストレベル判定の妥当性（レーンB F3-B-003 ＋ F3-B-013）
- **該当箇所**: 「解決の順序（デッドロック回避のため固定する）」／「解決の共通方針 > 分離レベル・終端条件」／「T-3」／AC-45・AC-54・AC-55／受け入れ条件冒頭の「Phase 5 のテスト観点はこの条件を唯一の根拠として起案される」
- **問題**: 追加された 3 つの並行系 AC はいずれも「特定の interleaving が起きたときにだけ違反が顕在化する」性質を期待値にしており、テストからその interleaving を強制する手段が設計書のどこにも規定されていない。AC-54（新規取引先 A・B を逆順に含む別日付の日報を同時保存 → デッドロックしない）は、順序を固定していない実装でも、2 つのトランザクションが実際に重なり双方が相手のマスタ挿入を未コミットで待つ瞬間が生じなければデッドロックしない。`Promise.all` では重なりを制御できず、順序を守らない実装が常に PASS しうる。AC-45・AC-55 も同様で、T-1 手順1 や T-2 手順1 を省いた実装が高確率で PASS する。さらに「テーブル間のロック順序を固定する」「マスタは名前の昇順に解決する（行ごとに逐次解決してはならない）」「分離レベルを変更してはならない」「再 SELECT が 0 件なら 1 回だけやり直す」の 4 規定には**対応する AC が 1 件も存在しない**（AC-01〜AC-61 を総当たりで確認）。
- **影響**: 行ごとに逐次解決する実装・テーブル順序を守らない実装・`db.transaction({ isolationLevel: 'repeatable read' })` を書いた実装・無限リトライ実装のいずれも、AC を全件 PASS したまま Phase 8・Phase 10 を通過する。実装承認ゲートがスキップされており Phase 10 の機械ゲートが最後の砦であるため、通過すると止める手段がない。現れる障害は (1) 本番でのみ間欠的に起きる `保存エラー: deadlock detected`、(2) REPEATABLE READ 環境での再 SELECT 空振りによる保存失敗、(3) 保存と削除が交差したときの孤児 `time_entries`。加えて非決定的な AC を結合(DB込み)テストとして凍結すること自体が CI に恒常的な flaky test を持ち込む。結合(DB込み)は人間本記載であり、人間が「どう書けば違反実装を落とせるか」の手掛かりを設計書から得られない。
- **失敗シナリオ**: `impl-builder` が対象行を走査しながら行ごとにマスタを解決する素直な実装（順序固定なし）を書く → AC-54 のテストは `Promise.all` で 2 件の保存を投げるが、実行時間の都合で 2 つのトランザクションが重ならず双方成功 → PASS → 運用開始 → 月初に別タブで 2 日分をまとめて保存した際にデッドロックし片方の日報が失われる。
- **推奨対応**: 非決定的な interleaving に依存しない、観測可能な事実に対する AC を追加する。①**順序の観測**：正規化後の名前が `"Z社"` → `"A社"` の順に並んだ日報を 1 回保存し、`clients` の作成順（`created_at` 昇順または挿入順）が名前の昇順と一致することを検証する AC。単一トランザクションで決定的に判定でき、行ごとの逐次解決実装を確実に落とす。②**テーブル順序の観測**：結合(内部・モック)で発行される文の順序が規定順であることを検証する AC。③**分離レベルの観測**：トランザクション内で `SHOW transaction_isolation` が `read committed` を返すことを検証する AC。④AC-45・AC-55 は、テスト側が別接続で対象日をロックしたうえで関数を呼び、ロック解放まで進行しないことを確認する形に期待値を書き換える。⑤終端条件（1 回だけ再試行）を検証する AC。あわせてこれらの検証手段を設計書側で規定し、人間本記載の記入例に含める。
- **仕様決定の要否**: 不要

#### F4-001: R-3 の「JS で丸めると 2.67 になる」は事実誤認であり、かつアプリ側丸め実装を落とす AC が 1 件も存在しない
- **観点 / レーン**: 仕様の曖昧性・受け入れ条件の検証可能性（レーンA F4-A-001）
- **該当箇所**: 「R-3: 実績h の格納と丸め」の「この方式を採る理由」第 1 項／AC-31・AC-32・AC-33・AC-35・AC-68・AC-03

#### F4-003: AC-62 は `created_at` が同一値になるため作成順を観測できず、行ごとの逐次解決実装を落とせない
- **観点 / レーン**: 受け入れ条件の検証可能性（**レーンA F4-A-003・レーンB F4-B-001・レーンC F4-C-004 の3レーンが独立に検出**）
- **該当箇所**: AC-62／「解決の順序（デッドロック回避のため固定する）」。実体は `apps/web/src/server/schema/master.ts:20-22`（`createdAt: timestamp(...).defaultNow()`）、`node_modules/drizzle-orm/pg-core/columns/date.common.js`（`defaultNow()` → `DEFAULT now()`）
- **問題**: `now()` は `transaction_timestamp()` の別名であり、**同一トランザクション内のすべての文で同一値**を返す。T-3 は全操作を 1 トランザクションで行うと規定しているため、1 回の保存で作成される `clients` 2 件の `created_at` は必ず同値になる。「`created_at` の昇順が名前の昇順と一致する」はキーが同値である以上、`ORDER BY created_at` の結果順が未定義（PostgreSQL はタイの順序を保証しない）であり判定が成立しない。代替の観測手段も無い（`id` は `defaultRandom()` の UUID v4、連番列なし）。**司令塔がスキーマ定義と Drizzle 実装を確認済み。**
- **影響**: AC-62 は F3-009 の推奨①（順序固定を守らない実装を確実に落とす）への唯一の対処として新設されたものであり、機能しないと「マスタは名前の昇順にまとめて解決する」規定に対応する AC がゼロに戻る。順序を守らない実装が全 AC を PASS して Phase 10 を通過し、異なる日付の同時保存で間欠的な `deadlock detected` を起こす。加えて、タイの解決順が物理順に依存するため**正しい実装でも flaky になる**。
- **推奨対応**: `created_at` に依存しない観測手段へ置き換える。(a) 結合(内部・モック)で `clients` に発行される INSERT/SELECT のキーの並びが正規化名の昇順であることを検証する（発行順の観測が直接の検証になる。文の本数で「まとめて解決」も判定できる）、(b) DB 込みなら `ctid` 昇順を AC で名指しする、(c) postgres-js の `debug` / Drizzle の `logger` で発行 SQL を記録する。「同一トランザクション内では `now()` が同値になるため `created_at` は順序の観測に使えない」ことを設計書に明記して再発を防ぐ。
- **仕様決定の要否**: 不要

#### F4-004: AC-63・AC-64 は観測点・到達手段がなく検証不能。AC-64 の状況は READ COMMITTED では原理的に発生しない
- **観点 / レーン**: 受け入れ条件の検証可能性（レーンA F4-A-004 ＋ レーンB F4-B-003 ＋ レーンC F4-C-011）
- **該当箇所**: AC-63・AC-64／「解決の共通方針 > 終端条件・分離レベル」／判定結果表。実体は `apps/web/src/server/db.ts:20-26`（`db` は `get` トラップが常に実体を返す Proxy）
- **問題**: (1) **AC-63 は実行主体が未定義**。テストは別接続からサーバー関数のトランザクションに文を差し込めない。実装が結果を返す／記録する規定もない。`db` は Proxy であり `vi.spyOn(db, 'transaction')` は無効化される。テスト自身の接続で `SHOW transaction_isolation` を実行しても**テストのセッションの既定値**を見るだけで、実装が `db.transaction({ isolationLevel: 'repeatable read' })` と書いた場合を落とせない — 本 AC が防ごうとした違反そのものをすり抜ける。(2) **AC-64 の状況は作れない**。READ COMMITTED では `INSERT ... #### F4-005: 「トランザクション外でロックを取る実装」「セッションレベルロックを使う実装」が並行系 AC を全件 PASS し、F3-004 の孤児経路がそのまま再発する
- **観点 / レーン**: 並行・ロックスコープ（レーンC F4-C-001）
- **該当箇所**: T-1 手順 1／T-2 手順 1／T-3／AC-45・AC-54・AC-55
- **問題**: AC-45 は「テストが別接続でロックを保持した状態で `saveReportFn` を呼ぶと、ロック解放まで完了しない」しか要求しておらず、**ロックがトランザクション内で取られたか否かを区別できない**。

- **推奨対応**: (a) ロックがトランザクション内で取られコミットまで保持されることを直接観測する AC を追加する（テストが別接続で `pg_try_advisory_lock` を試行し、`saveReportFn` の実行中に false が返ることを確認する等）。(b) 簡便な代替として「`saveReportFn` の完了直後に `pg_locks` の `locktype='advisory'` 行が当該キーに残っていないこと」を検証すればバリアント Y を確実に落とせる。(c) T-3 に「アドバイザリロックを含むすべての文をトランザクションハンドル経由で発行する」ことを明記し AC を紐づける。

#### F4-006: AC-45・AC-54 が要求する「別接続でのロック保持」は本リポジトリの接続機構では成立せず、正しい実装に対して偽陰性で FAIL する
- **観点 / レーン**: 並行・テスト構成の実現可能性（レーンC F4-C-002 ＋ レーンB F4-B-002）
- **該当箇所**: AC-45・AC-54／E2E 節「新しい接続機構を増やさない」。実体は `apps/web/src/test/db-helpers.ts`（`export const testDb = db` — 「テストからも本体と同じ接続を使う」と明記）、`apps/web/src/server/db.ts:10-14`（`max: 10`、postgres-js クライアントは非公開）、`node_modules/postgres/src/index.js:330-336`（`handler` が `open.shift()`）、`apps/web/vitest.integration.config.ts`（直列実行・`testTimeout: 20_000`）

#### F4-007: ロックキーが生入力文字列の `hashtext` であるため、同一日付を表す別書式の入力で直列化が黙って失われる（行ロック方式では起きなかった退行）
- **観点 / レーン**: 並行・境界値・入力検証の欠落（レーンC F4-C-003）
- **該当箇所**: T-1 手順 1・T-2 手順 1（`hashtext('daily_report:' || <対象日>)`）／R-7 の検証項目（`data.date` が文字列であることのみ）／T-2（入力検証の規定なし）／AC-55。実体は `apps/web/src/server/functions/reports.ts:105`（`deleteReportFn` の `inputValidator` は素通し）
- **問題**: ロックキーは**利用者から渡された文字列そのもの**のハッシュだが、実際に読み書きされる行は `date` 型カラムでの比較＝**パース後の日付**で特定される。PostgreSQL の `date` 入力は寛容で、`'2000-01-01'` / `'2000-1-1'` / `' 2000-01-01'` / `'01/01/2000'` / `'Jan 1, 2000'` はすべて同一の日付にパースされ**同一行**を指すが、`hashtext` の結果はすべて異なる。したがって「同じ日を対象とする T-1 と T-2」が**異なるロックキーで走り直列化がまったく効かない**。
  さらに `pg_advisory_xact_lock` は STRICT 関数であり、引数が NULL なら**関数は呼ばれず NULL を返す**（`'daily_report:' || NULL` も `hashtext(NULL)` も NULL）。`deleteReportFn({ date: null })` のような入力では**エラーにも例外にもならず、ロックを取らずに手順 2・3 へ進む**。
  R-7 の検証は `saveReportFn` にしかなく `date` は「文字列であること」だけで書式を検証しない。`deleteReportFn` には検証規定が一切なく、設計書自身が述べるとおり**この関数を呼ぶ UI は存在せずエンドポイント直叩きでのみ到達する**＝書式は完全に呼び出し元任せである。

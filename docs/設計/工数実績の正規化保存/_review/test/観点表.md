## 1. 結合(DB込み)向け 観点表（人間本記載方式）

### 該当トリガー（設計書「テストレベル判定」節より）

| 種別 | トリガー | 該当 |
|---|---|---|
| 影響度 | 不可逆操作 | **該当**（保存のたびに当該日付の `time_entries` を DELETE する） |
| 発生可能性 | DB 制約依存 | **該当**（ユニーク制約 S-1〜S-3・`NULLS NOT DISTINCT`・`numeric(4,2)` の丸め・`varchar(255)`） |

### 1.0 テストデータの分離（必須。Round 1 R1-C2 により新設）

**設計書の申し送り制約 #7 が「Phase 5 で決めること」と名指しした事項の決定である。**これが無いまま絶対件数で期待結果を書くと、正しい実装に対してテストが決定的に FAIL する（Round 1 でレーンC が実測：3-4 が「2 件」を期待する時点で `clients` 総数が 6 件になる）。

1. **マスタ名は観点番号を接頭辞に持つ一意な名前を使う。**書式は `IT<観点番号>-<名前>`（例：3-4 の取引先名は `IT34-A社`）。**接頭辞にハイフン以外の記号を使わない**（`LIKE` のワイルドカードと衝突するため）
2. **件数の主張は必ず接頭辞で絞った集合に対して行う。**`SELECT count(*) FROM clients` のようなテーブル全体に対する主張を書いてはならない。件数だけでなく **`name` の集合一致**まで判定する（件数一致だけでは名寄せ先を取り違える実装を見逃す）
3. **後始末は `afterEach` で、テストの成否によらず必ず実行する。**自分が使った日付の `time_entries` → `daily_reports` の順に削除し、続けて自分の接頭辞に一致するマスタを `tasks` → `projects` → `clients` の順に削除する。**`truncateTables()` は使わない**（`AGENTS.md`「DB込み結合テストの注意」）。E2E（2 章）はマスタを残す方針だが、**1 章はマスタも消す**（件数を主張するため）
4. **日付は 1 章内で一意に割り当てる。**割り当ては下表のとおり。表に無い観点は `2000-02-<観点番号の下2桁>` を使う

| 観点 | 使用する日付 |
|---|---|
| 1-3・1-4 | `2000-01-10`・`2000-01-11` |
| 1-1・1-2 | `2000-01-12`・`2000-01-13` |
| 1-5・1-6・1-10 | `2000-01-14`・`2000-01-15` |
| 1-7・1-8 | `2000-01-16`・`2000-01-17` |
| 3-1 | `2000-01-20`・`2000-01-21` |
| 4-2〜4-5・4-9 | `2000-01-30`〜`2000-01-31`・`2000-02-01`〜`2000-02-03` |

5. **「保存に成功する」は「throw しないこと」と読み替える。**Vitest からサーバー関数を直接呼ぶと戻り値は `undefined` になる（申し送り制約 #3。Round 1 でレーンC が実測確認）。成功の判定は戻り値ではなく「例外が投げられないこと」と「DB の状態」で行う

### 1.4 トランザクション

#### 並行性テストの土台（4-2〜4-5・4-9 の共通前提）

これらの観点は「テスト側が別接続でロックを保持したまま、サーバー関数を `await` せずに起動して待たされることを観測する」構成を共有する。**`testDb` をそのまま使うと成立しない。**

1. **専用クライアントを立てる**：`postgres(resolveDatabaseUrl(), { max: 1 })`。`testDb` は本体と同じ接続プールを共有しており（`export const testDb = db`）、**ロックを取っても後続の `db.transaction()` が同じ接続に割り当たると同一セッション内の再入で即座に成功する**（Round 1 でレーンC が実測：同一 pid に割り当たり 3ms で獲得）
2. **`{ max: 1 }` の専用クライアントでロックを保持したまま、同じクライアントから観測クエリ（`pg_locks` 等）を投げてはならない**（自己ブロックする）。観測にはもう 1 本別のクライアントを使う
3. **起動と同時に `.catch()` を装着する。**`const p = fn(...).then(r => ({ ok: r })).catch(e => ({ err: e }))` の形で**起動直後に**結果を包む。`Promise.allSettled` を後から生成すると、ハンドラ装着前に reject が確定して Node の unhandledRejection が発火し、**テストは PASS 表示のまま run 全体が exit code 1 で落ちる**（Round 1 でレーンC が実測）
4. **「待たされていること」の判定待ち時間 X は下限で規定する。**同一テスト内で**ロックを取らずに同じ保存を 1 回実行して計測した所要時間 T** の 10 倍以上、かつ**下限 300ms** とする。X が T より小さいと、ブロックしない違反実装でも「まだ解決していない」ため **false PASS** する（Round 1 R1-M14。当初の「解放操作より十分短く」は向きが逆だった）
5. **解放後の待ちに固定 sleep を使わない。**解放から待機側の獲得までは実測 1〜10ms であり、`await` で待てばよい
6. **解放は成否によらず `try/finally` / `afterEach` で行う。**ロック待ちは無期限であり、解放漏れがあると後続テストが `testTimeout: 20_000` まで固まる
7. **専用クライアントは `end()` で必ず閉じる**

## 2. E2E（クリティカルパス）シナリオ仕様（AI 起案 → Adversary レビュー → 人間が修正・承認して凍結）

該当トリガー：**クリティカルパス業務**

起案の根拠は承認済み設計書の「E2E シナリオの洗い出し > 自動化対象」節（E2E-1〜E2E-7）と受け入れ条件のみ。**コード化・実行は Phase 10**（本フェーズは仕様凍結まで）。

### 2.0 全シナリオ共通の前提

1. 各シナリオは保存前に**日付欄へ専用のセンチネル日付を入力する**（E2E-1 = `2000-01-01` … E2E-7 = `2000-01-07`）。**画面操作を伴うシナリオは、保存を成立させない意図であっても必ず入力する**
2. 各シナリオは他シナリオの実行結果・画面状態に依存しない（BrowserContext は独立し、初期状態は必ず `defaultDailyReport()`）
3. 後始末は `test.afterEach` で成否によらず実行し、自分のセンチネル日付の `time_entries` → `daily_reports` の順に削除する（**2 章はマスタを残す**。`truncateTables()` は使わない）
4. ログイン済みが既定。未認証を見るシナリオのみ個別に上書きする
5. **入力するマスタ名はシナリオごとに一意にする**（`E2E<番号>-取引先` 等）。マスタは後始末で残るため、シナリオ間で共有すると `fullyParallel: true` の下で 4-9 と同じマスタ作成競合が起きる
6. **タイマー起点の規定：**自動消去タイマーは `await reportStorage.save(data)` の**後**に張られる。したがって「◯秒後」の判定はすべて**クリック時刻ではなく `saved-msg` の表示を観測した時刻**を起点とする

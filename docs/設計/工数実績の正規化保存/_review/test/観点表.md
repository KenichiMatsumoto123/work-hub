## 0. この表の使い方（人間の記載者向け）

1章の表は、**観点列・該当トリガー列・関連 AC 列を AI が機械生成**し、**テストケース列・期待結果列・優先度列は各観点につき 1〜2 件だけ AI が記入例を埋めてあります**（`（AI記入例）` と付記）。残りの空欄（`＜人間が記入＞`）を埋めるのが Phase 5 の人間側の作業です。

意図的に不完全にしてあります。空欄を埋める行為そのものが「どこまで疑うか」の深さの判断になるためです（`flow-review-policy` 1.4）。

- 行を**追加**して構いません（観点が足りないと感じた場合）
- 「この観点は不要」と判断した場合は削除せず、**期待結果列に「対象外（理由）」**と書いてください（削除すると Adversary レビューで「網羅漏れ」として再指摘されます）
- テストケースは **Given / When / Then 形式**を推奨します
- 優先度は 高 / 中 / 低

2章（E2E）は AI が全件起案済みです。**内容を確認して修正・承認**してください。

## 2. E2E（クリティカルパス）シナリオ仕様（AI 起案 → 人間が修正・承認して凍結）

該当トリガー：**クリティカルパス業務**（日報保存は本アプリの主要導線であり、これが失敗すると利用者は日報を記録できない）

起案の根拠は承認済み設計書の「E2E シナリオの洗い出し > 自動化対象」節（E2E-1〜E2E-7）と受け入れ条件のみ。**コード化・実行は Phase 10**（本フェーズは仕様凍結まで）。

### 2.0 全シナリオ共通の前提（設計書「テストデータの分離（必須）」より）

1. 各シナリオは保存前に**日付欄へ専用のセンチネル日付を入力する**（E2E-1 = `2000-01-01` … E2E-7 = `2000-01-07`）。**画面操作を伴うシナリオは、保存を成立させない意図であっても必ず入力する**
2. 各シナリオは他シナリオの実行結果・画面状態に依存しない（BrowserContext は独立し、初期状態は必ず `defaultDailyReport()`）
3. 後始末は `test.afterEach` で成否によらず実行し、自分のセンチネル日付の `time_entries` → `daily_reports` の順に削除する（マスタは残す。`truncateTables()` は使わない）
4. ログイン済みが既定（`playwright.config.ts` の `storageState`）。未認証を見るシナリオのみ個別に上書きする

> **仮置きの説明（人間確認が必要）：** 現状のメッセージ要素は `<span className="text-xs text-success">{savedMsg}</span>` で、安定した識別子がありません。E2E-4 は「この要素が `text-danger` を持つこと」を判定する必要があるため、クラス名だけを頼りにすると「`text-danger` を持つ要素が存在すること」しか言えず、**メッセージ要素以外の `text-danger` を拾う**・**要素が消えたのに他要素で PASS する**といった誤判定が起こります。
>
> 本機能はこの `<span>` の表示色・改行・自動消去を変更する対象そのものなので、同じ要素に `data-testid="saved-msg"` を足すことは変更範囲の内側だと判断しました。ただし設計書は「UI の変更（エラー表示）」節でクラスと改行の 2 点しか規定しておらず、`data-testid` の追加は**設計書に根拠がない仮置き**です。承認いただければ設計書にも追記します。
>
> 代替案：`data-testid` を足さず、保存ボタンの近傍を構造で特定する（例：`getByRole('button', { name: /日報保存/ }).locator('xpath=preceding-sibling::span[1]')`）。壊れやすいため推奨しません。

### 1.0 テストデータの分離（必須）

**設計書の申し送り制約 #7 が「Phase 5 で決めること」と名指しした事項の決定である。**

1. **マスタ名は観点番号を接頭辞に持つ一意な名前を使う。**書式は **`IT<節番号2桁><観点番号2桁>-<名前>`**（例：観点 3-4 の取引先名は `IT0304-A社`、観点 5-10 は `IT0510-`）。**接頭辞にハイフン以外の記号を使わない**（`_` と `%` は `LIKE` のワイルドカードであるため使用禁止）
2. **件数の主張は必ず接頭辞で絞った集合に対して行う。**`SELECT count(*) FROM clients` のようなテーブル全体に対する主張を書いてはならない。件数だけでなく **名前列（`clients.name` / `projects.name` / `tasks.title`）の集合一致**まで判定する
3. **後始末は `afterEach` で、テストの成否によらず必ず実行する。**自分が使った日付の `time_entries` → `daily_reports` の順に削除し、続けてマスタを `tasks` → `projects` → `clients` の順に削除する（**この順序でなければ外部キー制約違反になる**。Round 2 でレーンC が逆順の失敗＝23503 を実測）。**`truncateTables()` は使わない**

   **マスタの削除は接頭辞一致だけでなく親子を辿る**（Round 4 R4-C1。接頭辞一致だけだと、接頭辞付きの親の下にぶら下がった非接頭辞の子が残り、削除が 2 段連続で 23503 になって後始末が中断する。中断するとマスタが残留して 2 周目以降も毎回 FAIL する）：
   - `tasks`：`title LIKE '<接頭辞>%' OR project_id IN (<接頭辞の projects>) OR client_id IN (<接頭辞の clients>)`
   - `projects`：`name LIKE '<接頭辞>%' OR client_id IN (<接頭辞の clients>)`
   - `clients`：`name LIKE '<接頭辞>%'`
4. **接頭辞を付けられない名前は「保存前に存在しなかった場合のみ削除する」。**5-4（タスク名が空 → `title` が `(名称未設定)`）と 5-6（オブジェクト → `"[object Object]"`、数値 → `String()` 化された数値文字列）は設計書が定めた固定値であり接頭辞を付けられない。**対象は `tasks.title` だけでなく `clients.name` / `projects.name` も含む**（Round 4 R4-C1・レーンC が `clients.name='[object Object]'` / `'123'` の恒久残留を実測）。規定 3 の親子辿りでも回収できない（親を持たないため）。したがって 3 テーブルすべてについて：
   - **保存前**に当該名の行が存在するかを調べて記録する
   - **存在しなかった場合のみ**、後始末でその行を削除する。存在した場合は**削除しない**（テストが作っていない行だからである）
   - **`time_entries` を巻き添えで削除しない。**Round 3 の実測では、単に id を採取して `DELETE FROM tasks` すると既存の実績から参照されて **23503 で `afterEach` が throw** し、それを避けるために `time_entries` も消すと**開発者の実データを破壊する**（CI は毎回まっさらなので通ってしまい、ローカルでのみ壊れる）
5. **日付は下表で全観点に一意に割り当てる。**フォールバック規則は用いない（Round 2 で「表に無い観点は `2000-02-<下2桁>`」という規則が `2000-02-32` 等の**存在しない日付**を生成し、15 観点が決定的に FAIL する Critical を作ったため廃止した）

7. **土台の待ち時間 T は捨て日付で 1 回だけ測り、全観点で共有する。**各観点の中で T を測ると、その計測パスの副作用が Given を壊す（4-9 は取引先がコミット済みになって観測用 INSERT が 23505 で落ち、4-3 は `daily_reports` 行が消え、4-4 は逆に行が作られる。Round 2 でレーンC が実測）。`beforeAll` で `2000-03-10` に対しロックを取らずに 1 回保存して所要時間を測り、**その日付のデータと計測が作ったマスタを削除してから**各テストへ進む。**計測用の日報は「マスタを 1 組（取引先・PJ・タスク）新規作成する対象行を 1 件だけ含む」ものとし、名前には専用接頭辞 `IT0000-` を用いる**（空の日報で測ると往復 3 回分＝実測 1ms となり、マスタ解決を含むパスの代表値にならない）。後始末は規定 3 と同じ順序（`time_entries` → `daily_reports` → `tasks` → `projects` → `clients`）で `IT0000-` を削除する（**`beforeAll` の書き込みは規定 1・3 の射程外であるため、ここで明示する**）
8. **テストが張った DDL は `beforeAll` の冒頭で冪等に撤去してから張り直す。**1-7 の一時 CHECK 制約は、プロセスが強制終了すると `afterAll` が走らず残留し、次回以降の実行で `42710` により当該ファイル全体が起動不能になる（Round 2 でレーンC が実測）。`DROP CONSTRAINT IF EXISTS` を `beforeAll` 冒頭と `afterAll` の両方に置く
9. **SQLSTATE は `(e.cause?.code ?? e.code)` で取得する。**Drizzle 経由の例外は `DrizzleQueryError` であり **`e.code` は `undefined`**、実値は `e.cause.code` に入る（Round 3 で実測。postgres-js を直接使った場合は逆に `e.code` に入る）。`e.code === '23505'` と書くと 2-1〜2-3 が**正しい実装でも必ず FAIL** し、`e.code !== '40P01'` と書くと**あらゆるエラーで真になりトートロジー**になる。**SQLSTATE は診断情報として扱い、主判定は「throw するか否か」「DB の状態」で行うこと**

### 1.4 トランザクション

#### 並行性テストの土台（4-2〜4-5・4-9 の共通前提）

1. **専用クライアントを立てる**：`postgres(resolveDatabaseUrl(), { max: 1 })`。`testDb` は本体と同じ接続プールを共有しており、ロックを取っても後続の `db.transaction()` が同じ接続に割り当たると**同一セッション内の再入で即座に成功する**（Round 1 で実測：同一 pid に割り当たり 3ms で獲得）
2. **ロック保持クライアントと観測クライアントを分ける。**`{ max: 1 }` のクライアントが `begin()` でトランザクションを開いたまま保持している場合、同じクライアントからの観測クエリは自己ブロックする（セッションレベル `pg_advisory_lock` の保持中は自己ブロックしないことを Round 2 で実測済みだが、用途を分けるほうが安全）
3. **起動と同時に `.catch()` を装着する。**`const p = fn(...).then(r => ({ ok: r })).catch(e => ({ err: e }))` の形で**起動直後に**包む。後付けにすると Node の unhandledRejection が発火し、**テストは PASS 表示のまま run 全体が exit code 1 で落ちる**（Round 1・2 で実測。起動時装着なら EXIT=0）
4. **「待たされていること」の判定待ち時間 X は下限で規定する。**`beforeAll` で捨て日付 `2000-03-10` に対しロックを取らずに 1 回保存して測った所要時間 T の **10 倍以上、かつ下限 300ms**。X が T より小さいと、ブロックしない違反実装でも「まだ解決していない」ため **false PASS** する。**T の計測は各観点の中で行わない**（計測パスの副作用が Given を壊す。1.0 節 規定 7）
5. **解放後の待ちに固定 sleep を使わない**（解放から獲得までは実測 1〜10ms）
6. **解放は成否によらず `try/finally` / `afterEach` で行う**（ロック待ちは無期限。解放漏れで後続テストが `testTimeout: 20_000` まで固まる）
7. **専用クライアントは `end()` で必ず閉じる**
8. **観測クライアントが開いた未コミットトランザクション（4-5③⑤・4-9）は `finally` で必ず `COMMIT` または `ROLLBACK` する**（放置すると idle-in-transaction セッションが残る）

## 2. E2E（クリティカルパス）シナリオ仕様（AI 起案 → Adversary レビュー → 人間が修正・承認して凍結）

### 2.0 全シナリオ共通の前提

1. 各シナリオは保存前に**日付欄へ専用のセンチネル日付を入力する**（E2E-1 = `2000-01-01` … E2E-7 = `2000-01-07`）。**画面操作を伴うシナリオは、保存を成立させない意図であっても必ず入力する**
2. 各シナリオは他シナリオの実行結果・画面状態に依存しない（BrowserContext は独立し、初期状態は必ず `defaultDailyReport()`）
3. 後始末は `test.afterEach` で成否によらず実行し、自分のセンチネル日付の `time_entries` → `daily_reports` の順に削除する（**2 章はマスタを残す**。`truncateTables()` は使わない）
4. ログイン済みが既定。未認証を見るシナリオのみ個別に上書きする
5. **入力するマスタ名はシナリオごとに一意にする**（`E2E<番号>-取引先` 等）。マスタは後始末で残るため、シナリオ間で共有すると `fullyParallel: true` の下で 4-9 と同じマスタ作成競合が起きる
6. **タイマー起点の規定：**自動消去タイマーは `await reportStorage.save(data)` の**後**に張られる。したがって「◯秒後」の判定はすべて**クリック時刻ではなく `saved-msg` の表示を観測した時刻**を起点とする

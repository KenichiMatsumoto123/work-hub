## Critical

### FIND-C01: 後始末が日付だけで `time_entries` / `daily_reports` を無条件 DELETE し、利用者の実データを破壊する

- **観点 / レーン**：⑤ セキュリティ・品質観点（MC-2・MC-3・MC-5）／レーンC
- **重大度**：**Critical**
- **ファイル**：`apps/web/src/test/report-db-helpers.ts:65-69`（`deleteByDates`）・`:104-107`（`cleanup`）／観点表 1.0 節 規定 3
- **問題**：`deleteByDates` は `WHERE date IN (...)` で削除するのみで、**接頭辞も「保存前に存在したか」も一切見ていない**。観点表 規定 4 の「保存前に存在しなかった場合のみ削除する」防御は `clients` / `projects` / `tasks` の 3 テーブルにしか実装されておらず、`time_entries` / `daily_reports` には適用されない
- **実測（レーンC）**：「利用者の開発 DB に既に `2000-01-01` の日報・実績がある」状況を模擬（接頭辞なしの 5 テーブル各 1 行）して結合テストを実行したところ、**`daily_reports` と `time_entries` の当該行が削除された**。マスタ側は接頭辞なしのため削除対象にもならず**孤児として残留**（部分破壊＋残骸化）
- **影響**：AGENTS.md「DB込み結合テストの注意（重要）」が明示的に禁じる「テストが作成していないデータの削除」に直接抵触する。`npm run test:integration` は CI 専用ではなく通常のローカル開発コマンドであり、CI は毎回まっさらなので**ローカルでのみ壊れる**。観点表 規定 4 自身が「`time_entries` も消すと開発者の実データを破壊する」と警告していた、まさにその形
- **司令塔による事実確認（レーンC の因果記述の訂正）**：レーンC は「今回の diff が新設した seed によって初めてこの経路が揃った」と記述したが、**これは正確ではない**。司令塔が実測で確認した：
  - `deleteByDates` の無条件 DELETE は `c6b0605` 時点で同一（`0d71b14` の `report-db-helpers.ts` への変更は `deleteReportRaw` の追加のみ）
  - `CLEANUP_DATES = [...ACCEPTED, '2000-01-01']` も `c6b0605` 時点で存在（Round 1 の Minor FIND-B04 が指摘済み）

  したがって **`0d71b14` が作った退行ではなく、Phase 5 のテスト作成時から潜在していた欠陥**である。Round 1 のレーンC が見逃したのは、pre-existing データの模擬に `2050-06-15`（後始末対象外の日付）だけを使い、**テスト自身が削除する日付での安全性を測らなかった**ため。新しい seed は欠陥を作ったのではなく可観測にした
- **影響範囲の実測（司令塔）**：後始末対象になる日付を全件洗い出したところ、**年 0004 / 0050 / 2000 / 2028 のみ**（`2026-13-01` 等の 2026 年の日付はすべて「拒否される入力」で DB に到達しない）。現実の日報データと衝突しうるのは実質 `2000-01-01` に集中するが、機構としては全日付が同じ構造
- **推奨対応**：`time_entries` / `daily_reports` にも規定 4 と同型の「保存前に存在しなかった場合のみ削除する」防御を入れる（対象日の既存行 ID をスナップショットし、差分のみ削除）。ヘルパー内で完結し、テストファイルの変更は不要。ただし**観点表 規定 3 が記述する後始末の方法そのものの変更**にあたるため人間判断が必要
- **戻り先**：**人間（Phase 7）へエスカレーション。**凍結済み成果物の変更を伴うため AI 判断でのループ継続は不可

  async function deleteReportFn({ data }) {
    const { date } = data

    await tx.delete(dailyReports).where(eq(dailyReports.date, normalized))
    if (!isCalendarDateValid(date)) {                 // 検証は DB 操作の後（規範違反）
      throw new Error('日報のデータ形式が不正です。')  // メッセージは正しい

## Round 1

- レビュー日：2026-08-15
- レーン：A（網羅性）／B（期待結果の厳密さ・設計書との整合）／C（実現可能性）
- 総合判定：**FAIL**（Critical 2・Major 17・Minor 25）

各レーンには、この観点表が**対話方式で確定した**（人間がファイルを直接編集できない環境のため、司令塔が案と論点を提示し人間が採否を決定した）ことを伝え、**司令塔の起案に人間の判断が引きずられた可能性を能動的に疑う**よう指示した。

### Critical

| ID | 見出し | 検出レーン |
|---|---|---|
| R1-C1 | 1-7・4-1（AC-39 原子性）を対象外とした根拠が**2 つとも事実誤認**であり、不可逆 DELETE のデータ損失経路が全面無検証になる | A |
| R1-C2 | 1 章に後始末・名前空間の規定が一切なく、絶対件数を主張する期待結果が**同一スイート内で決定的に破綻する** | C（A・B も Major として検出） |

**R1-C1 の詳細（司令塔の説明が誤っていた）**

対象外の根拠として司令塔が示した 2 点は、いずれも成立しない。

1. 「障害注入には実装構造の規定が必要（申し送り制約 #4）」→ **制約 #4 は AC-64（再 SELECT 0 件）についての記述**であり AC-39 のものではない。原子性の障害注入は、テストの `beforeAll` で一時的な CHECK 制約を張る（例 `CHECK (hours <> 13.13)`）だけで成立し、**実装側に何も要求しない**
2. 「壊しうる経路は T-3 と AC-72 がカバーする」→ **カバーしていない。**AC-72 が規定するのは**アドバイザリロックの取得文だけ**の所属である

結果、次の実装が観点表の全行を PASS する：

```
db.transaction(async (tx) => {
  await tx.execute(sql`SELECT pg_advisory_xact_lock(...)`)   // 4-2/4-3/4-5 PASS
  await tx.insert(dailyReports)...
  await db.delete(timeEntries).where(...)      // ← db を直接使用
  await db.insert(timeEntries).values(rows)    // ← db を直接使用
})
```

正常系では結果が同じため全観点を通過するが、E-5（接続断・デッドロック・一意制約競合）でトランザクションが失敗した瞬間、**`time_entries` の DELETE だけが確定し `daily_reports` はロールバックする**。本機能で唯一の不可逆操作が巻き戻らない。

**R1-C2 の詳細（実測）**

1 章の期待結果は絶対件数で書かれている（1-2「1 件のまま」、3-4「2 件のみ」、3-5「合計 3 件」等）が、1 章には後始末規定も名前空間規定も無い。`vitest.integration.config.ts` は `fileParallelism: false`（直列）であり、**直列だからこそ前のケースが作ったマスタが必ず残る**。名前も衝突する（2-1 と 3-4 が `"A社"`、3-3 と 3-6 が `"基幹刷新"`、2-3 と 3-6 が `"調査"`）。

レーンC がクリーンな `workhub_test` 上で 2-1 → 3-5 → E2E-1 → 3-4 の順に投入して実測：

```
3-4 が 2 件を期待する時点の clients 総数 = 6
3-5 が 3 件を期待する時点の clients 総数 = 6
```

CI は毎回まっさらだが**同一 run 内の累積だけで落ちる**。ローカルは開発用 DB に接続する運用のためさらに落ちる。設計書の申し送り制約 #7 が「Phase 5 で方針を決めること」と名指しした事項が未決のまま凍結されようとしていた（MC-4）。

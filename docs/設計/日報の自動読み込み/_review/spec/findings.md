### Major

#### F-001: 日付変更手順の `false なら return` がフロー図と矛盾
- **観点 / レーン**: 仕様の曖昧性（レーンA）／元 F-A-001
- **該当箇所**: 「日付変更」節、業務フロー「正常系：日付変更」
- **問題**: 「isReportDirty が true なら confirm、false なら return」と読める。フロー図は dirty でないとき読み込みへ進む。confirm キャンセルと dirty=false が同じ return に見える。
- **影響**: dirty=false で日付変更が動かない実装が、一部 AC だけ通る。
- **推奨対応**: 「dirty なら confirm。キャンセルなら return。dirty でない、または OK なら startLoad」とフロー図に揃える。
- **仕様決定の要否**: 不要

#### F-002: 「フォーム全体が一致」の比較単位が未定義
- **観点 / レーン**: 仕様の曖昧性 / 受け入れ条件の検証可能性（レーンA）／元 F-A-002
- **該当箇所**: 目的、AC-L31/L33、E2E-L1
- **問題**: 比較対象（raw_data 直比較 vs rowToReport）、配列順、id、欠損フィールド、画面未表示フィールドが未定義。E2E-L1 は取引先名などの部分観測。
- **影響**: id 差し替え・順序変更・一部欠損でも E2E と一部 AC が通る。
- **推奨対応**: UI/結合の「一致」を `isReportDirty` と同型のフィールド集合（id 除外）で固定する。
- **仕様決定の要否**: 要

#### F-003: `applyLoadSuccess` が非 null 時に要求日付を強制しない
- **観点 / レーン**: 仕様の曖昧性（レーンA）／元 F-A-003
- **該当箇所**: `applyLoadSuccess`、AC-L33
- **問題**: 非 null では `report` をそのまま返す。`rowToReport` は `raw_data` をキャストするだけで列 `date` との一致を保証しない。
- **影響**: `raw_data.date` と要求日付が食い違う行で、日付欄が D にならない実装が仕様上合法。
- **推奨対応**: 成功時は常に `{ ...report, date }` とするか、不一致をエラー/null にする。
- **仕様決定の要否**: 要

#### F-007: 画面オープン直後の保存済み読み込みにクリティカルパス E2E がない
- **観点 / レーン**: 受け入れ条件の検証可能性（レーンA）＋ 要件の網羅性（レーンB）／元 F-A-007、F-B-001
- **該当箇所**: AC-L31/L32、E2E-L1〜L6、要件メモ UC#1・種1
- **問題**: 主ユースケース「`/` を開いたとき今日の保存済みを載せる」が E2E に無い。E2E-L1 は日付変更後、E2E-L3 は日付欄が今日であることのみ。

- **推奨対応**: 今日（または固定した今日相当日）に DB 行を投入して `/` を開き、保存済みが載る E2E を追加する。隔離手順も規定する。
- **仕様決定の要否**: 要

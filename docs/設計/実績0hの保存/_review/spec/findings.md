#### F-001: AC-Z01 が 0 表記 3 種を OR にして必須検証にならない
- **観点 / レーン**: 受け入れ条件の検証可能性（レーンA）
- **該当箇所**: 受け入れ条件「0h の記録」AC-Z01
- **問題**: AC-Z01 の本文は `"0"` / `"0.0"` / `"0h"` の**いずれか** 1 件だけであり、3 表記のうち 1 つを試せば AC は充足する。目的と分類表は 3 表記すべてを `0.00` 記録としているが、Phase 5 の根拠は AC である。
- **影響**: `"0"` だけを書いて `"0.0"` / `"0h"` を書かないテストセットが AC 上合法になる。`parseFloat("0h") === 0` に依存する経路が未検証で残る。
- **推奨対応**: AC-Z01 を 3 表記それぞれ必須にする。
- **仕様決定の要否**: 不要

#### F-002: AC-Z10 が参照だけで、期待するマスタ行を機械判定できない
- **観点 / レーン**: 受け入れ条件の検証可能性（レーンA）
- **該当箇所**: 受け入れ条件「マスタ・再保存・検証」AC-Z10
- **問題**: 期待結果が「親 R-4 と同じ規則」「そのタスクを指す」だけである。`type` / `title` / 解決キーの具体値が無く、`task_id IS NOT NULL` でも文言上充足する。
- **影響**: 0h 専用に常に `adhoc` にする等の R-4 逸脱を、この AC は落とさない。
- **推奨対応**: 親 AC-26 型で具体化する。adhoc 3 分岐は親 AC-23〜25 を新しい「有効な行」定義で継承すると明示する。
- **仕様決定の要否**: 不要（要件メモ決定#6「`h > 0` と同じ規則」と親 R-4 で足りる。司令塔判断）

#### F-003: 「負数は DB でも拒否」と `numeric(4,2)` + `hours >= 0` が矛盾する
- **観点 / レーン**: 仕様の曖昧性 / MC-4（レーンA）＋ エッジケース（レーンC）。F-A-003 と F-C-001 を統合
- **該当箇所**: S-Z1、例外系旧注記、既存 check 制約との整合、AC-Z18
- **問題**: PostgreSQL は CHECK を列型キャスト後に評価する。`'-0.004'` 直 INSERT は格納値が `0.00` になり `>= 0` を満たす。旧 `hours > 0` では同じ入力は落ちていた。S-Z1 と例外系は「負数は DB でも拒否」と書く。AC-Z18 が固定しているのは `hours = -0.01` だけ。
- **影響**: 実装者は (a) `>= 0` だけ置く（丸め後ゼロの負数は通る）(b) 散文に合わせてより狭い CHECK を足す、のどちらでも設計準拠を主張できる。判定 2 が甘いと負の微小入力が 0h として静かに残る。
- **推奨対応**: CHECK の意味を「**キャスト後の格納値が非負**」に限定する。丸め後 `0.00` になる負の直 INSERT は許可されると書く。アプリ経路の `"-0.004"` は判定 2 だけでスキップすると AC に落とす。
- **仕様決定の要否**: 不要（R-2 の `value < 0` は既定。直すのは防波堤の事実関係と AC。司令塔判断）

#### F-004: 要件メモ AC種9（表示側不変）が AC にも画面シナリオにも落ちていない
- **観点 / レーン**: 要件の網羅性（レーンB）
- **該当箇所**: 受け入れ条件／対象外の機能・要件／E2E 候補カタログ／Phase 5 申し送り
- **問題**: 要件メモは「日報テキスト・月次表・`getProjectSummary` は変更しない」を AC 種として挙げている。設計書は非ゴールと「画面テストを書かない」に変換しただけで、AC-Z も画面シナリオも無い。
- **影響**: 実装者が `getProjectSummary` の `> 0` を `>= 0` に変えても AC-Z01–Z19 では検出できない。
- **推奨対応**: 「AC 化しない。表示側の不変は非ゴールのみ。Phase 5 は表示モジュールのテストを書かない」と明示し、候補カタログに残す。
- **仕様決定の要否**: 不要（決定#4「保存だけ」で足りる）

#### F-005: クリティカルパス「該当」と E2E「必須」が矛盾している
- **観点 / レーン**: 設計書フォーマット準拠（レーンB）
- **該当箇所**: 影響度トリガー クリティカルパス行／判定結果 E2E 行／自動化対象
- **問題**: トリガー表はクリティカルパス該当なら E2E 必須。`_flow-config.md` は起案→凍結と書く。設計書は「該当」のまま判定結果を「既存分の維持のみ」にし、C-Z1 をカタログに落としている。
- **影響**: Phase 5 が設計書に従うと flow-config の起案を飛ばし、flow-config に従うと「新規なし」と衝突する。親 E2E の退行確認自体を省略する読みも成立する。
- **推奨対応**: 判定結果を「E2E **必須**（親 E2E-1〜7 を維持。本差分の新規起案なし）」と書き、flow-config の起案手順を本差分では適用しないと明記する。
- **仕様決定の要否**: 不要（画面非変更・0.00 は画面から観測不能、という既存決定の文書整合。司令塔判断）

#### F-006: 判定下限の変更と制約差し替えの適用順が未規定
- **観点 / レーン**: エッジケース（レーンC）
- **該当箇所**: マイグレーション手順、影響を受ける実装
- **問題**: 0.00 書き込みは判定変更と制約差し替えの両方が揃って初めて成立する。手順はスキーマの DROP/ADD だけを列挙し、判定変更との前後が無い。コード先行だと旧 CHECK が 0.00 を拒否し、保存全体が失敗する（親 F-001 と同型）。
- **影響**: `db:push` 前の環境で 0 を入れた日報が保存不能になる。同一 TX の他行も巻き戻る。
- **推奨対応**: 制約の `db:push` を判定下限の変更より前（少なくとも同環境で制約が有効な状態）に行うと書く。
- **仕様決定の要否**: 不要

# 開発フロー レビュー方針（flow-review-policy）

10フェーズフローにおける **レビューの回し方** の正本。各レビューフェーズ（Phase 2 / 6 / 10）と、人間レビューの ON/OFF に関わるフェーズ（Phase 5 / 7 / 8 / 10）から参照される部品。

本書が定義するのは次の4点：

1. **フロー設定（flow-config）** — 機能ごとに人間レビュー（承認ゲート）の実施要否を先に決めて記録する
2. **較正不変の原則** — レビュー時間を短縮するときに「何を削ってよく、何を削ってはいけないか」
3. **観点レーン分割と並列起動** — 時間短縮の主手段
4. **収束ループ** — Critical / Major がゼロになるまでレビュー→修正→再レビューを繰り返す手順

## 1. フロー設定（flow-config）

### 1.1 位置づけ

**機能ごとに、開発を始める最初の時点で人間レビューの実施要否を決めて記録する。**フェーズの途中で「今回は人間レビューをどうしますか」と都度尋ねるのではなく、`flow-kickoff`（または Phase 1 直行時は Phase 1）で一度決め、以後すべてのフェーズがこの設定を読んで挙動を変える。

- **保存先**：`docs/設計/<機能名>/_flow-config.md`
- **作成**：`flow-kickoff` Step 2.5（Phase 1 直行時は `flow-phase1-design-doc` Step 1.5 でフォールバック作成）
- **参照**：Phase 1 / 5 / 6 / 7 / 8 / 10 の各 skill が起動時に必ず読む。存在しない場合は作成してから先へ進む
- **変更**：途中で変更してよい。変更時は「更新履歴」に理由とともに追記する

### 1.2 選べるゲートと選べないゲート

| ゲート | 対象 | 設定 |
|---|---|---|
| 設計書承認（Phase 3） | 設計書 + Phase 2 findings | **実施固定（スキップ不可）** |
| テスト承認（Phase 7） | テスト + Phase 6 findings | 実施 / スキップ |
| 実装承認（Phase 10 完了時） | 実行検証証拠 + Phase 10 findings | 実施 / スキップ |

**Phase 3 をスキップ不可とする理由：** 設計書は要件の写像であり、「何を作るか」の判断は人間にしか帰属しない。ここを AI に閉じさせると、以降のフェーズがどれだけ厳密でも「正しく作られた誤ったもの」に収束する。Phase 7 / 10 は「作られたものが設計書に対して正しいか」の検証であり、判定基準（設計書）がすでに人間承認済みのため、AI による検証で代替しうる。

### 1.3 人間レビューをスキップした場合の代償措置（必須）

スキップは「レビューを省く」ことではなく「**人間の判断を AI の検証で置き換える**」ことである。以下は設定に関わらず必ず適用する。

| スキップしたゲート | 代償措置 |
|---|---|
| Phase 7（テスト承認） | ① Phase 5 のテスト観点は AI が全件起案する（後述 1.4）。② 起案した観点表を Adversary が敵対的レビューし、Critical/Major ゼロまで収束させてから凍結する。③ Phase 6 の収束ループで **Major の「文書化のみで通過」は使えない**（Critical/Major の完全ゼロ化が必須）。④ 設計書に根拠がない仮置きが1件でもあれば、そこだけは人間に確認する（設計書の不備であり、テストの問題ではないため） |
| Phase 10 完了時（実装承認） | ① Phase 10 の収束ループで **Major の「文書化のみで通過」は使えない**。② 実行検証（全テスト・E2E・lint・型・build）は1項目も省略できない。③ フィードバックルーティングで戻り先が Phase 1 / 5 になる findings（仕様の曖昧さ・テストの不備）が出た場合は、スキップ設定にかかわらず人間へエスカレーションする（設計書・テストの変更は人間承認済み成果物の変更にあたるため） |

### 1.4 テスト観点の確定方式

Phase 5 の「テスト仕様確定フロー」（影響度トリガー該当分）の記載方式は、Phase 7 の設定に連動する：

| Phase 7 の設定 | 結合(DB込み)の観点表 | クリティカルパスE2E のシナリオ仕様 |
|---|---|---|
| 実施 | **人間本記載方式**（AI は各観点1〜2件の記入例のみ。残りは人間が記載） | **AI起案 → Adversary レビュー → 人間が修正・承認して凍結** |
| スキップ | **AI起案方式**（AI が全件起案。1.5 のチェックリストを足場にする） | **AI起案 → Adversary レビュー → Critical/Major ゼロで凍結** |

### 1.5 AI がテスト観点を起案するときのチェックリスト（人間の「深さ」を代替する足場）

人間本記載方式が担保していたのは「網羅表を埋める行為そのものが深さの判断になる」という性質である。AI 起案でこれを代替するため、**該当トリガーごとに以下の観点を最低限すべて起案する**（該当なしと判断した場合は「該当なし」の理由を観点表に明記する。無言の省略は不可）。

| 該当トリガー | 起案必須の観点 |
|---|---|
| 認可境界 | 他社／他ユーザーのデータ混在時の除外・未認証（null / undefined / 壊れたセッション）・権限の異なるロールでの実行・ID 直接指定（IDOR）・where 句の絞り込み漏れ |
| PII 取扱い | 型レベルでの除外・モック汚染（意図的に PII を混入させて除外を確認）・JSON シリアライズ結果の値検証・ログ出力への混入・エラーレスポンスへの混入 |
| 認証セッション | 有効期限切れ・改ざんされたトークン・ログアウト後の再利用・同時ログイン・セッション固定 |
| 不可逆操作 | 二重実行（冪等性）・部分失敗時のロールバック・確認ステップの回避・削除済みデータへの再操作 |
| 金銭契約 | 端数・丸め・通貨単位・0 および負数・上限値・二重課金の防止 |
| クリティカルパス業務 | 正常系の完走・主要な異常系（入力不正・権限なし・対象なし）・中断／再開・前提データがない状態 |
| DB制約依存 | ユニーク制約違反・外部キー制約違反・NOT NULL 違反時のレスポンス変換 |
| 実JOINクエリ | 論理削除済みリレーション・リレーション先が 0 件・N+1 の発生有無 |
| トランザクション | 途中失敗時の原子性・並行実行時の競合 |
| 複雑な状態遷移 | 定義された全遷移・未定義の遷移要求の拒否・境界となる状態での操作 |

さらに、トリガーによらず共通で起案する：**境界値（0件・1件・上限件数）／null・undefined・空文字／不正な型・想定外の enum 値のフォールバック**。

### 1.6 flow-config の様式

```markdown
# <機能名> フロー設定

- 作成日: YYYY-MM-DD
- 対象機能: <機能名>

## 人間レビュー（承認ゲート）

| ゲート | 対象フェーズ | 設定 |
|---|---|---|
| 設計書承認 | Phase 3 | 実施（固定） |
| テスト承認 | Phase 7 | 実施 / スキップ |
| 実装承認 | Phase 10 完了時 | 実施 / スキップ |

## テスト観点の確定方式（Phase 5・影響度トリガー該当分）

- 結合(DB込み): 人間本記載 / AI起案（Phase 7 の設定に連動）
- クリティカルパスE2E: AI起案 → Adversary レビュー → 人間承認 / Adversary レビューで収束後に凍結

## レビュー設定

- 較正: 敵対的（固定・変更不可）
- 観点レーン並列: 有効 / 無効（サブエージェントの並列起動ができない環境のみ無効）
- 収束ループ上限: 5 周（既定）
- 運用モード: 厳格 / lean

## 更新履歴

| 日付 | 変更内容 | 理由 |
|---|---|---|
| YYYY-MM-DD | 初版作成 | — |
```

## 2. 較正不変の原則（レビュー時間短縮の鉄則）

### 2.1 原則

> **レビュー時間の短縮は「較正（欠陥を能動的に探す姿勢と探索の深さ）」を下げて行ってはならない。短縮は「探索の分割（並列化）」「報告の閾値」「出力の粒度」「再走査の範囲（差分化）」の4つで行う。**

**この原則が置かれた経緯（2026-08-12 追加）：** 敵対的レビューの所要時間を削るために「批判的」という観点自体を外した通常較正レビューへ置き換えたところ、不具合の見落としが発生した（実走で確認済み）。原因は、**「探索の深さ」と「報告の閾値」という別の2軸を、まとめて下げてしまった**ことにある。報告を Critical / Major に絞ること（ノイズ削減）は正しかったが、それに引きずられて探索そのものを浅くしたため、Critical 級の欠陥が探索段階で発見されなくなった。

したがって、以後すべてのレビューで次のように分離して扱う：

| 軸 | 設定 | 調整可否 |
|---|---|---|
| **探索の較正**（どれだけ疑って読むか） | 敵対的（欠陥を能動的に探し、反証を試みる） | **調整不可。常に最大** |
| **報告の閾値**（何を findings に載せるか） | フェーズごとに規定（Phase 2/6 は Critical/Major/Minor、Phase 10 は Critical/Major のみ） | フェーズ規定に従う |
| **探索の分割**（何人で分担するか） | 観点レーンごとに並列起動 | 環境に応じて調整可 |
| **出力の粒度**（1件あたり何を書くか） | 出力予算（2.3）に従う | 調整可 |
| **再走査の範囲**（2周目以降どこを見るか） | 差分レビュー（4.4） | 調整可 |

### 2.2 削ってよいもの・削ってはいけないもの

**削ってよい（時間短縮の対象）：**

- 1エージェントが全観点を直列に読むこと → レーン分割で並列化する
- Minor findings の詳細記述 → 見出し＋該当箇所の1行に圧縮する
- PASS 観点の肯定的証拠の冗長な列挙 → 検証した具体箇所を1〜2行に圧縮する
- 2周目以降の全体再走査 → 差分レビューに限定する
- 同じ指摘の言い換えによる件数の水増し → 統合する

**削ってはいけない（品質の床）：**

- 「欠陥を能動的に探す」姿勢そのもの（肯定的要約の禁止・反証としての読み）
- 後述 2.4 の **must-catch チェック**（毎周・全プロファイルで必須）
- 証拠（ファイルパス・行番号／該当節）の明記
- 観点ごとの PASS / FAIL のバイナリ判定

### 2.3 出力予算

| severity | 記述量 |
|---|---|
| Critical | フル記述（該当箇所・問題・影響・失敗シナリオ・推奨対応） |
| Major | フル記述（同上） |
| Minor | **1行**（`FIND-XXX: <見出し>（<ファイル:行>）` のみ。影響・推奨対応は省略） |
| PASS 観点の裏付け | 観点ごとに1〜2行（検証した具体箇所） |

### 2.4 must-catch チェック（見落とし防止の床）

過去の実走で実際に見落とし・素通しが起きた項目。**レーン分割・差分レビュー・時間短縮のいずれを適用しても、毎回必ず確認する。**該当レーンの担当エージェントに明示的に指示する。

| # | 項目 | 主に見るフェーズ |
|---|---|---|
| MC-1 | トートロジーテスト（モックが返す値をそのまま assert していないか） | Phase 6 |
| MC-2 | PII 除外の3層検証（型・モック汚染・シリアライズ値） | Phase 6 / 10 |
| MC-3 | 認可境界の2層検証（where 引数の assert ＋ 他社データ混在モック） | Phase 6 / 10 |
| MC-4 | 未決事項を温存したまま書かれたテスト・実装 | Phase 2 / 6 |
| MC-5 | Red Phase 証拠の妥当性（期待値不一致で個別 FAIL しているか。スタブに実ロジックが混入していないか） | Phase 6 |
| MC-6 | 受け入れ条件 × テストの対応マトリクスに ❌ / ⚠️ が残っていないか | Phase 6 |
| MC-7 | **テストが検証していない経路の欠陥**（テスト全件 PASS でもすり抜ける分岐・エラー経路・状態遷移・並行/競合・例外時の副作用） | Phase 10 |
| MC-8 | 実装の仕様乖離（設計書にない挙動の追加・暗黙のスコープ拡大） | Phase 10 |
| MC-9 | 既存規約との整合（ラッパー・認証ヘルパー・エラーレスポンス形式） | Phase 6 / 10 |

## 3. 観点レーン分割と並列起動

### 3.1 手順

1. 司令塔がレビュー観点を**レーン**（担当グループ）に分ける（既定のレーン割りは 3.2）
2. レーンごとに**別々の fresh context サブエージェント**を起動する。**同一メッセージ内でまとめて起動し、並列に走らせる**
3. 各エージェントには「担当レーンの観点のみを、敵対的較正で深く見る」ことと、**担当レーンに関係する must-catch 項目**を明示する
4. 各エージェントの findings（応答テキスト）を司令塔が受け取り、マージする（3.3）
5. マージ結果を `findings.md` に Write する

**並列起動できない環境の場合：** `flow-config` の「観点レーン並列」を無効にし、1エージェントに全観点を渡して直列でレビューする。この場合も較正・must-catch は一切下げない（所要時間が延びることを受け入れる）。

### 3.2 既定のレーン割り

**Phase 2（設計書・3レーン）**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: 仕様の確からしさ | 仕様の曖昧性／受け入れ条件の検証可能性 | MC-4 |
| B: 網羅とスコープ | 要件の網羅性／非ゴールの明確性／設計書フォーマット準拠 | — |
| C: 異常系 | エッジケース（例外系・境界値・異常系・空状態・権限・並行） | — |

**Phase 6（テスト・3レーン）**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: テスト自体の欺瞞性 | トートロジー検出／実装詳細の過剰束縛 | MC-1 |
| B: 仕様との対応 | 受け入れ条件との対応（マトリクス作成）／エッジケース・例外系の網羅 | MC-4・MC-6 |
| C: セキュリティと証拠 | セキュリティ・品質観点（PII・認可・N+1・既存規約整合）／Red Phase log の妥当性 | MC-2・MC-3・MC-5・MC-9 |

**Phase 10（実装・3レーン）**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: 仕様忠実性 | 実装と設計書の受け入れ条件の突き合わせ／設計書にない挙動 | MC-8 |
| B: セキュリティ | 認可境界・PII 露出・インジェクション・N+1 | MC-2・MC-3 |
| C: テストのすり抜け | テストが検証していない分岐・エラー経路・状態遷移・並行/競合・例外時の副作用・リソース解放 | MC-7・MC-9 |

Phase 10 のレーン C は、**実行検証（全テスト PASS）をすり抜ける欠陥**を探すための専用レーンである。「テストが通っている」ことを根拠に安心してはならない。

### 3.3 findings のマージ規則（司令塔の責務）

- **重複の統合**：複数レーンが同じ箇所を指摘した場合は1件に統合し、観点欄に両方を併記する。件数の水増しをしない
- **severity の裁定**：レーン間で severity が食い違う場合は**高い方を採る**（見落としのコストが過大評価のコストを上回るため）
- **矛盾の明示**：レーン間で判定が矛盾する場合（一方が PASS・他方が FAIL）は、統合せずに両論を findings に残し、司令塔の判断と根拠を併記する
- **改竄の禁止**：司令塔は各エージェントの指摘内容を要約・軟化・削除してはならない。統合と体裁の整理のみ許される

## 4. 収束ループ（Critical / Major ゼロまで繰り返す）

### 4.1 基本形

各レビューフェーズは**1回のレビューで終了しない**。次のループを、収束条件を満たすまで回す：

```
Round 1: フルレビュー（レーン並列）
   ↓ Critical / Major あり
修正（担当は下表）
   ↓
Round 2: 差分レビュー（前回 findings の解消確認 ＋ 修正差分の新規欠陥 ＋ must-catch）
   ↓ Critical / Major あり
修正 → Round 3 → …（最大 5 周）
   ↓ Critical 0 かつ Major 0
収束 → 人間ゲート（実施設定時）または次フェーズへ
```

| フェーズ | 修正の担当 |
|---|---|
| Phase 2（設計書） | 司令塔（メイン会話）。ただし 4.3 の制限あり |
| Phase 6（テスト） | `test-builder` を fresh context で再起動（司令塔がテストを直接書かない） |
| Phase 10（実装） | `impl-builder` を fresh context で再起動（司令塔が実装を直接書かない。テストは誰も変更しない） |

### 4.2 収束条件

- **Critical: 0 件 かつ Major: 0 件**
- Minor は収束の条件に含めない（`findings.md` に1行で記録して通過してよい）
- **例外（lean 運用かつ該当ゲートが「実施」の場合のみ）**：人間が明示的に「対応方針を文書化して通過」と判断した Major は、`findings.md` に「deferred: 理由・対応時期」を記録したうえで収束扱いにしてよい。**人間ゲートをスキップした機能ではこの例外は使えない**（AI が自分の判断で Major を deferred にすることは禁止）

### 4.3 ループを抜けて人間へ即エスカレーションする条件

以下に該当する finding は、周回の途中であっても**その時点でループを止め、人間に判断を仰ぐ**：

1. **仕様判断が必要**：設計書に根拠がなく、解消には「何を作るか」の新しい決定が要るもの（AI が仕様を発明して閉じるのを防ぐ）
2. **承認済み成果物の変更が必要**：Phase 6 のループ中に設計書の修正が必要と判明した場合（Phase 1/3 へ差し戻し）、Phase 10 のループ中にテストの修正が必要と判明した場合（Phase 5/7 へ差し戻し）
3. **スコープの拡大**：解消すると当初スコープを超えるもの
4. **振動の検知**：同一 finding が2周連続で解消されない／修正のたびに新規 Critical が発生する
5. **周回上限の到達**：5 周（既定）を終えても収束しない

エスカレーション時は、残っている findings・各周で試みた修正・司令塔の見立て（原因の仮説と対応案）をまとめて提示する。

### 4.4 差分レビュー（2周目以降）

Round 2 以降のレビューは、次に限定する（フル再走査をやり直して新規の指摘を積み増さない）：

1. 前回 findings の**解消確認**（1件ずつ「解消 / 未解消 / 部分的」を判定）
2. **修正差分**に含まれる新規欠陥
3. **must-catch チェック**（毎周必須。差分に関係なく確認する）

**例外：** 修正が成果物の広範囲に波及した場合（設計方針の変更・テスト構成の全面見直し等）は、司令塔の判断でフルレビューに戻してよい。その旨を `review-log.md` に記録する。

## 5. 禁止事項

- 較正（敵対的な探索の深さ）を下げることで所要時間を短縮しない
- must-catch チェックを、時間短縮・差分レビュー・レーン分割のいずれを理由にしても省略しない
- 司令塔がレビュワーの指摘を要約・軟化・削除しない（統合と体裁整理のみ）
- 人間ゲートをスキップした機能で、AI の判断により Major を deferred（文書化のみ通過）にしない
- 仕様判断が必要な finding を、AI が仕様を推測して閉じない（即エスカレーション）
- 収束ループを1周で打ち切らない（Critical/Major が残っている状態で次フェーズへ進めない）
- `_flow-config.md` を読まずにフェーズを開始しない

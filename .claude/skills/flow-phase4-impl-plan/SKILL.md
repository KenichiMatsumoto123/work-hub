# Phase 4: 実装計画書作成

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 4** を担当するスキル。Phase 3 で承認された設計書をもとに、10フェーズフローの各フェーズに対応するタスクを WBS 形式で整理した実装計画書を作成する。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 10フェーズフローの正典。実装計画書の章立てはこのフローに沿う
2. 対象機能の設計書（Phase 1 で作成・Phase 3 で承認済み）
3. 設計書 敵対的レビューの findings（`_review/spec/findings.md`）— レビュー結果をタスクに反映する
4. `docs/設計/共通機能設計書.md` — 共通仕様（存在する場合のみ）
5. `docs/開発プロセス/ブランチ運用方針.md` — 実装スコープの分割基準（大規模機能の場合）
6. 既存実装計画書サンプル — 参考フォーマットとして（対象リポジトリに過去の実装計画書があれば）

## 重要な前提（必ず守ること）

1. **Phase 3 承認後に着手する**
   - 設計書のステータスが「合意済」になっていることを確認する
   - 未承認の場合は、設計書の承認状態をユーザーに確認してから進める

2. **章立ては10フェーズフローに対応させる**
   - Phase 0（前提タスク・依存）
   - Phase 1（設計書作成）— 既に完了している前提
   - Phase 2（設計書 敵対的レビュー）— 既に完了している前提
   - Phase 4（実装計画書作成）— 本skill 自身
   - Phase 5（テスト作成・Red Phase）
   - Phase 6（テスト 敵対的レビュー）
   - Phase 7（人間レビュー：テスト承認）※`_flow-config.md` で「スキップ」の場合はその旨を明記
   - Phase 8（実装・Green Phase）
   - Phase 9（リファクタ）
   - Phase 10（実装検証：テスト・E2E 実行＋実装レビュー）
   - 実装承認ゲート ※`_flow-config.md` で「スキップ」の場合はその旨を明記
   - フィードバックルーティング（未収束・エスカレーション時）
   - 完了条件
   - 補足：テスト方針論点
   - 将来拡張

3. **各フェーズに「ゲート条件」を明記する**
   - Phase 5 → Red Phase 証拠（new-feature-tests: FAIL / regression-baseline: PASS）
   - Phase 8 → Green Phase 証拠（target-feature-tests: PASS / regression-baseline: PASS）
   - Phase 2/6 → **収束（Critical 0 かつ Major 0）**。1回のレビューで終わらず、修正と差分再レビューを繰り返す
   - Phase 10 → 実行検証（全テスト・E2E）PASS + **収束（Critical 0 かつ Major 0）**
   - これらをタスクとして明示する（収束ループが複数周回る前提で見積もる）

4. **テスト方針論点を「補足」セクションに含める**
   - Q.1〜Q.10 形式でメタ論点をリストアップ
   - 機能特有の論点があれば追加

5. **運用モード・フロー設定の反映**
   - `docs/設計/<機能名>/_flow-config.md` を読み、**人間レビューゲートの設定（Phase 7・実装承認）**と運用モード（厳格 / lean）を把握する（存在しない場合はユーザーに確認して作成を促す）
   - lean運用ならPhase 4・Phase 9 を「省略可」と明記
   - 省略不可フェーズ（Phase 2/5/6/8/10）と収束ループは lean でも省略しない
   - Phase 7 が「スキップ」の場合、Phase 5 のタスクに「テスト観点表を AI が全件起案 → Adversary レビューで収束」を明記する

## 実行手順

### Step 1: 対象機能と運用モードの確認

ユーザーから以下を確認する：

- 対象機能（設計書のパス）
- 設計書のステータスが「合意済」か
- **`_flow-config.md` の内容**（人間レビューゲートの設定・運用モード）。既に決定済みのため再確認は不要だが、計画書に反映するため必ず読む
- 運用モードが未設定の場合のみ：「フル10フェーズ」or「lean運用」を確認する
- 機能特有の前提タスク（依存する他機能・他PRの完了待ち等）

### Step 2: 必須参照ファイルの読み込み

設計書、findings、共通機能設計書、既存実装計画書サンプル、フロー定義を読む。

### Step 3: 実装スコープの決定（大規模機能のみ）

設計書のボリューム・見積工数から、1ブランチで完結させるか複数ブランチに分割するかを判断する（`docs/開発プロセス/ブランチ運用方針.md` 参照）。**小〜中規模機能は分割不要。本Stepをスキップして Step 4 へ進む。**

分割が必要と判断した場合：

1. **分割案の提案**：安全にマージできる単位を提案する
   - 新規追加のみで完結する部分（既存機能から参照・依存されない）を優先スコープとする
   - 既存の挙動・レスポンス形式・DBスキーマを変更する部分は、依存先が揃うまで後続スコープに回すか、変更元と同一スコープにまとめる
   - バックエンド/フロントエンドという分け方は一例。画面単位・エンドポイント単位等、機能の性質に応じて柔軟に判断する
   - 提案には「今回のブランチで実装するスコープ」「後続に残すスコープとその実装順序」「分割理由（なぜこの境界が安全か）」を含める
2. **人間による確定**：提案をユーザーに提示し、承認または調整を依頼する
3. **ブランチ名の見直し**：現在のブランチ名（例：`add/<機能名>`）が機能全体を指す名称で、確定したスコープが機能全体でない場合、スコープを反映した名前へのリネームをユーザーに提案する（例：`add/<機能名>_一覧API`）
4. 後続スコープが残る場合、その旨と各スコープの実装順序を実装計画書冒頭に明記する（Phase 1〜3 の再実施は不要。同一の承認済み設計書を参照し続ける）

以降の Step は、本Stepで確定したスコープ（分割しない場合は機能全体）のみを対象に実施する。

### Step 4: タスク粒度の決定

設計書から以下を抽出してタスク化：

- DB スキーマ変更（あれば）
- API 実装（エンドポイント・認可・where句・レスポンス整形）
- 既存APIへの影響（リグレッション対応）
- フロントエンド実装（画面・コンポーネント・apiClient・型定義・サイドメニュー等）
- 環境変数・定数

各タスクは **数十分〜数時間で完了でき、PRレビューしやすい単位** とする。

### Step 5: テスト観点の抽出（Phase 5 のための準備）

設計書の受け入れ条件・エッジケース・認可・PII除外などからテストケースを抽出。Phase 5 の章で個別タスクとして列挙する。

観点の例（機能による）：

- 認可境界（他社データ漏洩防止）
- PII除外（レスポンスに氏名・電話番号・メアド等を含めない）
- 検索条件（単一・複数・該当なし・全選択）
- ページネーション
- N+1問題
- 空状態・初期表示
- 既存APIリグレッション
- 未認証
- 論理削除済みレコードの除外

### Step 6: 実装計画書の作成

格納ルール：

- 配置先：`docs/設計/<機能名>/`
- ファイル名：`<機能名>_実装計画.md`

### 実装計画書の標準章立て

```
# <機能名> 実装計画

## 本書の位置づけ
（10フェーズフローに沿うことの宣言。大規模機能でスコープ分割した場合は対象スコープと後続スコープの一覧を明記）

## 作業ステータス凡例
（完了／一部対応／未着手／未実施／ブロック中／将来対応）

## 参照資料一覧
（設計書、画面イメージ、共通機能設計書、フロー定義、既存実装等のテーブル）

## レビュー成果物の格納先
（_review/spec/, _review/test/, _review/impl/ の配置を明示）

## 0. 前提タスク（他機能で対応・本機能の着手前提）
（依存タスク・ブロック中ステータス）

## Phase 1. 設計書作成
（完了している前提のチェックリスト）

## Phase 2. 設計書 敵対的レビュー
（完了している前提のチェックリスト）

## Phase 3. 人間レビュー（設計書承認ゲート）
（承認済みの確認）

## Phase 4. 実装計画書作成
（本書自体）

## Phase 5. テスト作成（Red Phase）
### 5.1 環境・定数の準備（テスト記述に最低限必要）
### 5.2 API/サービス層の単体テスト
（観点ごとに 5.2.1, 5.2.2, ... と番号付け）
### 5.3 既存リグレッションテストの追加
### 5.4 Red Phase 証拠の記録

## Phase 6. テスト 敵対的レビュー（収束ループ）
（タスク・ゲート条件＝Critical 0 かつ Major 0 まで収束）

## Phase 7. 人間レビュー（テスト承認ゲート）
（タスク。_flow-config.md で「スキップ」の場合はその旨と代替措置を記載）

## Phase 8. 実装（Green Phase）
### 8.1 環境・定数（残り）
### 8.2 DB・Prisma
### 8.3 API実装
### 8.4 既存APIリグレッション対応
### 8.5 フロントエンド実装
### 8.6 Green Phase 証拠の記録

## Phase 9. リファクタ
（タスク・ゲート条件）

## Phase 10. 実装検証（テスト・E2E 実行＋実装レビュー・収束ループ）
（実行検証ゲート・E2Eコード化の要否・3レーンのレビュー観点・収束条件）

## 実装承認ゲート
（タスク。_flow-config.md で「スキップ」の場合はその旨を記載）

## フィードバックルーティング（未収束・エスカレーション時）
（findings種類 → 戻り先フェーズの対応表。ループ内で解消するもの／人間へ上げるものを区別）

## 完了条件
（全ゲートPASSのチェックリスト）

## 補足：テスト方針として議論すべき論点（メタ目的）
（Q.1〜Q.N 形式）

## 将来拡張
（F.1〜F.N 形式、対象外機能の備忘録）
```

各タスクテーブルの列構成：

| 列名 | 内容 |
|---|---|
| No | 階層番号（5.2.1, 5.2.2, ... 等） |
| タスク | タスク名（短い動詞句） |
| 詳細 | 実装方針・参考資料・注意点 |
| ステータス | 凡例から選択 |

### Step 7: 自己レビュー

書き終えたら、以下を自己チェックする：

- [ ] 設計書のすべての受け入れ条件がテストタスク（Phase 5）でカバーされているか
- [ ] 設計書の項目定義のすべてが実装タスク（Phase 8）でカバーされているか
- [ ] 認可・PII除外などのセキュリティ観点がテストタスクに含まれているか
- [ ] 既存APIへのリグレッション対応タスクがあるか
- [ ] 各 Phase のゲート条件（Red/Green Phase 証拠等）が明記されているか
- [ ] 前提タスク（依存）が「ブロック中」として明記されているか
- [ ] 補足のテスト方針論点が機能に応じて整理されているか
- [ ] フィードバックルーティングの対応表が含まれているか
- [ ] 完了条件が全ゲートPASS基準で書かれているか
- [ ] スコープ分割した場合、対象スコープと後続スコープが明記されているか

### Step 8: 完了通知と次フェーズ案内

```
Phase 4（実装計画書作成）が完了しました。
- 実装計画書: docs/設計/<機能名>/<機能名>_実装計画.md
- タスク総数: N（うち未着手 N、ブロック中 N、完了 N）
- 各フェーズの構成: Phase 0〜10 + 補足

【スコープ分割した場合】
- 今回のブランチで実装するスコープ: <内容>
- 後続スコープ: <内容と実装順序>
- ブランチ名: 現状のまま／<新しい名前>へのリネームを推奨（理由: <理由>）

次は Phase 5（テスト作成・Red Phase）です。
準備ができたら「テストを書いて」「Red Phase に入って」とお声がけください。

ただし、前提タスク（Phase 0）に「ブロック中」がある場合は、それらが完了するまで Phase 5 のテスト作成は限定的になります。
ブロック中の前提タスクの状況も合わせてご確認ください。
```

## 禁止事項

- 設計書のステータスが「合意済」でないまま実装計画書を作成しない（Phase 3 の承認待ち）
- 10フェーズフロー以外の章立てを採用しない（既存の旧フォーマットに引きずられない）
- テスト観点を「テスト・検証」の単一カテゴリにまとめない（Phase 5/Phase 6/Phase 8/Phase 10 に分離する）
- 実装タスクを Phase 5（テスト）より先に書かない（フローの順序を崩さない）
- ベースに無いが必要な項目（機能特有の論点）を抑制しない（積極的に追加してよい）
- 実装スコープの分割・ブランチリネームを人間確認なしに確定しない（Step 3 は必ず提案→承認のステップを踏む）
- 既存の挙動・レスポンス形式・DBスキーマを変更するタスクを、安全性を検証せずに先行スコープへ含めない（`ブランチ運用方針.md` 2.3 の基準に従う）

## 補足：参考になる既存実装計画書

対象リポジトリに10フェーズフロー対応の実装計画書が既にあれば、章立て・タスク粒度・ゲート条件の書き方の見本として活用する。

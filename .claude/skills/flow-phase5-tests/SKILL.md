# Phase 5: テスト作成（Red Phase）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 5** を担当するスキル。合意済み設計書と実装計画書をもとにした失敗するテストの作成を、司令塔（メイン会話のAI）と分離された **fresh context** の `test-builder` ワーカーエージェントが行う。**実装コードは書かない**（Phase 8 の責務）。

**ワーカーを分離する理由：** テスト作成者が設計段階の会話履歴を持っていると、設計書に書かれていない「議論の記憶」でテストの曖昧さを補ってしまい、設計書の不備が Phase 6 まで顕在化しない。fresh context のワーカーは disk 上の設計書だけを仕様として読むため、「設計書がテストを書くのに十分か」の検証を兼ねる。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典
1-b. `flow-review-policy` skill（本 skill と同じ skills ディレクトリ内。絶対パスに解決して読む）— **テスト観点の確定方式（1.4）・AI起案チェックリスト（1.5）・収束ループ（4章）の正本**
1-c. `docs/設計/<機能名>/_flow-config.md` — フロー設定（**Phase 7 の実施要否**＝観点表の記載方式を決定する）
2. 対象機能の設計書（Phase 3 で承認済みであることをステータス欄で確認）。「テストレベル判定」節（Phase 1 Step 6 で記載）を必ず確認する
3. 対象機能の実装計画書（Phase 5 セクションのテストケース一覧）
4. `AGENTS.md` の「テスト指針」セクション — テスト対象の判断基準
5. `docs/開発プロセス/テストレベル選定トリガー表.md` — 影響度トリガー該当分の判定基準
6. `docs/開発プロセス/テスト観点表テンプレート.md` — テスト仕様確定フローの様式（影響度トリガー該当時のみ使用。結合DB込み：人間本記載／E2E：AI起案→人間承認）

## 重要な前提（必ず守ること）

1. **テスト作成は fresh context の `test-builder` が行う**
   - `test-builder` 役割のサブエージェントを **新規エージェントとして** 起動する（起動方法は末尾「補足」参照）
   - 司令塔（メイン会話）は自分でテストコードを書かない
   - 設計書・実装計画書はワーカーに **disk から読ませる**（会話履歴経由ではない）
   - テスト記述の詳細ルール（配置・命名・モック化・トートロジー禁止・PII 3層検証等）は役割ファイル（`flow-agent-roles/roles/test-builder.md`）に固定済み

2. **実装ロジックは書かない・書かせない**
   - 例外：テスト記述に最低限必要な「型定義」「enum定数」（実装計画書 Phase 5.1 相当）と、Red Phase 証拠用の**スタブ最小実装**（シグネチャ＋固定ダミー返却のみ）はワーカーが書いてよい
   - Red Phase 証拠は**スタブ最小実装方式**（2026-07-12 決定）：新規テストは import エラーではなく期待値不一致で個別に FAIL させる。スタブ段階で PASS するテストはトートロジー疑い

3. **未決事項はワーカー起動前に解消する**
   - ワーカーは実行中にユーザーへ質問できない。テスト記述に直接関わる未決事項（DB カラム名・デフォルト orderBy・enum 未知値のフォールバック・バリデーションエラーの error code 等）が設計書に残っている場合、**起動前に** ユーザーに確認して解消する
   - 未決のまま書かれたテストは Phase 6 で必ず指摘される（過去実績）

4. **Red Phase は司令塔が独立に再検証する**
   - ワーカーの「新規 FAIL／既存 PASS」の自己申告を鵜呑みにせず、司令塔自身が `npm run test` を再実行して確認する

5. **Red Phase 証拠は司令塔が記録する**
   - `docs/設計/<機能名>/_review/test/red-phase-evidence.md` に保存。これがないと Phase 6 に進めない

6. **前提タスクのブロック判定**
   - 設計書「影響を受ける実装済み機能」の前提タスク（DB スキーマ変更等）がブロック中の場合：モック化ベースのテストのみ実施可能と説明し、実施範囲をユーザーに確認 **してから** ワーカーを起動する

7. **影響度トリガー該当分はテスト仕様を先に確定してからコード化する（2026-07-12 追加・2026-08-12 改訂）**
   - 設計書「テストレベル判定」節で影響度トリガー（認可境界・PII取扱い・認証セッション・不可逆操作・クリティカルパス業務・金銭契約）に該当する項目は、`test-builder` に直接テストケースを考えさせない
   - **記載方式はフロー設定（`_flow-config.md`）の Phase 7 実施要否で決まる**（`flow-review-policy` 1.4）：

     | Phase 7 の設定 | 結合(DB込み)の観点表 | クリティカルパスE2E |
     |---|---|---|
     | 実施 | **人間本記載方式**（司令塔は各観点1〜2件の記入例のみ。残りはユーザーが記載） | **AI起案 → Adversary レビュー → 人間が修正・承認して凍結** |
     | スキップ | **AI起案方式**（司令塔が全件起案。`flow-review-policy` 1.5 のチェックリストを足場にする） | **AI起案 → Adversary レビュー → Critical/Major ゼロで凍結** |

   - **AI起案方式で守ること**：根拠は承認済み設計書・要件メモのみ。設計書にない挙動を推測で補った箇所は「仮置き」と明記し、**仮置きが1件でもあればその点だけはユーザーに確認する**（設計書の不備であり、テストの問題ではないため）
   - 発生可能性トリガーのみ該当・トリガー非該当の項目は、現行どおり `test-builder` が機械的に導出する

8. **クリティカルパスE2Eは仕様凍結のみ、コード化・実行は Phase 10**
   - Phase 5 では E2E のシナリオ仕様（操作手順・期待結果）を AI起案→人間承認フローで確定（凍結）するところまでを行う
   - Playwright コードの実装は本skillの対象外（Phase 10 の実装検証で司令塔がコード化し、実行検証ゲート `npm run test:e2e` の対象として全件実行する）

## 実行手順

### Step 1: 設計書の承認状態とフロー設定の確認

設計書冒頭の「ステータス」が「合意済」であることを確認する。「レビュー中」「未着手」の場合は本skillを実行せず、Phase 3 完了を促す。

あわせて `docs/設計/<機能名>/_flow-config.md` を読み、**Phase 7（テスト承認ゲート）の実施要否**・運用モード・レーン並列・収束ループ上限を把握する。設定ファイルが存在しない場合は、`flow-review-policy` 1.6 の様式に従いユーザーに確認して作成してから先へ進む（設定なしでは Step 4 の記載方式が決まらない）。

### Step 2: 未決事項・前提タスクの解消（ワーカー起動前）

- 設計書の未決事項のうち、テスト記述に直接関わるものを洗い出し、残っていればユーザーに確認して解消する
- 前提タスクがブロック中の場合、実施範囲（モック化ベースで実施／ブロック解除を待つ）をユーザーに確認する
- テスト方針の論点（モック vs 実DB・PII 除外の担保方法・N+1 検証手法・組み合わせ爆発の扱い等）で本機能特有の判断が必要なら、ここでユーザーに確認する

### Step 3: テスト範囲・トリガーの決定

実装計画書の Phase 5 セクションと `AGENTS.md`「テスト対象の判断基準」から、対象テストケースを抽出して一覧化する：

- **書く**：API ルートハンドラ（結合・内部）／ヘルパー関数・サービス層（単体）／認可境界・PII除外・N+1 等のセキュリティ・品質観点
- **書かない**：表示系コンポーネント／スナップショット

あわせて、設計書「テストレベル判定」節（Phase 1 で記載済み）から該当トリガーを確認し、対象を2グループに分ける：

- **グループA（テスト仕様確定フロー対象）**：影響度トリガー該当分（結合DB込みの一部・クリティカルパスE2E）→ Step 4 へ。結合(DB込み)分は**人間本記載方式**、クリティカルパスE2E分は**AI起案方式**で仕様を確定する
- **グループB（機械導出）**：発生可能性トリガーのみ該当・トリガー非該当（単体・結合内部・結合DB込みの技術検証部分）→ Step 5 へ直行

### Step 4: テスト仕様の確定フロー（グループAのみ実施）

グループAに該当する項目がない場合は本Stepをスキップし、Step 5 へ進む。結合(DB込み)分とE2E分の両方がある場合は、1つの観点表ファイルで並行して進める（Adversary レビューは1回にまとめてよい）。

保存先：`docs/設計/<機能名>/_review/test/観点表.md`（様式は `docs/開発プロセス/テスト観点表テンプレート.md`）

#### 4-1. 観点表の生成・起案（司令塔）

**結合(DB込み)分** — `_flow-config.md` の Phase 7 設定で分岐する：

- **Phase 7「実施」→ 人間本記載方式**（1章の様式）：該当トリガーごとに観点行を作成し、各観点につき **1〜2件のみ** 記入例を埋める（意図的に不完全にする。残りは人間が記載する）
- **Phase 7「スキップ」→ AI起案方式**（1章の様式・全件記載）：司令塔が全観点・全テストケース・期待結果を起案する。このとき **`flow-review-policy` 1.5 のチェックリストを必ず開き、該当トリガーごとの「起案必須の観点」をすべて起案する**（該当なしと判断した観点は「該当なし」の理由を表に明記する。無言の省略は不可）。根拠は承認済み設計書・要件メモのみとし、根拠がない箇所は「仮置き」と明記する

**クリティカルパスE2E分**（2章の様式・AI起案方式・設定によらず共通）：承認済み設計書（「テストレベル判定」節・受け入れ条件）のみを根拠に、シナリオ・操作手順・期待結果・必要なセレクタ仕様を**全件記載した起案**を作成する。設計書にない挙動を推測で補った箇所は「仮置き」と明記する。

#### 4-2. 人間による本記載（Phase 7「実施」かつ 結合DB込み分がある場合のみ）

生成した観点表をユーザーに提示し、空欄のテストケース・期待結果の記載を依頼する。ここで一時停止し、ユーザーの記載完了を待つ。E2E分は起案済みのため本記載は不要（人間の確認は 4-4 でまとめて行う）。

#### 4-3. Adversary レビューと収束ループ

`adversarial-reviewer` 役割のサブエージェントを fresh context として起動し（起動方法は末尾「補足」参照）、観点表をレビューさせる。

- **レビュー観点**：① 網羅性（該当トリガーに対して必要な観点が揃っているか。`flow-review-policy` 1.5 のチェックリストと突き合わせる）／② 期待結果の曖昧さ（テストで判定できる形になっているか）／③ 実現可能性（テストとして書けるか・前提データが用意できるか）／④ クリティカルパス選定の妥当性／⑤ 仮置き箇所の妥当性
- **AI起案方式の場合は必ず伝える**：「この観点表は AI が起案したものであり、人間の本記載による網羅性の担保がない。**起案者が思いつかなかった観点を能動的に探すこと**が本レビューの主目的である」
- **出力予算**：Critical / Major はフル記述、Minor は1行

**収束ループ（`flow-review-policy` 4章）：** レビュー結果に Critical / Major がある場合、司令塔が観点表を修正して**差分再レビュー**を行い、**Critical 0 かつ Major 0 になるまで繰り返す**（上限は `_flow-config.md` の設定・既定5周）。設計書に根拠がない指摘（仮置きの妥当性・仕様判断が必要なもの）はループを止めてユーザーに確認する。各周の記録は `_review/test/review-log.md` の「観点表レビュー」節に残す。

#### 4-4. 最終確定（凍結）

- **Phase 7「実施」の場合**：記載内容とレビュー結果をユーザーに提示し、修正・取捨選択のうえ確定を依頼する。**人間の承認なしにE2Eシナリオ仕様・観点表を凍結してはならない**
- **Phase 7「スキップ」の場合**：収束（Critical 0・Major 0）をもって凍結する。ただし**仮置きが残っている場合はその点のみユーザーに確認してから凍結する**

確定後、観点表ファイルの冒頭に「確定日時」「確定方式（人間確定 / 収束による確定）」「レビュー Round 数」を追記する。

確定した観点表は Step 5 で `test-builder` への入力として渡す（テストケースの内容を変更してはならない。コード化のみを委ねる）。凍結したE2Eシナリオ仕様は Phase 10 の実装検証で司令塔が Playwright コード化し、実行検証ゲート（`npm run test:e2e`）の対象になる。

### Step 5: test-builder ワーカーの起動

`test-builder` 役割のサブエージェントを fresh context として起動する（起動方法は末尾「補足」参照）。

**プロンプトに含める内容：**

- 役割ファイル（`flow-agent-roles/roles/test-builder.md`）の絶対パスと「最初に読み、以後その役割に完全に従う」指示
- 設計書・実装計画書・`AGENTS.md` の絶対パス
- Step 3 で決定したテスト範囲（書くテスト・書かないテストの一覧）
- Step 2 で解消した未決事項の決定内容
- **グループA該当分**：Step 4 で確定した観点表のパス。「記載されたテストケースをそのままコード化すること。内容の変更・追加・削除は不可」と明記する
- **クリティカルパスE2E分**：シナリオ仕様は確定するが、この時点ではPlaywrightコード化は行わない（Phase 10 の実装検証でコード化・実行）ことを明記し、対象から除外する
- 参考にすべき既存テストのパス（対象リポジトリの類似機能の既存テストから司令塔が選定する）
- 既存類似 API の route.ts のパス（`apiHandler` ラッパー等の構造確認用）
- 前提タスクの状況（保留するテストがあればその一覧）
- 最終応答フォーマット（役割ファイルのフォーマットに従うこと）を明記

### Step 6: ワーカー報告の受領と判断

ワーカーの最終応答を確認する：

- **「質問・仮置き事項」がある場合** → 内容をユーザーに報告して判断を仰ぐ。設計書の修正が必要なら Phase 3 差し戻しを案内。解消後にワーカーを再起動（または SendMessage で継続）する
- **完了報告の場合** → Step 7 へ

### Step 7: Red Phase 独立検証（司令塔の責務）

司令塔自身が実行する：

```bash
npm run test
```

期待する結果：

- **新規テスト：全件 FAIL、かつ失敗理由がスタブに対する期待値不一致であること**（import エラーの一括 FAIL は原則不可。残る場合は理由を証拠に明記）
- **既存テスト（リグレッション）：全件 PASS**

あわせて確認する：

- **既存の実装ファイルが変更されていないこと**（`git status` で変更が テストファイル＋型定義・定数＋スタブ最小実装のみ であること）
- **スタブに実ロジックが書かれていないこと**（スタブは固定ダミー返却のみ。条件分岐や整形が入っていたら Phase 8 の先取りとして差し戻す）
- 新規テストが通ってしまった場合はトートロジー疑い。findings をまとめてワーカーを再起動する

### Step 8: Red Phase 証拠の記録（司令塔の責務）

`docs/設計/<機能名>/_review/test/red-phase-evidence.md` に保存：

```markdown
# Red Phase Evidence

- 機能：<機能名>
- 実施日時：<YYYY-MM-DD HH:MM>
- テスト作成：test-builder（fresh context）／Red Phase 検証：司令塔が独立再実行
- 実行コマンド：`npm run test`

## マーカー

- new-feature-tests: FAIL（N tests・全件期待値不一致）
- regression-baseline: PASS（M tests）
- impl-files-unchanged: 確認済（変更はテスト＋型定義・定数＋スタブ最小実装のみ）

## 新規テストの失敗内訳

| テストファイル | Fail件数 | 主な失敗理由 |
|---|---|---|
| route.test.ts | 18 | スタブに対する期待値不一致 |

※スタブ最小実装方式（2026-07-12 決定）：全件が期待値不一致 FAIL であること。import エラー型が残る場合は対象と理由を明記する（その範囲はトートロジー検出不能として Phase 6 に引き継がれる）
※スタブ段階で PASS したテスト（トートロジー疑い）があった場合は、書き直しの内容を補足に記載する

## 既存テスト（リグレッション）の通過確認

全 M 件 PASS。

## 補足

- 前提タスクのブロックにより保留したテストがあればその旨を明記
- ワーカーからの仮置き報告があればその内容と司令塔の判断を明記
```

### Step 9: E2E候補カタログへの追記

設計書「テストレベル判定」節に記載された、クリティカルパス外の画面操作シナリオを `docs/開発プロセス/E2E候補カタログ.md` に追記する（`テスト観点表テンプレート.md` 3章の様式に従う）。ファイルが存在しない場合は様式に沿って新規作成する。

### Step 10: 完了通知と次フェーズ案内

```
Phase 5（テスト作成・Red Phase）が完了しました。

成果物:
- テストファイル: <パス一覧>
- Red Phase log: docs/設計/<機能名>/_review/test/red-phase-evidence.md
- 観点表（テスト仕様確定フロー該当時）: docs/設計/<機能名>/_review/test/観点表.md
  - 記載方式: 人間本記載 / AI起案（Phase 7 スキップ設定）
  - 確定方式: 人間確定 / 収束による確定（Adversary レビュー Round N で Critical 0・Major 0）
- E2Eシナリオ仕様（クリティカルパス該当時）: 観点表2章にて凍結済み（Phase 10 でコード化・実行）
```

## 禁止事項

- **司令塔（メイン会話）が直接テストコードを書かない**（必ず `test-builder` を fresh context で起動）
- 実装ロジックを書かない・書かせない（Phase 8 の責務）
- 未決事項・前提タスクの扱いを解消しないままワーカーを起動しない
- ワーカーの自己申告のみで Red Phase 成立と判定しない（司令塔の独立再検証必須）
- 既存テストが FAIL する状態で Phase 5 を続行しない（原因を別タスクとして切り出す）
- スナップショットテストを書かせない（AGENTS.md 推奨外）
- **Phase 7「実施」設定の機能で、影響度トリガー該当の結合(DB込み)分のテストケースを AI（司令塔・test-builder いずれも）が勝手に決めない**（観点表テンプレートの記入例1〜2件のみ許可。残りは人間の本記載必須）
- **Phase 7「実施」設定の機能で、人間の承認なしに観点表・E2Eシナリオ仕様を凍結しない**（起案＋Adversaryレビュー＋人間確定がそろって初めて仕様凍結となる）
- **Phase 7「スキップ」設定の機能で、Adversary レビューを省略して AI 起案の観点表をそのまま凍結しない**（Critical/Major ゼロまでの収束が人間本記載の代替措置である）
- **AI 起案時に `flow-review-policy` 1.5 のチェックリストを開かずに観点を起案しない**（該当トリガーごとの必須観点を無言で省略しない）
- 設計書に根拠のない仮置きを、ユーザー確認なしに凍結しない
- 確定済み観点表のテストケース内容を `test-builder` に変更させない（コード化のみを委ねる）
- クリティカルパスE2E の Playwright コードを Phase 5 内で書かない（Phase 10 の実装検証で実施）

## 補足：ワーカー・Adversary の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/` 配下（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）：

- テスト作成ワーカー：`flow-agent-roles/roles/test-builder.md`
- 観点表レビュー用 Adversary：`flow-agent-roles/roles/adversarial-reviewer.md`

**起動方法：** ツールの汎用サブエージェント起動機能で新規エージェント（fresh context）を起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・最終応答フォーマットに完全に従うこと」を指示する。Adversary の読み取り専用の制約は役割ファイル内の指示で担保する。

起動できない場合はユーザーに環境設定の確認を求める。司令塔（メイン会話）が役割を代行してはならない。

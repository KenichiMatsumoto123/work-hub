# Phase 6: テスト 敵対的レビュー（収束ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 6** を担当するスキル。Phase 5 で作成されたテストファイルを、司令塔（メイン会話のAI）と分離された **fresh context** の `adversarial-reviewer` サブエージェントが批判的にレビューする。

**このフェーズの存在理由：** AIは「テストを先に書いて、後で実装をテストに合わせる」が起きやすい。また作成者は自分が書いたテストの脆弱性（特にトートロジー）に構造的に気付けない。テスト段階で独立レビューすることで、「テストが仕様を正しく表現していない」を実装前に検出する。

**本フェーズは1回のレビューでは終わらない。** Critical / Major がゼロになるまで「レビュー → `test-builder` による修正 → 差分再レビュー」を繰り返す。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典。Phase 6 の位置づけとゲート観点を理解する
2. `flow-review-policy` skill（本 skill と同じ skills ディレクトリ内。絶対パスに解決して読む）— **較正不変の原則・観点レーン分割・出力予算・must-catch・収束ループの正本**
3. `docs/設計/<機能名>/_flow-config.md` — フロー設定（**Phase 7 の実施要否**・運用モード・レーン並列・収束ループ上限）
4. 対象機能の設計書（`docs/設計/<機能名>/<機能名>_設計書.md`）— 受け入れ条件との対応チェックの基準
5. 対象機能の実装計画書（あれば）— テストケースリストとの対応チェックの基準
6. Red Phase 証拠（`docs/設計/<機能名>/_review/test/red-phase-evidence.md`）— Red Phase の成立確認
7. 観点表（`docs/設計/<機能名>/_review/test/観点表.md`）— 存在する場合。確定済みテスト仕様との対応チェックの基準
8. `AGENTS.md` のテスト指針 — テスト作成ルール・配置・命名の準拠確認

## 重要な前提（必ず守ること）

1. **Adversary は fresh context で起動する**
   - `adversarial-reviewer` 役割のサブエージェントを **新規エージェントとして** 起動する（起動方法は末尾「補足」参照）
   - 司令塔（メイン会話）の文脈・「なぜこう書いたか」の弁明を一切引き継がない
   - テストファイル・設計書を **disk から読ませる**（会話履歴経由ではない）

2. **観点はレーンに分割して並列起動する（時間短縮の主手段）**
   - 較正（敵対的な探索の深さ）は絶対に下げない。短縮は「分割・並列化」「出力粒度」「差分レビュー」で行う（`flow-review-policy` 2章）
   - 既定は3レーン（下記 Step 4）。**同一メッセージ内でまとめて起動して並列に走らせる**

3. **findings の disk 書き出しは司令塔（本skillの実行AI）が担当する**
   - Adversary は Read 専用エージェントであり、findings は最終応答テキストとして返却する
   - 司令塔は各レーンの応答をマージして `_review/test/findings.md` に Write する

4. **「全体的によい」は禁止**
   - findings は必ず severity（Critical / Major / Minor）と該当箇所（ファイルパス・行番号）を明記する
   - 問題が見つからない観点も「該当なし」と肯定的な証拠（検証した具体箇所）を明示する

5. **収束するまでループする**
   - テストの修正は **`test-builder` を fresh context で再起動して行わせる**（司令塔がテストコードを直接書かない）
   - 修正後は司令塔が `npm run test` を再実行し、Red Phase が維持されていること（新規 FAIL / 既存 PASS）を再検証する
   - **Phase 7 をスキップする設定の機能では、Major の「文書化のみで通過」は使えない**（Critical/Major の完全ゼロ化が必須）

## 実行手順

### Step 1: レビュー対象とフロー設定の確認

以下を確認する（既に提示されていれば省略）：

- レビュー対象のテストファイルパス（例: `src/app/api/<機能>/__tests__/route.test.ts`、`_lib/__tests__/*.test.ts`）
- 対象機能の設計書・実装計画書・観点表のパス
- Red Phase 証拠のパス
- テストが参照する型定義・定数ファイル（`_types/api.d.ts`、`_constant/` 等）
- `_flow-config.md` の **Phase 7 実施要否**・運用モード・レーン並列・収束ループ上限（既定5周）

### Step 2: 必須参照ファイルの読み込み

上記「必須参照ファイル」を読む。Phase 5 の完了（Red Phase 証拠の存在）を確認し、なければ Phase 5 の実施を先に案内する。

### Step 3: 出力先ディレクトリの確認

対象機能の設計書と同じディレクトリの `_review/test/` を使用する（Phase 5 で作成済み）。

- findings: `docs/設計/<機能名>/_review/test/findings.md`
- 収束ログ: `docs/設計/<機能名>/_review/test/review-log.md`

### Step 4: Adversary サブエージェントの並列起動（Round 1）

`adversarial-reviewer` 役割のサブエージェントを、**レーンごとに fresh context で並列起動する**（起動方法は末尾「補足」参照）。

**既定のレーン割り（`flow-review-policy` 3.2）：**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: テスト自体の欺瞞性 | ① **トートロジー検出**（モックが返す値をそのまま assert していないか。実装の整形・フィルタリング・変換ロジックを検証しているか。`expect(x).toBeDefined()` だけの実質空のテストがないか）／② 実装詳細の過剰束縛（正当なリファクタを妨げないか） | MC-1 |
| B: 仕様との対応 | ③ 受け入れ条件との対応（**受け入れ条件×テストの対応マトリクス**（✅/⚠️/❌/N/A）の作成を必須とする。観点表がある場合は確定済みテストケースとの対応も検証）／④ エッジケース・例外系の網羅（境界値・不正値・0件・null リレーション・未認証の it.each 網羅） | MC-4・MC-6 |
| C: セキュリティと証拠 | ⑤ セキュリティ・品質観点（下記パターン）／⑥ Red Phase log の妥当性 | MC-2・MC-3・MC-5・MC-9 |

**レーン C に伝える必須チェックパターン**（過去の実走で確立）：

- **PII 除外の3層検証**：型レベル + モック汚染テスト（モックに意図的に PII を混入させて除外を確認）+ JSON シリアライズ値検証。モックが PII を返さないだけのテストはトートロジー
- **認可境界の2層検証**：where 引数の assert + 他社データ混在モックでの検証
- **N+1 検出**：`mockImplementation` 等でクエリ数を強制カウントしているか
- **既存規約整合**：既存の類似 API の構造（`apiHandler` ラッパーの有無、`isAuth` の使い方等）をテストが正しく前提にしているか。既存 route.ts を実際に読んで突き合わせる
- **Red Phase log の妥当性**：新規テスト全件 FAIL + 既存テスト全件 PASS が実行ログで証明されているか。スタブ最小実装方式に従い、失敗が**期待値不一致で個別に enumerate** されているか。**スタブに実ロジックが混入していないか**（Phase 8 の先取り検出）。import エラーによる一括失敗が残っている場合は、その範囲でトートロジー混入を検出できないことを findings に明記させる

**レーン B に伝える追加指示**：**未決事項の素通し**（設計書に未決事項が残ったまま書かれた、曖昧性を温存するテストがないか）を必ず確認する。

**各レーンのプロンプトに含める内容：**

- 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- レビュー対象テストファイルの絶対パス（全件）
- 設計書・実装計画書・観点表・Red Phase 証拠・関連型定義の絶対パス
- **担当レーンの観点のみ**を敵対的較正で深く見ること
- 担当する **must-catch 項目**と必須チェックパターン（上記）
- **出力予算**：Critical / Major はフル記述、Minor は「FIND-XXX: 見出し（ファイル:行）」の1行のみ、PASS 観点の裏付けは1〜2行
- **Phase 7 の実施要否**（スキップ設定の場合は「人間の最終確認が入らないため、Critical/Major の見落としがそのまま実装に流れる」ことを明記する）
- **findings は最終応答テキストとして返却することを明記**

### Step 5: findings のマージと disk 書き出し（司令塔の責務）

各レーンの応答テキストを `flow-review-policy` 3.3 のマージ規則に従って統合する（重複統合・severity は高い方・矛盾は両論併記・**要約や軟化や削除はしない**）。統合結果を `Write` ツールで `docs/設計/<機能名>/_review/test/findings.md` に保存する。

```markdown
# テスト 敵対的レビュー結果（Phase 6 Round N）

- **対象**: <テストファイル・関連ファイルのパス一覧>
- **レビュー日時**: YYYY-MM-DD
- **方式**: 敵対的較正・3レーン並列（A: 欺瞞性 / B: 仕様対応 / C: セキュリティと証拠）。Adversary は fresh context・Read 専用。findings は司令塔が disk に保存
- **Phase 7（人間レビュー）**: 実施 / スキップ
- **総合判定**: PASS（Critical 0・Major 0）/ FAIL

## サマリー

| Severity | 件数 |
|---|---|
| Critical | N |
| Major    | N |
| Minor    | N |

### Critical / Major findings 見出し一覧

- **FIND-001**: <短い見出し>

## 設計書 受け入れ条件 × テスト 対応マトリクス

凡例：✅ 対応テストあり / ⚠️ 部分的・不十分 / ❌ 未対応 / N/A 本テストの責務外

| 設計書 受け入れ条件 | 該当行 | 対応テスト | 状況 |
|---|---|---|---|

## Findings（Critical / Major）

### FIND-001: <タイトル>
- **観点 / レーン**: <該当観点>（レーン<X>）
- **重大度**: Critical / Major
- **ファイル**: <ファイルパス:行番号>
- **問題**: <具体的な問題点>
- **影響**: <この問題が解決されないと Phase 8 以降で何が起きるか>
- **推奨対応**: <修正方針>
- **戻り先**: Phase 5（テスト修正）/ Phase 1・3（設計書の不備）

## Minor（1行のみ）

- FIND-XXX: <見出し>（<ファイル:行>）

## レビュー観点ごとの判定

| 観点 | レーン | 判定 | 裏付け |
|---|---|---|---|
| トートロジー検出 | A | PASS / FAIL | |
| 実装詳細の過剰束縛 | A | PASS / FAIL | |
| 受け入れ条件との対応 | B | PASS / FAIL | |
| エッジケース・例外系の網羅 | B | PASS / FAIL | |
| セキュリティ・品質観点 | C | PASS / FAIL | |
| Red Phase log の妥当性 | C | PASS / FAIL | |
```

Round 2 以降は前回分を上書きせず「Round N」の節として追記する（Phase 7 判定記録が含まれる場合があるため、既存内容は必ず保持する）。

### Step 6: 収束ループ（Critical / Major がゼロになるまで）

**収束条件：Critical 0 件 かつ Major 0 件。**Minor は収束条件に含めない。

収束していない場合、次を繰り返す：

1. **findings の仕分け**
   - **戻り先が Phase 5（テストの不備）** → ループ内で解消する（下記 2 へ）
   - **戻り先が Phase 1・3（設計書の不備・仕様判断が必要）** → `flow-review-policy` 4.3 によりループを止めて**人間へエスカレーション**する（承認済み設計書の変更は人間の判断事項）
2. **`test-builder` の再起動による修正**（司令塔はテストコードを書かない）
   - 役割ファイル（`flow-agent-roles/roles/test-builder.md`）の絶対パス
   - 解消すべき findings（FIND-ID・問題・推奨対応）
   - 「観点表がある場合、確定済みテストケースの内容は変更しないこと。指摘された欠陥の修正のみ行うこと」
   - 「既存の実装ファイルを変更しないこと。スタブに実ロジックを書かないこと」
3. **Red Phase の再検証**（司令塔）：`npm run test` を自ら再実行し、**新規テスト全件 FAIL（期待値不一致）／既存テスト全件 PASS** が維持されていることを確認する。`red-phase-evidence.md` を更新する
4. **差分再レビュー（Round N+1）**：`flow-review-policy` 4.4 に従い、次に限定して Adversary を再起動する
   - 前回 findings の解消確認（1件ずつ「解消 / 未解消 / 部分的」）
   - 修正差分に含まれる新規欠陥
   - must-catch チェック（毎周必須。特に MC-1 トートロジーは修正で再混入しやすい）
   - **例外**：テスト構成の全面見直しなど修正が広範囲に波及した場合は、司令塔の判断でフルレビュー（3レーン並列）に戻してよい
5. 収束するまで 1〜4 を繰り返す

**ループを抜けて人間へ即エスカレーションする条件（`flow-review-policy` 4.3）：** 設計書の修正が必要／仕様判断が必要／スコープ拡大／同一 finding が2周連続で未解消・振動／収束ループ上限（既定5周）到達。

### Step 7: 収束ログの記録

`docs/設計/<機能名>/_review/test/review-log.md` に `flow-review-policy` 4.5 の様式で記録する。

### Step 8: 完了通知と次フェーズ案内

**Phase 7 を「実施」に設定している場合：**

```
Phase 6（テスト 敵対的レビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/test/findings.md
- 収束ログ: docs/設計/<機能名>/_review/test/review-log.md
- 収束: Round N で Critical 0・Major 0（Minor N 件は記録のみ）
- 受け入れ条件マトリクス: 未対応 ❌ 0 件 / 部分的 ⚠️ 0 件
- Red Phase: 再検証済（新規 N 件 FAIL / 既存 M 件 PASS）

次は Phase 7（人間レビュー・テスト承認ゲート）です。
findings と収束ログをご確認の上、以下のいずれかをお伝えください：
  - 「テストを修正して」 → Phase 5 に戻り、ご指摘を反映
  - 「テストを承認します」 → Phase 8（実装・Green Phase）に進む
    ※承認時に、承認判定と Minor findings の取り扱い方針を findings.md に記録します
```

**Phase 7 を「スキップ」に設定している場合：**

```
Phase 6（テスト 敵対的レビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/test/findings.md
- 収束ログ: docs/設計/<機能名>/_review/test/review-log.md
- 収束: Round N で Critical 0・Major 0（Minor N 件は記録のみ）
- 受け入れ条件マトリクス: 未対応 ❌ 0 件 / 部分的 ⚠️ 0 件
- Red Phase: 再検証済（新規 N 件 FAIL / 既存 M 件 PASS）

フロー設定により Phase 7（人間レビュー）はスキップします。
収束（Critical 0・Major 0）をもってテスト承認とみなし、findings.md に
「Phase 7: スキップ（フロー設定）／収束をもって承認」を記録しました。

次は Phase 8（実装・Green Phase）です。
「実装して」とお声がけください（flow-phase8-impl skill が起動します）。
```

Phase 7 実施時に承認された場合、司令塔は承認判定・Critical/Major の解消状況・Minor の取り扱い方針を「Phase 7 人間レビュー判定」節として findings.md に追記する。スキップ時も同節に「スキップ（フロー設定）」と収束の根拠を記録する。

## 禁止事項

- **Adversary をメイン会話のAIとして実行しない**（必ず fresh context のサブエージェントとして起動）
- **較正を下げて時間短縮しない**（短縮は分割・並列化・出力粒度・差分レビューで行う）
- must-catch チェック（特に MC-1 トートロジー）を差分レビューを理由に省略しない
- Adversary に Write を強要しない（findings 書き出しは司令塔の責務）
- 各レーンの指摘を司令塔が要約・軟化・削除しない
- 「全体的によい」「特に問題なし」だけの findings を許容しない
- **司令塔がテストコードを直接修正しない**（修正は `test-builder` を fresh context で再起動）
- **1回のレビューで打ち切らない**（Critical/Major が残った状態で Phase 8 へ進めない）
- **Phase 7 をスキップする機能で、AI の判断により Major を「文書化のみで通過」にしない**
- 設計書の不備に起因する findings をテスト側の小手先修正で潰さない（人間へエスカレーション）
- Red Phase 証拠なしでレビューを開始しない（Phase 5 未完了の場合は先に Phase 5 を案内）

## 補足：Adversary の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/adversarial-reviewer.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。テスト修正時のワーカーは `flow-agent-roles/roles/test-builder.md`。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・出力形式に完全に従うこと」を指示する。読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。**レーン並列時は、レーンごとに別のサブエージェントを同一メッセージ内でまとめて起動する。**

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

# Phase 9: リファクタ

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 9** を担当するスキル。Phase 8 のコードを、承認済みテストを安全網として構造改善する。

**Phase 8 と分ける理由（フロー正典より）：**「動くこと」と「良いコード」の責任を分離する。テストが Green を維持している限り、構造変更は安全に行える。

**lean 運用：** 簡単な機能で明らかに不要ならスキップ可。スキップする場合はその判断をユーザーに確認し、Green Phase 証拠に「Phase 9 スキップ（理由）」を追記して Phase 10 に進む。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — Phase 9 の観点とゲート条件
2. Phase 8 の実装コードと Green Phase 証拠（`_review/impl/green-phase-evidence.md`）
3. `AGENTS.md` — コーディング規約（命名・配置・`@/` エイリアス等）

## 重要な前提（必ず守ること）

1. **外部から見た振る舞いを変えない** — 仕様追加・挙動変更・バグ修正はリファクタではない。発見した場合は中断してユーザーに報告する
2. **テストの検証内容を変えない** — リファクタに伴う機械的な追随（import パス・関数名変更）のみ可。期待値・アサート内容の変更は禁止
3. **小さく刻む** — 1観点ずつ変更し、都度 `npm run test` で Green を確認する
4. **過剰な抽象化をしない** — 「将来使うかも」の抽象は導入しない。現在のコードの重複・不明瞭さの解消に限定する

## 実行手順

### Step 1: 前提確認

Green Phase 証拠（`_review/impl/green-phase-evidence.md`）の存在を確認する。なければ Phase 8 の完了を先に案内する。

### Step 2: リファクタ候補の洗い出し

#### 2-1. fallow による機械的な候補抽出（advisory）

対象が TypeScript / JavaScript プロジェクトの場合、静的解析ツール **fallow**（Rust 製・[fallow-rs/fallow](https://github.com/fallow-rs/fallow)）を実行し、リファクタ候補を機械的に洗い出す。**fallow の出力は参考情報（候補）であり、ゲートではない。** 採否は 2-2 の人手点検とあわせて最終的にユーザーが判断する。

```bash
npx fallow              # フル解析（dead code・重複・複雑度・循環依存をまとめて検出）
# 個別に確認したい場合：
npx fallow dupes        # 重複クローン（DRY 観点）
npx fallow dead-code    # 未使用 export / 循環依存
npx fallow health       # 複雑度スコア・ホットスポット
```

- **fallow 未導入・非 TS/JS プロジェクトの場合はこの 2-1 をスキップ**し、その旨を記録して 2-2 に進む（fallow の有無で Phase 9 をブロックしない）
- **本機能の変更ファイルに絞って注目する。** fallow は既存の無関係な負債も検出するが、リファクタは「現在のコードの重複・不明瞭さの解消」に限定する原則（前提4・振る舞い不変）に従い、今回のスコープ外の既存指摘は対象にしない
- **dead-code 指摘は鵜呑みにしない。** 新機能の公開 API・動的 import・テスト経由の利用を「未使用」と誤検出しうる。削除は 2-2 以降で人手判断し、Step 3 でテスト Green 維持を確認しながら行う

fallow の検出結果を、下記5観点にマッピングして候補一覧に反映する：

| fallow 検出 | 対応する観点 |
|---|---|
| dupes（重複クローン） | 重複削除（DRY） |
| health（複雑度ホットスポット） | 責務分離・抽象度の調整・可読性向上 |
| dead-code（未使用 export） | 可読性向上（不要コード削除） |
| circular（循環依存） | 抽象度の調整・責務分離 |

#### 2-2. 5観点による点検

フロー正典の5観点で対象コードを点検し、2-1 の fallow 候補とあわせて候補一覧をユーザーに提示する：

| 観点 | 例 |
|---|---|
| 重複削除（DRY） | テスト間・実装間のコピペロジック共通化 |
| 命名改善 | 意図が伝わらない変数名・関数名 |
| 責務分離 | Route Handler に混ざったビジネスロジックの切り出し |
| 抽象度の調整 | 過剰な間接層の削除／不足している関数分割 |
| 可読性向上 | ネスト解消・早期リターン・マジックナンバーの定数化 |

候補が無ければ（fallow・人手点検とも）「リファクタ不要」と判断し、その旨を記録して Step 5 に進む。

### Step 3: リファクタ実施

候補を1件ずつ適用し、都度 `npm run test` で Green 維持を確認する。FAIL したら直前の変更を戻す。

### Step 4: ゲート確認

Phase 8 と同じゲートを再実行する：

```bash
npm run test              # 全件 PASS
npm run test:integration  # ※該当テストがある場合
npm run lint
npm run check-types
npm run build
```

### Step 5: 記録と次フェーズ案内

`_review/impl/green-phase-evidence.md` に「Phase 9 リファクタ記録」節を追記する（fallow 実行有無、実施項目一覧 or スキップ理由、ゲート再確認の結果）。fallow を実行した場合は「検出→採用/見送りの内訳」も残す（見送りは理由を添える）。

```
Phase 9（リファクタ）が完了しました。
- fallow: 実行（検出 N 件 → 採用 M 件・見送り K 件）／ スキップ（理由: 非 TS/JS・未導入 等）
- 実施項目: N 件（<観点別の内訳>）／ スキップ（理由: <理由>）
- ゲート確認: 全テスト PASS 維持・lint / check-types / build PASS

次は Phase 10（実装検証：テスト・E2E 実行＋実装レビュー）です。
「実装を検証して」とお声がけください（flow-phase10-impl-review skill が起動します）。
```

## 禁止事項

- 振る舞いの変更・仕様の追加・バグ修正を混ぜない（発見時は中断して報告）
- テストの期待値・検証内容を変更しない
- Green を確認せずに複数の変更を積み重ねない
- Phase 8 の Green Phase 証拠なしで実行しない
- **fallow の検出結果をゲート扱いにしない**（Phase 9 のゲートは「全テスト Green 維持」のみ。fallow 指摘の有無で FAIL・差戻しにしない）
- **`fallow fix` で一括自動修正しない**（「小さく刻む・都度 Green 確認」の原則を崩さない。適用する候補は Step 3 の手順に乗せて1件ずつ検証する）
- fallow が検出した無関係な既存負債を今回のリファクタ対象に含めない（振る舞い不変・スコープ限定）

# Phase 10: 実装検証（テスト・E2E 実行＋実装レビュー・修正ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 10** を担当するスキル。品質保証の主役は**実行による証明**（全テスト＋E2E の実行）であり、レビューは実行では拾えない欠陥（仕様乖離・セキュリティ）に絞った最終確認として従の位置づけで行う。実装起因の問題は本 skill 内の修正ループ（fix-builder → 機械ゲート再実行 → 別レビュワーで再レビュー）で解消する。

**このフェーズの設計思想：** Phase 10 に到達した実装は、レビュー済み設計書（Phase 1-3）と独立レビュー済みのテスト（Phase 5-7）に挟まれており、テスト自体の品質が既に独立検証されている。そのため (1) 全テスト・E2E の実行を義務化して「動くことの機械的な証明」をゲートの主役にし、(2) レビューは `reviewer`（fresh context）で仕様忠実性とセキュリティだけを確認する。findings は Critical / Major / Minor の3段階で報告させるが、ゲート（修正ループの対象）は Critical / Major のみ。構造品質は Phase 9（リファクタ）の責務とする。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — Phase 10 のゲート条件と FAIL 時のフィードバックルーティング
2. 対象機能の設計書 — 「テストレベル判定」節（影響度トリガー・クリティカルパス E2E の該当有無）と受け入れ条件
3. Green Phase 証拠（`docs/設計/<機能名>/_review/impl/green-phase-evidence.md`）— Phase 8/9 の完了確認
4. （クリティカルパス E2E 該当時）Phase 5 で凍結した E2E シナリオ仕様（テスト観点表）
5. `docs/開発プロセス/テストレベル選定トリガー表.md` — トリガー判定の基準

## 重要な前提（必ず守ること）

1. **ゲートの主役は実行検証** — 司令塔（本skillの実行AI）自身がテスト・E2E・lint・build を実行して確認する。サブエージェントやワーカーの自己申告を根拠にしない
2. **Reviewer / Fix Builder は毎回 fresh context で起動する** — `reviewer` 役割・`fix-builder` 役割のサブエージェントを **毎回新規エージェントとして** 起動する。**同一インスタンスの使い回し禁止**：再レビューは前回のレビュワーとは別の新規エージェント、修正は Phase 8 の impl-builder とは別の新規エージェントが行う
3. **severity は Critical / Major / Minor の3段階** — Critical / Major は修正ループの対象（修正必須）。Minor は記録のみで通過可（対応は任意。命名・構造・別解提案は原則 Minor 扱いで判定に使わない）
4. **findings の disk 書き出しは司令塔が担当する** — Reviewer は findings を最終応答テキストとして返却し、司令塔が `_review/impl/findings.md` に Write する
5. **修正は fix-builder に委譲する** — 司令塔がメイン会話で実装を直接修正しない。fix-builder には「テストファイル変更禁止・指定 findings のみ修正（デグレ防止）」を課す（役割ファイルで担保）
6. **設計書・テスト起因の問題はループで解消しない** — 実装側で解消できない問題（仕様の曖昧性・テストの不備）はフィードバックルーティングで戻り先フェーズを特定し、ユーザーに判断を仰ぐ
7. **ループの安全弁** — 修正 → 再検証 → 再レビューのサイクルは **最大3回** まで。超えたら残 findings と経緯をユーザーに報告して判断を仰ぐ

## 実行手順

### Step 1: 前提確認とレビュー対象の特定

- Green Phase 証拠の存在を確認する（なければ Phase 8 の完了を先に案内）。Phase 9 実施時はリファクタ記録も確認
- 設計書「テストレベル判定」節から、影響度トリガー該当有無・クリティカルパス E2E 該当有無を確認する
- 対象を特定する：実装ファイル（Route Handler・`_lib`・型定義等）、テストファイル、設計書のパス一覧

### Step 2: E2E コード化（クリティカルパス該当時のみ）

Phase 5 で凍結した E2E シナリオ仕様（操作手順・期待結果）を、Playwright コード（`tests/<機能名>.spec.ts`）に書き起こす。

- **凍結済み仕様（操作手順・期待結果）の改変は禁止。** 実装の実際の挙動に合わせて期待結果を変えたくなった場合、それは仕様と実装の乖離である。コード化を中断してユーザーに報告する
- セレクタ・待機条件など技術詳細のみ、実装された実際の DOM に合わせて記述する
- クリティカルパス非該当の機能ではこの Step をスキップし、その旨を Step 5 の証拠に記録する

### Step 3: 実行検証（機械ゲート・司令塔の責務）

司令塔自身が以下をすべて実行する：

```bash
npm run test              # 単体 + 結合（内部）全件 PASS
npm run test:integration  # 結合（DB込み）全件 PASS ※該当テストがある場合
npm run lint              # ESLint PASS
npm run check-types       # 型チェック PASS（作業範囲外エラーは報告のみ）
npm run build             # ビルド成功
npm run test:e2e          # E2E 全件 PASS ※下記
```

**E2E の実行対象：** (a) Step 2 でコード化した当該機能の E2E、(b) 既存の自動化済み E2E 全件（クリティカルパス常設スイート＝E2E リグレッション）。E2E 基盤未整備・自動化済みシナリオが存在しない場合は「対象なし」として証拠に明記する。

**テスト無改変確認：** `git diff -- <テストファイルパス>` が空であること（テスト承認時点から変更なし）。変更されていた場合は重大な違反として即座にユーザーへ報告する。

**実行検証に FAIL がある場合：** 失敗原因を仕分けする。**実装起因（実装バグ）**なら Step 6 の修正ループへ（レビュー Step 4 は初回の修正ループ収束後に実施）。**テスト・設計書起因**なら Step 5 で証拠を記録して Step 7 のフィードバックルーティングへ。

### Step 4: 実装レビュー（reviewer・fresh context）

`reviewer` 役割のサブエージェントを fresh context として起動する（起動方法は末尾「補足」参照）。

**プロンプトに含める内容：**

- （汎用サブエージェント起動の場合）役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- 実装ファイル・テストファイル・設計書の絶対パス
- 影響度トリガー該当有無（設計書「テストレベル判定」節の判定結果）
- レビューモード：「初回（フルレビュー）」
- レビュー観点：**仕様忠実性・セキュリティの2観点**（下記）
- findings は **Critical / Major / Minor の3段階**で報告すること。命名・コードスタイル・構造の好み・別解提案は原則 Minor（ゲート対象外）であること
- **findings は最終応答テキストとして返却することを明記**

**Reviewer に伝えるレビュー観点（2つ）：**

1. **仕様忠実性** — 実装が設計書の要件・受け入れ条件を過不足なく実現しているか。テストが検証していない受け入れ条件について実装が仕様と乖離している箇所はないか。設計書にない挙動（勝手な仕様追加・暗黙のスコープ拡大）はないか
2. **セキュリティ** — 認可境界（他ユーザー・他社データへのアクセス可否、where 句の絞り込み漏れ）／PII の露出（レスポンス・ログへの混入）／インジェクション（SQL・XSS・コマンド・パストラバーサル）／N+1 等、現実の利用規模で顕在化する性能欠陥。影響度トリガー該当機能は重点的・網羅的に確認する

### Step 5: 証拠と findings の記録（司令塔の責務）

**1. 実行検証の証拠** を `docs/設計/<機能名>/_review/impl/verification-evidence.md` に保存：

```markdown
# Phase 10 実行検証証拠（第N回）

- 機能：<機能名>
- 実施日時：<YYYY-MM-DD HH:MM>
- 実行者：司令塔（独立実行）

## 実行検証結果

| チェック | コマンド | 結果 |
|---|---|---|
| 単体 + 結合（内部） | `npm run test` | PASS（N tests） |
| 結合（DB込み） | `npm run test:integration` | PASS / 対象なし |
| Lint | `npm run lint` | PASS |
| 型チェック | `npm run check-types` | PASS |
| ビルド | `npm run build` | PASS |
| E2E（当該機能） | `npm run test:e2e` | PASS（N scenarios）/ 対象なし（クリティカルパス非該当） |
| E2E（常設スイート） | `npm run test:e2e` | PASS（M scenarios）/ 対象なし（自動化済みシナリオなし） |
| テスト無改変 | `git diff -- <テストパス>` | 変更なし |

## E2E コード化の記録

- コード化したシナリオ：<一覧> / 対象なし（理由）
- 凍結仕様との差異：なし（あれば中断・報告済みのはず）
```

**2. レビュー結果** を `docs/設計/<機能名>/_review/impl/findings.md` に保存する。修正ループの2周目以降・再実行時は前回分を上書きせず「第N回」として追記する。Minor findings は「Minor（ゲート対象外・記録のみ）」節として分離して記録し、判定に使わない。

### Step 6: 判定と修正ループ

**総合 PASS の条件：** 実行検証（Step 3）すべて PASS、かつレビューの Critical / Major が 0 件。

**総合 PASS の場合** → Step 7（完了通知）へ。

**実行検証 FAIL（実装起因）またはレビューの Critical / Major が 1 件以上の場合** → 以下の修正ループを実行する：

1. **原因の仕分け（司令塔）**：失敗・findings のうち実装側で解消できないもの（仕様の曖昧性・要件不足・テストの不備に起因するもの）があれば、ループに含めず Step 7 のフィードバックルーティングでユーザーに判断を仰ぐ。実装側で解消できるもののみループに進む
2. **fix-builder の起動（fresh context）**：`fix-builder` 役割のサブエージェントを新規起動する。プロンプトに含める内容：
   - 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
   - 成果物種別：**実装コード（Green Phase 後）**
   - 修正対象：実行検証の失敗内容（失敗ログ・該当テスト）および findings（Critical / Major の全文。Minor は渡さない）
   - 実装ファイル・テストファイル・設計書・AGENTS.md の絶対パス
   - **テストファイルの変更禁止**、**指定 findings・失敗の解消に必要な最小限の変更のみ（デグレ防止）** を明記
3. **機械ゲートの再実行（司令塔）**：fix-builder の完了報告後、司令塔が Step 3 の実行検証を**全件**再実行する。`git diff` で修正差分が findings・失敗の範囲に収まっていること、テストファイルが無改変であることを検証する。証拠を「第N回」として記録する
4. **再レビュー（別の fresh context の Reviewer）**：`reviewer` 役割のサブエージェントを**新規に**起動する。プロンプトに含める内容：
   - レビューモード：「再レビュー」
   - 前回 findings（Critical / Major）の一覧と、修正差分の範囲（変更ファイル）
   - 「前回 findings の解消確認＋修正差分に混入した新規欠陥の検出に限定。修正されていない箇所への新規のフル指摘はしない」ことを明記
5. 再レビューの findings を Step 5 の要領で「第N回」として追記し、本 Step の判定に戻る

**ループ上限**：修正サイクルは最大3回。超えたら残 findings・経緯・推奨対応をユーザーに報告して判断を仰ぐ。

**再発防止の記録**：修正ループで解消した Critical のうち「テストで再発防止すべきもの」（テストの網が拾えなかった仕様乖離・セキュリティ欠陥）があれば、完了通知にその旨を含め、Phase 5 へのテスト追加をユーザーに提案する（テストの追加は本 skill 内では行わない）。

### Step 7: 完了通知・フィードバックルーティング

**総合 PASS の場合：**

```
Phase 10（実装検証）が完了しました。総合判定: PASS
- 実行検証: 全テスト PASS ／ E2E PASS（当該機能 N・常設スイート M）／ テスト無改変
- レビュー・修正ループ: N 回で収束（Critical 0 件・Major 0 件・Minor N 件）
- 証拠: _review/impl/verification-evidence.md, findings.md
- （あれば）テスト追加の提案: <再発防止すべき findings の一覧>

10フェーズフローはこれで完了です。PR 作成に進めます（E2E は本フェーズで実行済み）。
```

**実装側で解消できない問題（設計書・テスト起因）がある場合：** 種類ごとに戻り先を特定してユーザーに提示する（フロー正典のルーティング表）：

| 失敗・findings の種類 | 戻り先 |
|---|---|
| 仕様の曖昧性・要件不足に起因する乖離 | Phase 1（設計書作成） |
| エッジケースの欠落 | Phase 1 + Phase 5 |
| テストの不備（テストが仕様を表現できていない） | Phase 5（テスト作成） |
| （参考）実装バグ・実装の仕様乖離・セキュリティ欠陥 | 本 skill 内の修正ループで解消済みのはず。ループ上限到達分はユーザー判断 |

```
Phase 10（実装検証）の結果、実装側では解消できない問題が見つかりました。
- 実行検証: <結果サマリー> ／ レビュー: Critical N 件・Major N 件（うち実装側で解消済み M 件）
- 戻り先の提案: <項目・FIND-ID ごとの戻り先一覧>

修正方針をご判断ください。修正後、「Phase 10 を再実行」で差分検証します。
```

## 禁止事項

- **実行検証を省略してレビューだけで PASS にしない**（テスト・E2E の実行がこのフェーズの主役）
- Reviewer / fix-builder をメイン会話のAIとして実行しない（必ず fresh context のサブエージェントとして起動）
- **再レビューに前回と同一のレビュワーインスタンスを使わない**（毎回新規起動）
- Reviewer に Write を強要しない（findings 書き出しは司令塔の責務）
- 司令塔がメイン会話で実装を直接修正しない（修正は fix-builder に委譲）
- E2E の凍結済み仕様（操作手順・期待結果）を実装の挙動に合わせて改変しない（乖離発見時は中断・報告）
- 修正ループ内でテストファイルを変更しない（テスト起因の問題はフィードバックルーティングでユーザー判断）
- Critical / Major を残したまま PASS にしない（ループ上限到達時はユーザー判断を仰ぐ）
- Minor findings を修正ループ・判定に含めない（記録のみ）
- Green Phase 証拠なしで開始しない
- 再レビュー時にフルレビューをやり直して新規の指摘を積み増さない（解消確認＋修正差分に限定）

## 補足：Reviewer / Fix Builder の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/reviewer.md`・`flow-agent-roles/roles/fix-builder.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・出力形式に完全に従うこと」を指示する。Reviewer の読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

# Phase 10: 実装検証（テスト・E2E 実行＋実装レビュー・収束ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 10** を担当するスキル。品質保証の主役は**実行による証明**（全テスト＋E2E の実行）であり、レビューは実行では拾えない欠陥（仕様乖離・セキュリティ・テストのすり抜け）に絞った最終確認として行う。

**本フェーズの設計思想（2026-08-12 改訂）：** 2026-07-20 改訂では所要時間を削るためにレビューを「通常較正」に変更したが、その結果**不具合の見落とし**が発生した（実走で確認済み）。原因は「探索の較正（どれだけ疑って読むか）」と「報告の閾値（何を findings に載せるか）」という別の2軸をまとめて下げたことにある。本改訂では次のように分離する：

- **探索の較正は敵対的に戻す**（欠陥を能動的に探し、反証として読む）
- **報告の閾値は Critical / Major のまま据え置く**（命名・構造・スタイル・別解提案は報告しない。構造品質は Phase 9 の責務）
- **所要時間は観点レーンの並列化・出力予算・差分レビューで抑える**（`flow-review-policy` 2章「較正不変の原則」）

さらに、テスト全件 PASS をすり抜ける欠陥を探す専用レーン（レーン C）を新設した。「テストが通っている」ことを根拠に安心してはならない。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — Phase 10 のゲート条件と FAIL 時のフィードバックルーティング
2. `flow-review-policy` skill（本 skill と同じ skills ディレクトリ内。絶対パスに解決して読む）— **較正不変の原則・観点レーン分割・出力予算・must-catch・収束ループの正本**
3. `docs/設計/<機能名>/_flow-config.md` — フロー設定（**実装承認ゲートの実施要否**・運用モード・レーン並列・収束ループ上限）
4. 対象機能の設計書 — 「テストレベル判定」節（影響度トリガー・クリティカルパス E2E の該当有無）と受け入れ条件
5. Green Phase 証拠（`docs/設計/<機能名>/_review/impl/green-phase-evidence.md`）— Phase 8/9 の完了確認
6. （クリティカルパス E2E 該当時）Phase 5 で凍結した E2E シナリオ仕様（テスト観点表）
7. `docs/開発プロセス/テストレベル選定トリガー表.md` — トリガー判定の基準

## 重要な前提（必ず守ること）

1. **ゲートの主役は実行検証** — 司令塔（本skillの実行AI）自身がテスト・E2E・lint・build を実行して確認する。サブエージェントやワーカーの自己申告を根拠にしない
2. **レビューは `impl-reviewer` 役割で、敵対的較正・Critical/Major 報告で行う** — 探索は徹底的に、報告は絞る。命名・構造・スタイル・別解提案は報告対象外（役割ファイルで担保）。fresh context 起動・Read 専用は従来どおり
3. **観点はレーンに分割して並列起動する** — 既定は3レーン（Step 4）。**同一メッセージ内でまとめて起動して並列に走らせる**。並列起動できない環境では `_flow-config.md` の設定を無効にし、1エージェントに全観点を渡す（較正は下げない）
4. **findings の disk 書き出しは司令塔が担当する** — Reviewer は findings を最終応答テキストとして返却し、司令塔が `_review/impl/findings.md` に Write する
5. **収束するまでループする** — 実行検証の失敗と Critical/Major がゼロになるまで「修正 → 差分再検証」を繰り返す（Step 6）。実装の修正は **`impl-builder` を fresh context で再起動して行わせる**（司令塔が実装コードを直接書かない）。**テストは誰も変更しない**
6. **戻り先が Phase 1 / 5 の findings は人間へエスカレーションする** — 承認済み設計書・テストの変更は人間の判断事項。実装承認ゲートをスキップする設定でもこの扱いは変わらない

## 実行手順

### Step 1: 前提確認とレビュー対象の特定

- Green Phase 証拠の存在を確認する（なければ Phase 8 の完了を先に案内）。Phase 9 実施時はリファクタ記録も確認
- `_flow-config.md` を読み、**実装承認ゲートの実施要否**・運用モード・レーン並列・収束ループ上限（既定5周）を把握する
- 設計書「テストレベル判定」節から、影響度トリガー該当有無・クリティカルパス E2E 該当有無を確認する
- 対象を特定する：実装ファイル（Route Handler・`_lib`・型定義等）、テストファイル、設計書のパス一覧

### Step 2: E2E コード化（クリティカルパス該当時のみ）

Phase 5 で凍結した E2E シナリオ仕様（操作手順・期待結果）を、Playwright コード（`tests/<機能名>.spec.ts`）に書き起こす。

- **凍結済み仕様（操作手順・期待結果）の改変は禁止。** 実装の実際の挙動に合わせて期待結果を変えたくなった場合、それは仕様と実装の乖離である。コード化を中断してユーザーに報告する
- セレクタ・待機条件など技術詳細のみ、実装された実際の DOM に合わせて記述する
- クリティカルパス非該当の機能ではこの Step をスキップし、その旨を Step 5 の証拠に記録する

### Step 3: 実行検証（機械ゲート・司令塔の責務）

司令塔自身が以下をすべて実行する：

```bash
npm run test              # 単体 + 結合（内部）全件 PASS
npm run test:integration  # 結合（DB込み）全件 PASS ※該当テストがある場合
npm run lint              # ESLint PASS
npm run check-types       # 型チェック PASS（作業範囲外エラーは報告のみ）
npm run build             # ビルド成功
npm run test:e2e          # E2E 全件 PASS ※下記
```

**E2E の実行対象：** (a) Step 2 でコード化した当該機能の E2E、(b) 既存の自動化済み E2E 全件（クリティカルパス常設スイート＝E2E リグレッション）。E2E 基盤未整備・自動化済みシナリオが存在しない場合は「対象なし」として証拠に明記する。

**テスト無改変確認：** `git diff -- <テストファイルパス>` が空であること（Phase 7 承認／Phase 6 収束の時点から変更なし）。変更されていた場合は重大な違反として即座にユーザーへ報告する。

**実行検証に FAIL がある場合：** Step 4（レビュー）に進まず、Step 5 で証拠を記録して Step 6 の収束ループへ入る（実装バグの修正が先。レビューは修正後の実装に対して行う）。

### Step 4: 実装レビュー（impl-reviewer・レーン並列・fresh context）

`impl-reviewer` 役割のサブエージェントを、**レーンごとに fresh context で並列起動する**（起動方法は末尾「補足」参照）。

**既定のレーン割り（`flow-review-policy` 3.2）：**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: 仕様忠実性 | 実装が設計書の要件・受け入れ条件を過不足なく実現しているか／テストが検証していない受け入れ条件で仕様と乖離している箇所／設計書にない挙動（勝手な仕様追加・暗黙のスコープ拡大） | MC-8 |
| B: セキュリティ | 認可境界（他ユーザー・他社データ、where 句の絞り込み漏れ、ID 直接指定）／PII の露出（レスポンス・ログ・エラー）／インジェクション（SQL・XSS・コマンド・パストラバーサル）／N+1 等、現実の利用規模で顕在化する性能欠陥 | MC-2・MC-3 |
| C: テストのすり抜け | **テスト全件 PASS でもすり抜ける欠陥**：テストが検証していない分岐・エラー経路・例外時の副作用・状態遷移・並行/競合・リソース解放漏れ・外部呼び出し失敗時のフォールバック | MC-7・MC-9 |

**各レーンのプロンプトに含める内容：**

- 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- 実装ファイル・テストファイル・設計書の絶対パス
- 影響度トリガー該当有無（設計書「テストレベル判定」節の判定結果）
- **担当レーンの観点のみ**を敵対的較正（欠陥を能動的に探し、反証として読む）で深く見ること
- 担当する **must-catch 項目**
- **報告は Critical / Major のみ**であること（役割ファイルの報告閾値に従う。探索は徹底、報告は絞る）
- **出力予算**：Critical / Major はフル記述（失敗シナリオを1文で必須）、PASS の裏付けは1〜2行
- **findings は最終応答テキストとして返却することを明記**
- 再実行（Round 2 以降）の場合：前回 findings の一覧と修正差分の範囲を渡し、「解消確認＋差分の新規欠陥＋must-catch」に限定することを指示する

**レーン C に伝える追加指示：** 「このコードは全テストが PASS している。**テストが通っていることを安心の根拠にしてはならない。**あなたの仕事は、テストが見ていない経路を特定し、そこに欠陥がないかを確認することである。まずテストがカバーしている経路を把握し、次に実装のうち**テストが一度も通っていない分岐・例外経路**を列挙してから、そこを重点的に読むこと。」

### Step 5: 証拠と findings の記録（司令塔の責務）

**1. 実行検証の証拠** を `docs/設計/<機能名>/_review/impl/verification-evidence.md` に保存（Round ごとに追記）：

```markdown
# Phase 10 実行検証証拠（Round N）

- 機能：<機能名>
- 実施日時：<YYYY-MM-DD HH:MM>
- 実行者：司令塔（独立実行）

## 実行検証結果

| チェック | コマンド | 結果 |
|---|---|---|
| 単体 + 結合（内部） | `npm run test` | PASS（N tests） |
| 結合（DB込み） | `npm run test:integration` | PASS / 対象なし |
| Lint | `npm run lint` | PASS |
| 型チェック | `npm run check-types` | PASS |
| ビルド | `npm run build` | PASS |
| E2E（当該機能） | `npm run test:e2e` | PASS（N scenarios）/ 対象なし（クリティカルパス非該当） |
| E2E（常設スイート） | `npm run test:e2e` | PASS（M scenarios）/ 対象なし（自動化済みシナリオなし） |
| テスト無改変 | `git diff -- <テストパス>` | 変更なし |

## E2E コード化の記録

- コード化したシナリオ：<一覧> / 対象なし（理由）
- 凍結仕様との差異：なし（あれば中断・報告済みのはず）
```

**2. レビュー結果** を `docs/設計/<機能名>/_review/impl/findings.md` に保存する。各レーンの応答は `flow-review-policy` 3.3 のマージ規則で統合する（重複統合・severity は高い方・矛盾は両論併記・**要約や軟化や削除はしない**）。Round 2 以降は前回分を上書きせず「Round N」として追記する。Reviewer が報告閾値外の指摘（Minor・スタイル等）を返してきた場合は、findings 本文と分離して「参考（ゲート対象外）」節に記録し、判定に使わない。

各 finding には**戻り先**（Phase 8 実装 / Phase 5 テスト / Phase 1 設計書）を必ず付す。

### Step 6: 収束ループ（実行検証 PASS かつ Critical / Major ゼロまで）

**収束条件：実行検証（Step 3）が全項目 PASS、かつ Critical 0 件 かつ Major 0 件。**

収束していない場合、次を繰り返す：

1. **失敗・findings の仕分け**（フロー正典のルーティング表に従う）

   | 失敗・findings の種類 | 戻り先 | ループ内で解消できるか |
   |---|---|---|
   | テスト・E2E の実行失敗（実装バグ） | Phase 8（実装） | ✅ できる |
   | 実装の仕様乖離・セキュリティ欠陥 | Phase 8（実装） | ✅ できる |
   | lint / 型 / build の失敗 | Phase 8（実装） | ✅ できる |
   | テストの不備（テストが仕様を表現できていない） | Phase 5（テスト） | ❌ 人間へエスカレーション |
   | エッジケースの欠落 | Phase 1 + Phase 5 | ❌ 人間へエスカレーション |
   | 仕様の曖昧性・要件不足に起因する乖離 | Phase 1（設計書） | ❌ 人間へエスカレーション |
   | E2E 凍結仕様と実装挙動の乖離 | 人間判断（仕様か実装かの決定） | ❌ 人間へエスカレーション |

2. **`impl-builder` の再起動による修正**（司令塔は実装コードを書かない。**テストは変更しない・させない**）
   - 役割ファイル（`flow-agent-roles/roles/impl-builder.md`）の絶対パス
   - 解消すべき失敗・findings（FIND-ID・失敗シナリオ・推奨対応）
   - 「テストファイルの変更は禁止。テストと設計書の矛盾を発見した場合は修正せず中断して報告すること」
3. **差分再検証（Round N+1）**
   - **実行検証（Step 3）は毎回全件実行する**（差分化しない。リグレッションの検出が目的のため）
   - **レビューは差分レビュー**（`flow-review-policy` 4.4）：前回 findings の解消確認＋修正差分の新規欠陥＋must-catch チェック
   - 例外：修正が広範囲に波及した場合は、司令塔の判断でフルレビュー（3レーン並列）に戻してよい
4. 収束するまで 1〜3 を繰り返す

**ループを抜けて人間へ即エスカレーションする条件（`flow-review-policy` 4.3）：** 上表の「❌」に該当する findings が出た／スコープ拡大／同一 finding が2周連続で未解消・振動／収束ループ上限（既定5周）到達。

**収束ログ** は `docs/設計/<機能名>/_review/impl/review-log.md` に `flow-review-policy` 4.5 の様式で記録する。

### Step 7: 判定・完了通知（実装承認ゲート）

**実装承認ゲート「実施」の場合：**

```
Phase 10（実装検証）が収束しました。総合判定: PASS
- 実行検証: 全テスト PASS ／ E2E PASS（当該機能 N・常設スイート M）／ lint・型・build PASS ／ テスト無改変
- レビュー: 敵対的較正・3レーン並列（仕様忠実性 / セキュリティ / テストのすり抜け）
- 収束: Round N で Critical 0・Major 0
- 証拠: _review/impl/verification-evidence.md, findings.md, review-log.md

次は実装承認ゲート（人間レビュー）です。
証拠と findings をご確認の上、以下のいずれかをお伝えください：
  - 「実装を承認します」 → 10フェーズフロー完了・PR 作成へ
  - 「<指摘内容>を直して」 → 該当フェーズへ差し戻し
```

**実装承認ゲート「スキップ」の場合：**

```
Phase 10（実装検証）が収束しました。総合判定: PASS
- 実行検証: 全テスト PASS ／ E2E PASS（当該機能 N・常設スイート M）／ lint・型・build PASS ／ テスト無改変
- レビュー: 敵対的較正・3レーン並列。Round N で Critical 0・Major 0
- 証拠: _review/impl/verification-evidence.md, findings.md, review-log.md

フロー設定により実装承認ゲート（人間レビュー）はスキップします。
収束をもって完了とし、findings.md に「実装承認: スキップ（フロー設定）／収束をもって承認」を記録しました。

10フェーズフローはこれで完了です。PR 作成に進めます（E2E は本フェーズで実行済み）。
```

**エスカレーションした場合（設定によらず人間へ）：**

```
Phase 10 の収束ループを中断しました（理由: <上限到達 / 振動 / 戻り先が Phase 1・5 / スコープ拡大>）。
- 実行検証: <状況> ／ 残 findings: Critical N 件・Major N 件
- 戻り先の提案: <FIND-ID ごとの戻り先一覧>
- 各周で試みた修正: <要約>
- 司令塔の見立て: <原因の仮説と対応案>

修正方針をご判断ください。テスト・設計書の変更が必要な場合は Phase 5 / Phase 1 へ差し戻します。
```

## 禁止事項

- **実行検証を省略してレビューだけで PASS にしない**（テスト・E2E の実行がこのフェーズの主役）
- **較正を下げて時間短縮しない**（「批判的観点を外す」「観点を減らす」等。短縮は分割・並列化・出力粒度・差分レビューで行う。**過去にこの禁を破って見落としが発生している**）
- **報告閾値を緩めない**（Minor・命名・構造・スタイル・別解提案は findings に載せない。ゲートのノイズになる）
- must-catch チェック（特に MC-7 テストのすり抜け）を差分レビューを理由に省略しない
- Reviewer をメイン会話のAIとして実行しない（必ず fresh context のサブエージェントとして起動）
- Reviewer に Write を強要しない（findings 書き出しは司令塔の責務）
- 各レーンの指摘を司令塔が要約・軟化・削除しない
- **司令塔が実装コードを直接修正しない**（修正は `impl-builder` を fresh context で再起動）
- **テストファイルを変更しない・させない**（不備発見時は中断して人間へ）
- E2E の凍結済み仕様（操作手順・期待結果）を実装の挙動に合わせて改変しない（乖離発見時は中断・報告）
- **1回の検証で打ち切らない**（実行検証 FAIL または Critical/Major が残った状態で完了としない）
- **実装承認ゲートをスキップする機能で、AI の判断により Major を「文書化のみで通過」にしない**
- 戻り先が Phase 1 / 5 の findings を、実装側の小手先修正で潰さない（人間へエスカレーション）
- Green Phase 証拠なしで開始しない

## 補足：Reviewer の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/impl-reviewer.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。修正時のワーカーは `flow-agent-roles/roles/impl-builder.md`。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・報告閾値・出力形式に完全に従うこと」を指示する。読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。**レーン並列時は、レーンごとに別のサブエージェントを同一メッセージ内でまとめて起動する。**

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

# flow-kickoff: 開発開始の受付（要件の受け取りとフロー設定）

10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の**前段**を担当する skill。要件が固まっていない状態で設計・実装に突入することを防ぎ、Phase 1 の入力となる**要件メモ**と、フロー全体の挙動を決める**フロー設定（`_flow-config.md`）**を整えるのが責務。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典
2. `flow-review-policy` skill（同じ skills ディレクトリ内。絶対パスに解決して読む）— フロー設定（`_flow-config.md`）の様式・人間レビューをスキップした場合の代償措置の正本

**Phase 8 との混同に注意：** 「実装したい」という言葉が含まれていても、設計書・承認済みテストがまだ存在しない**新規開発の開始合図**は本 skill が受ける。`flow-phase8-impl`（「実装して」）は Phase 7 承認済みのテストを通す実装フェーズであり、別物。

## 実行手順

### Step 1: 要件の提示を求める

ユーザーに対象機能の要件を提示してもらう。形式は自由（箇条書きメモ・利用フロー・画面モック・既存資料のパス等）。何を出せばよいか迷わないよう、最低限の例を添える：

- 何を実現したいか（目的）
- 誰が使うか（利用者）
- 主な操作・画面のイメージ
- やらないこと（分かっていれば）

依頼文にすでに要件が含まれている場合は、その内容を要約して確認し、Step 2 へ進む。

### Step 2: フロー設定の決定（人間レビューの要否）— 本 skill の必須ステップ

**この機能の開発でどこに人間の承認ゲートを置くかを、開発を始める前に決める。**フェーズの途中で都度尋ねるのではなく、ここで一度決めて `docs/設計/<機能名>/_flow-config.md` に記録し、以後すべてのフェーズがこの設定を読んで挙動を変える。

ユーザーに次の2点を選択させる（`AskUserQuestion` 等でまとめて提示してよい）：

1. **テスト承認ゲート（Phase 7）** — 実施 / スキップ
   - 「実施」：Phase 6 のレビュー収束後、テスト内容を人間が確認して承認する。Phase 5 のテスト観点表（影響度トリガー該当分）は**人間が本記載**する
   - 「スキップ」：Phase 5 のテスト観点は **AI が全件起案**し（`flow-review-policy` 1.5 のチェックリストを足場にする）、Adversary の敵対的レビューで Critical/Major ゼロまで収束させてから凍結する。Phase 6 も Critical/Major の完全ゼロ化が必須になる
2. **実装承認ゲート（Phase 10 完了時）** — 実施 / スキップ
   - 「実施」：Phase 10 の収束後、実行検証証拠と findings を人間が確認して完了とする
   - 「スキップ」：Phase 10 の収束（実行検証すべて PASS ＋ Critical/Major ゼロ）をもって完了とする

**設計書承認ゲート（Phase 3）は選択肢に含めない。**「何を作るか」の判断は人間にしか帰属しないため実施固定である。この点は選択を求める際にあわせて説明する。

あわせて、この機能の**運用モード**（厳格 / lean）を確認する（判断材料がなければ既定は lean。プロトタイプ・MVP 検証なら lean、safety-critical なら厳格）。

選択結果を `flow-review-policy` 1.6 の様式に従って `docs/設計/<機能名>/_flow-config.md` に保存する（フォルダがなければ作成する）。**このファイルは Phase 1 で作成する設計書と同じフォルダに置く。**フォルダ名（機能名）を後で変更する場合は、設定ファイルも一緒に移動する。

保存後、決定内容をユーザーに1〜3行で確認提示してから Step 3 へ進む。

### Step 3: 深掘り（grilling）の要否をユーザーに選択させる

提示された要件に対して、次の選択肢を提示して**ユーザーに選ばせる**（勝手に深掘りを始めない）：

1. **grilling で深掘りする**（推奨：要件が粗い・新規性が高い・影響範囲が読めない場合）→ Step 4 へ
2. **深掘りせずこのまま進む** → Step 5 へ

**人間レビューをスキップする設定を選んだ場合は、深掘りの実施を強く推奨する。**後段の人間ゲートが減る分、要件の取り違えを検出できる最後の砦が Phase 3（設計書承認）だけになるため、その入力となる要件メモの精度が品質を左右する。

### Step 4: grilling による深掘り（選択時のみ）

提示された要件を対象に `grilling` skill を起動し、前提・スコープ・受け入れ条件の種を質問攻めで掘り起こす。

**grilling skill が未導入の場合**：その旨と導入コマンドを案内する：

```bash
npx skills add https://github.com/mattpocock/skills --skill grilling
```

導入せずに進む場合は、grilling の手法に準拠した**簡易深掘り（フォールバック）**を司令塔自身が実施する。

**進め方の原則（grilling 準拠）：**

- 提示された要件の**あらゆる側面について、共通理解に達するまで徹底的に質問する**。設計判断の木を枝ごとに辿り、判断同士の依存関係を1つずつ解決していく
- **質問は必ず1問ずつ**提示し、回答を待ってから次に進む。複数の質問を同時に投げることは混乱のもとであり禁止
- **各質問には自分の推奨回答を理由付きで添える**（例：「私のおすすめは○○です。理由は△△だからです。いかがですか？」）
- **コードベースを調べれば分かる事実は、質問せず自分で調べる**。ただし**判断はユーザーのもの** — 判断が必要な点は必ず1つずつユーザーに問い、回答を待つ
- **ユーザーが「共通理解に達した」と確認するまで、次の Step（要件メモ化）に進まない**
- **人間レビューをスキップする設定の場合は、受け入れ条件の種を特に厚く掘る**（Phase 5 で AI がテスト観点を起案する際の根拠になるため）

**質問の起点となる枝（ここから回答に応じて依存関係を辿り、深掘りする）：**

1. 目的 — なぜこの機能が必要か。何が解決されれば成功か
2. 利用者 — 誰が・どんな頻度で使うか
3. 主要ユースケース — 代表的な操作の流れ。例外的な流れはあるか
4. スコープ外 — やらないこと。将来に回すこと
5. 受け入れ条件の種 — 「できた」をどう判定するか（テストで検証できる形の候補）
6. 既存機能への影響 — 変更・共存が必要な既存機能はあるか（コードベースで確認できる事実は自分で調べたうえで、判断だけを問う）

### Step 5: 要件メモの整理と保存

深掘り結果（または提示された要件そのまま）を以下の構成で整理し、ユーザーに内容を確認してもらってから `docs/要件/<機能名>_要件メモ.md` に保存する：

```markdown
# <機能名> 要件メモ

- 作成日: YYYY-MM-DD
- 深掘り: grilling 実施 / 簡易深掘り実施 / なし（提示のまま）

## 目的・背景
## 利用者
## 主要ユースケース
## スコープ外（やらないこと）
## 受け入れ条件の種
## 未決事項
## 参考資料
```

- ユーザーが明言していないことを発明して書かない。未確認の点は「未決事項」に置く
- 未決事項は Phase 1〜3 で解消される前提でよい（ここで全部を確定させようとしない）

### Step 6: 完了通知と次フェーズ案内

```
開発開始の受付が完了しました。
- 要件メモ: docs/要件/<機能名>_要件メモ.md
- フロー設定: docs/設計/<機能名>/_flow-config.md
  - 設計書承認（Phase 3）: 実施（固定）
  - テスト承認（Phase 7）: 実施 / スキップ
  - 実装承認（Phase 10 完了時）: 実施 / スキップ
  - 運用モード: 厳格 / lean
- 深掘り: <実施内容>
- 未決事項: N 件（Phase 1〜3 で解消します）

次は Phase 1（設計書作成）です。
「<機能名>の設計書を作って」とお声がけください（flow-phase1-design-doc が起動します）。
```

## 禁止事項

- 要件の提示を受けずに設計・実装フェーズへ進まない
- **フロー設定（`_flow-config.md`）を作らずに Phase 1 へ引き継がない**
- **設計書承認ゲート（Phase 3）をスキップする選択肢を提示しない**（実施固定）
- 人間レビューの要否をユーザーに確認せず AI が勝手に決めない
- 深掘りの要否をユーザーに確認せず勝手に grilling を始めない
- 要件メモにユーザーが言っていないことを発明して書かない
- 本 skill 内で設計書を書き始めない（Phase 1 の責務）
- 「実装したい」という言葉だけを根拠に `flow-phase8-impl` を起動しない（承認済みテストがない場合は本 skill が受ける）

# Phase 6: テストレビュー（レビュー・修正ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 6** を担当するスキル。Phase 5 で作成されたテストファイルを、司令塔（メイン会話のAI）と分離された **fresh context** の `reviewer` サブエージェントがレビューし、Critical / Major の findings があれば **fresh context の `fix-builder`**（Phase 5 の test-builder とは別インスタンス）が修正 → **別の fresh context の `reviewer`** が再レビュー、を Critical / Major が 0 件になるまで繰り返す。

**このフェーズの存在理由：** AIは「テストを先に書いて、後で実装をテストに合わせる」が起きやすい。また作成者は自分が書いたテストの脆弱性（特にトートロジー）に構造的に気付けない。テスト段階で独立レビューすることで、「テストが仕様を正しく表現していない」を実装前に検出する。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典。Phase 6 の位置づけとゲート観点を理解する
2. `docs/開発プロセス/フロー運用設定.md` — Phase 7（人間承認）の要否設定（存在しない場合は「承認必要」として扱う）
3. 対象機能の設計書（`docs/設計/<機能名>/<機能名>_設計書.md`）— 受け入れ条件との対応チェックの基準
4. 対象機能の実装計画書（あれば）— テストケースリストとの対応チェックの基準
5. Red Phase 証拠（`docs/設計/<機能名>/_review/test/red-phase-evidence.md`）— Red Phase の成立確認
6. `AGENTS.md` のテスト指針 — テスト作成ルール・配置・命名の準拠確認

## 重要な前提（必ず守ること）

1. **Reviewer / Fix Builder は毎回 fresh context で起動する**
   - `reviewer` 役割・`fix-builder` 役割のサブエージェントを **毎回新規エージェントとして** 起動する（起動方法は末尾「補足」参照）
   - 司令塔（メイン会話）の文脈・「なぜこう書いたか」の弁明を一切引き継がない。テストファイル・設計書は **disk から読ませる**
   - **同一インスタンスの使い回し禁止**：再レビューは前回のレビュワーとは別の新規エージェント、修正は Phase 5 の test-builder とは別の新規エージェントが行う

2. **findings の disk 書き出しは司令塔（本skillの実行AI）が担当する**
   - Reviewer は Read 専用エージェントであり、findings は最終応答テキストとして返却する
   - 司令塔は Reviewer の応答テキストを `_review/test/findings.md` に Write する

3. **severity は Critical / Major / Minor の3段階**
   - Critical / Major は修正ループの対象（修正必須）。Minor は記録のみで通過可（対応は任意）
   - findings には必ず該当箇所（ファイルパス・行番号）を明記させる。「全体的によい」だけの報告は禁止

4. **修正は fix-builder に委譲し、Red Phase の規律を維持する**
   - 司令塔がメイン会話でテストを直接修正しない
   - 修正後も「新規テストはスタブ実装に対して期待値不一致で個別に FAIL・既存テストは全件 PASS」を維持する（fix-builder の役割ファイルで担保。司令塔も独立に再検証する）

5. **ループの安全弁**
   - レビュー → 修正 → 再レビューのサイクルは **最大3回** まで。3回目の再レビューでも Critical / Major が残る場合はループを打ち切り、残 findings と経緯をユーザーに報告して判断を仰ぐ
   - 設計書の不備に起因する findings（テスト側では解消できないもの）が出た場合はループで解消しようとせず、Phase 1（設計書修正）への差し戻しをユーザーに提案する

## 実行手順

### Step 1: レビュー対象の確認

ユーザーから以下を確認する（既に提示されていれば省略）：

- レビュー対象のテストファイルパス（例: `src/app/api/<機能>/__tests__/route.test.ts`、`_lib/__tests__/*.test.ts`）
- 対象機能の設計書・実装計画書のパス
- Red Phase 証拠のパス
- テストが参照する型定義・定数ファイル（`_types/api.d.ts`、`_constant/` 等）

### Step 2: 必須参照ファイルの読み込み

上記「必須参照ファイル」を読む。Phase 5 の完了（Red Phase 証拠の存在）を確認し、なければ Phase 5 の実施を先に案内する。`フロー運用設定.md` から Phase 7（人間承認）の要否を確認しておく。

### Step 3: 出力先ディレクトリの作成

対象機能の設計書と同じディレクトリに `_review/test/` を作成する（Phase 5 で作成済みの場合はそのまま使用）。

- 出力先: `docs/設計/<機能名>/_review/test/findings.md`

### Step 4: Reviewer サブエージェントの起動（第1回・フルレビュー）

`reviewer` 役割のサブエージェントを fresh context として起動する（起動方法は末尾「補足」参照）。

**プロンプトに含める内容：**

- （汎用サブエージェント起動の場合）役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- レビュー対象テストファイルの絶対パス（全件）
- 設計書・実装計画書・Red Phase 証拠・関連型定義の絶対パス
- レビューモード：「初回（フルレビュー）」
- レビュー観点（下記6つ）と必須チェックパターン（下記）
- 出力形式（下記）
- **findings は最終応答テキストとして返却することを明記**（disk への書き出しは司令塔が後で実施する）

**Reviewer に伝えるレビュー観点（6つ）：**

1. **受け入れ条件との対応（トレーサビリティ）** — 設計書の各受け入れ条件に対応するテストが存在するか。**受け入れ条件×テストの対応マトリクス**（✅/⚠️/❌/N/A）の作成を必須とする
2. **トートロジー検出** — テストが「モックが返す値」をそのまま assert していないか。**モックが何を返すかではなく、実装の整形・フィルタリング・変換ロジックを検証しているか**。`expect(x).toBeDefined()` だけで済ませた実質空のテストがないか。トートロジーテストは Critical とする
3. **エッジケース・例外系の網羅** — 境界値・不正値・0件・null リレーション・未認証（null/undefined/壊れたセッションの it.each 網羅）の検討漏れ
4. **実装詳細の過剰束縛** — テストが実装の内部構造（プライベートな中間処理）を縛りすぎて、正当なリファクタを妨げないか
5. **Red Phase log の妥当性** — 新規テスト全件 FAIL + 既存テスト全件 PASS が実行ログで証明されているか。**スタブ最小実装方式（2026-07-12 決定）に従い、失敗が期待値不一致で個別に enumerate されているか**。スタブに実ロジックが混入していないか（Phase 8 の先取り検出）。import エラーによる一括失敗が残っている場合は、その範囲でトートロジー混入を検出できないことを findings に明記させる
6. **セキュリティ・品質観点** — 認可境界／PII除外／N+1／既存規約整合が拾えているか（下記パターン参照）

**Reviewer に伝える必須チェックパターン**（過去の Phase 6 実走で確立）：

- **PII 除外の3層検証**：型レベル + モック汚染テスト（モックに意図的に PII を混入させて除外を確認）+ JSON シリアライズ値検証。モックが PII を返さないだけのテストはトートロジー
- **認可境界の2層検証**：where 引数の assert + 他社データ混在モックでの検証
- **N+1 検出**：`mockImplementation` 等でクエリ数を強制カウントしているか
- **既存規約整合**：既存の類似 API の構造（`apiHandler` ラッパーの有無、`isAuth` の使い方等）をテストが正しく前提にしているか。既存 route.ts を実際に読んで突き合わせる
- **未決事項の素通し**：設計書に未決事項が残ったまま書かれたテスト（曖昧性を温存するテスト）がないか

**Reviewer に出力させる形式（findings.md）：**

```markdown
# テストレビュー結果（Phase 6 第N回）

- **対象**: <テストファイル・関連ファイルのパス一覧>
- **レビュー日時**: YYYY-MM-DD
- **方法**: Reviewer AI（fresh context・Read 専用）。findings は司令塔が disk に保存
- **レビューモード**: 初回（フルレビュー）/ 再レビュー（解消確認＋修正差分）
- **総合判定**: PASS / FAIL（Critical または Major が1件でもあれば FAIL）

## サマリー

| Severity | 件数 |
|---|---|
| Critical | N |
| Major    | N |
| Minor    | N |

### Critical / Major findings 見出し一覧

- **FIND-001**: <短い見出し>

## 設計書 受け入れ条件 × テスト 対応マトリクス

凡例：✅ 対応テストあり / ⚠️ 部分的・不十分 / ❌ 未対応 / N/A 本テストの責務外

| 設計書 受け入れ条件 | 該当行 | 対応テスト | 状況 |
|---|---|---|---|
| ... | ... | ... | ... |

## Findings

### FIND-001: <タイトル>
- **観点**: <該当するレビュー観点>
- **重大度**: Critical / Major / Minor
- **ファイル**: <ファイルパス:行番号>
- **問題**: <具体的な問題点>
- **失敗シナリオ**: <この問題が解決されないと Phase 8 以降で何が起きるか（Critical / Major は必須）>
- **推奨対応**: <修正方針>

## レビュー観点ごとの判定

| 観点 | 判定 | 補足 |
|---|---|---|
| 受け入れ条件との対応 | PASS / FAIL | |
| トートロジー検出 | PASS / FAIL | |
| エッジケース・例外系の網羅 | PASS / FAIL | |
| 実装詳細の過剰束縛 | PASS / FAIL | |
| Red Phase log の妥当性 | PASS / FAIL | |
| セキュリティ・品質観点 | PASS / FAIL | |
```

### Step 5: findings の disk 書き出し（司令塔の責務）

Reviewer の応答テキストを受け取ったら、司令塔が `Write` ツールで `docs/設計/<機能名>/_review/test/findings.md` に保存する。

**書き出し時の留意点：**

- findings 本文部分をそのまま書き出す（冒頭のメタ説明・末尾の重複サマリーは整理してよい）
- 修正ループの2周目以降・再実行時は前回分を上書きせず、「第N回」としてファイル内に追記する（前回の findings に Phase 7 判定記録が含まれている場合があるため）

### Step 6: 判定と修正ループ

**Critical / Major が 0 件の場合** → Step 7（完了通知）へ。

**Critical / Major が 1 件以上の場合** → 以下の修正ループを実行する：

1. **差し戻し要否の仕分け（司令塔）**：findings のうち設計書の不備に起因するもの（テスト側では解消できないもの）があれば、ループを開始せず Phase 1 への差し戻しをユーザーに提案する。テスト側で解消できる findings のみループに進む
2. **fix-builder の起動（fresh context）**：`fix-builder` 役割のサブエージェントを新規起動する。プロンプトに含める内容：
   - 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
   - 成果物種別：**テストコード（Red Phase 中）**
   - 修正対象の findings（Critical / Major の全文。Minor は渡さない）
   - テストファイル・スタブ・設計書・Red Phase 証拠・AGENTS.md の絶対パス
   - **指定 findings 以外の箇所を変更しないこと（デグレ防止）**、**アサーションを弱める修正・スタブへの実ロジック追加の禁止**、**修正後も Red Phase（新規テスト期待値不一致 FAIL＋既存 PASS）を維持すること** を明記
3. **Red Phase の独立再検証（司令塔）**：fix-builder の完了報告後、司令塔が自ら `npm run test`（および該当時 `npm run test:integration`）を実行し、「新規テスト全件が期待値不一致で FAIL・既存テスト全件 PASS」を確認する。`git diff` で修正差分が findings の範囲に収まっていることも検証する。Red Phase 証拠（red-phase-evidence.md）を「第N回修正後」として更新する
4. **再レビュー（別の fresh context の Reviewer）**：`reviewer` 役割のサブエージェントを**新規に**起動する。プロンプトに含める内容：
   - レビューモード：「再レビュー」
   - 前回 findings（Critical / Major）の一覧と、修正差分の範囲（変更ファイル）
   - 「前回 findings の解消確認＋修正差分に混入した新規欠陥（トートロジー化・アサーション弱体化を含む）の検出に限定。修正されていない箇所への新規のフル指摘はしない」ことを明記
5. 再レビューの findings を Step 5 の要領で「第N回」として追記し、本 Step の判定に戻る

**ループ上限**：修正サイクルは最大3回。超えたら残 findings・経緯・推奨対応をユーザーに報告して判断を仰ぐ。

### Step 7: 完了通知と次フェーズ案内

`フロー運用設定.md` の Phase 7 設定に応じて分岐する。

**Phase 7（人間承認）が必要な場合：**

```
Phase 6（テストレビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/test/findings.md
- レビュー・修正ループ: N 回で収束（Critical 0 件・Major 0 件・Minor N 件）
- 受け入れ条件マトリクス: 全件対応（❌/⚠️ 0 件）
- Minor findings: <見出し一覧（あれば）>

次は Phase 7（人間レビュー・テスト承認ゲート）です。
テストと findings をご確認の上、以下のいずれかをお伝えください：
  - 「テストを承認します」 → Phase 8（実装・Green Phase）に進む
  - 「テストを修正して」 → 指摘内容を反映後、Phase 6 を再実行
```

承認の発話を受けたら、司令塔は承認判定・Minor の取り扱い方針を「Phase 7 人間レビュー判定」節として findings.md に追記する。

**Phase 7 が不要（スキップ設定）の場合：**

司令塔は findings.md に「Phase 7 スキップ（フロー運用設定による自動承認）」の記録（Minor の取り扱い方針を含む）を追記した上で通知する：

```
Phase 6（テストレビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/test/findings.md
- レビュー・修正ループ: N 回で収束（Critical 0 件・Major 0 件・Minor N 件）
- Phase 7（人間承認）はフロー運用設定によりスキップし、テストを承認済みとして記録しました。

次は Phase 8（実装・Green Phase）です。
「実装して」とお声がけください（flow-phase8-impl skill が起動します）。
```

## 禁止事項

- **Reviewer / fix-builder をメイン会話のAIとして実行しない**（必ず fresh context のサブエージェントとして起動）
- **再レビューに前回と同一のレビュワーインスタンスを使わない**（毎回新規起動）
- Reviewer に Write を強要しない（findings 書き出しは司令塔の責務）
- 「全体的によい」「特に問題なし」だけの findings を許容しない
- 司令塔がメイン会話でテストを直接修正しない（修正は fix-builder に委譲）
- 修正ループで Red Phase を崩さない（修正後の新規テストがスタブに対して PASS する状態を許容しない）
- Critical / Major を残したまま次フェーズに進まない（ループ上限到達時はユーザー判断を仰ぐ）
- Phase 7 が必要な設定のとき、人間の承認なしにテストを承認済み扱いにしない
- Red Phase 証拠なしでレビューを開始しない（Phase 5 未完了の場合は先に Phase 5 を案内）

## 補足：Reviewer / Fix Builder の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/reviewer.md`・`flow-agent-roles/roles/fix-builder.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・出力形式に完全に従うこと」を指示する。Reviewer の読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

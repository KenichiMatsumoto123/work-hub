# Phase 2: 設計書 敵対的レビュー（収束ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 2** を担当するスキル。Phase 1 で作成された設計書を、司令塔（メイン会話のAI）と分離された **fresh context** の `adversarial-reviewer` サブエージェントが批判的にレビューする。

**本フェーズは1回のレビューでは終わらない。** Critical / Major がゼロになるまで「レビュー → 修正 → 差分再レビュー」を繰り返し、収束した設計書を Phase 3（人間承認ゲート）へ渡す。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典。Phase 2 の位置づけと出力要件を理解する
2. `flow-review-policy` skill（本 skill と同じ skills ディレクトリ内。絶対パスに解決して読む）— **較正不変の原則・観点レーン分割・出力予算・must-catch・収束ループの正本**
3. `docs/設計/<機能名>/_flow-config.md` — フロー設定（運用モード・レーン並列の有効/無効・収束ループ上限）
4. `docs/設計/設計書フォーマット.md` — 設計書のベースフォーマット。レビューの基準として使用
5. `docs/設計/共通機能設計書.md` — システム共通仕様。レビュー時の判定基準として使用（存在する場合のみ）
6. 要件メモ（`docs/要件/<機能名>_要件メモ.md`）— 存在する場合。findings 修正時の根拠として使用

## 重要な前提（必ず守ること）

1. **Adversary は fresh context で起動する**

   - `adversarial-reviewer` 役割のサブエージェントを **新規エージェントとして** 起動する（起動方法は末尾「補足」参照）
   - 司令塔（メイン会話）の文脈・反論を引き継がない
   - 設計書ファイルを **disk から読む**（会話履歴経由ではない）

2. **観点はレーンに分割して並列起動する（時間短縮の主手段）**

   - 較正（敵対的な探索の深さ）は絶対に下げない。短縮は「分割・並列化」「出力粒度」「差分レビュー」で行う（`flow-review-policy` 2章）
   - 既定は3レーン（下記 Step 4）。**同一メッセージ内でまとめて起動して並列に走らせる**
   - 並列起動できない環境では `_flow-config.md` の「観点レーン並列」を無効にし、1エージェントに全観点を渡す（所要時間は延びるが較正は下げない）

3. **findings の disk 書き出しは司令塔（本skillの実行AI）が担当する**

   - Adversary は Read 専用エージェントであり、findings は最終応答テキストとして返却する
   - 司令塔は各レーンの応答をマージして `_review/spec/findings.md` に Write する
   - これは Claude Code harness レベルの「分析mdファイル書き出し制限」を回避するための運用上の取り決め

4. **「全体的によい」は禁止**

   - findings は必ず severity（Critical / Major / Minor）と該当箇所（ファイル名・該当節・該当行）を明記する
   - 「特に問題なし」と書きたい場合も、レビュー観点ごとに「該当なし」と検証した具体箇所を明示する

5. **収束するまでループする**

   - 1回のレビューで終了しない。Critical 0 かつ Major 0 になるまで修正と差分再レビューを繰り返す（Step 6）
   - 設計書の修正は司令塔が行うが、**新しい仕様決定が必要な finding は AI が推測で埋めず、その周のうちにユーザーへまとめて質問する**

## 実行手順

### Step 1: レビュー対象とフロー設定の確認

- レビュー対象の設計書パス（例: `docs/設計/<機能名>/<機能名>_設計書.md`）
- 関連資料（HTMLモック、機能候補一覧、利用フロー、要件メモ等）のパス
- `_flow-config.md` を読み、運用モード・レーン並列の有効/無効・収束ループ上限（既定5周）を把握する（存在しない場合は `flow-review-policy` 1.6 の様式でユーザーに確認して作成する）

### Step 2: 必須参照ファイルの読み込み

上記「必須参照ファイル」を読む。

### Step 3: 出力先ディレクトリの作成

レビュー対象の設計書と同じディレクトリに `_review/spec/` を作成する。

- findings: `docs/設計/<機能名>/_review/spec/findings.md`
- 収束ログ: `docs/設計/<機能名>/_review/spec/review-log.md`

### Step 4: Adversary サブエージェントの並列起動（Round 1）

`adversarial-reviewer` 役割のサブエージェントを、**レーンごとに fresh context で並列起動する**（起動方法は末尾「補足」参照）。

**既定のレーン割り（`flow-review-policy` 3.2）：**

| レーン | 担当観点 | must-catch |
|---|---|---|
| A: 仕様の確からしさ | ① 仕様の曖昧性（解釈の余地・複数実装が成立しうる箇所）／② 受け入れ条件の検証可能性（テストで判定できる形か） | MC-4（未決事項の温存） |
| B: 網羅とスコープ | ③ 要件の網羅性（受け入れ条件・対象外・未決事項の抜け）／④ 非ゴールの明確性／⑤ 設計書フォーマット準拠（基本情報・要件・業務フロー・影響を受ける実装済み機能・テストレベル判定） | — |
| C: 異常系 | ⑥ エッジケース（例外系・境界値・異常系・空状態・権限・並行・大量データ） | — |

**各レーンのプロンプトに含める内容：**

- 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- レビュー対象設計書の絶対パス
- 関連資料（フォーマット・共通機能設計書・要件ドキュメント等）の絶対パス
- **担当レーンの観点のみ**を敵対的較正で深く見ること（他レーンの観点は他のエージェントが担当している旨も伝える）
- 担当する **must-catch 項目**（上表）
- **出力予算**：Critical / Major はフル記述、Minor は「FIND-XXX: 見出し（該当節）」の1行のみ、PASS 観点の裏付けは1〜2行
- 出力形式（下記）
- **findings は最終応答テキストとして返却することを明記**（disk への書き出しは司令塔が後で実施する）

**各レーンに出させる形式：**

```markdown
## レーン<X>（<担当観点>）レビュー結果

### 観点ごとの判定

| 観点 | 判定 | 裏付け（検証した具体箇所・1〜2行） |
|---|---|---|
| <観点名> | PASS / FAIL | |

### Findings

#### F-<レーン>-001: <短い見出し>
- **観点**: <該当観点>
- **重大度**: Critical / Major
- **該当箇所**: <設計書のセクション名・行番号>
- **問題**: <具体的な問題点>
- **影響**: <この問題が解決されないと何が起きるか>
- **推奨対応**: <修正方針>
- **仕様決定の要否**: 要（設計書・要件メモに根拠がなく、新たな決定が必要）/ 不要（既存の記述から解消できる）

### Minor（1行のみ）
- F-<レーン>-00N: <見出し>（<該当節>）
```

### Step 5: findings のマージと disk 書き出し（司令塔の責務）

各レーンの応答テキストを受け取ったら、`flow-review-policy` 3.3 のマージ規則に従って統合する：

- 重複は1件に統合（観点欄に併記）。件数を水増ししない
- severity がレーン間で食い違う場合は**高い方**を採る
- 判定が矛盾する場合は両論を残し、司令塔の判断と根拠を併記する
- **各レーンの指摘内容を要約・軟化・削除してはならない**（統合と体裁整理のみ）

統合結果を `Write` ツールで `docs/設計/<機能名>/_review/spec/findings.md` に保存する。

```markdown
# 設計書 敵対的レビュー結果（Round N）

- 対象: <設計書のパス>
- レビュー日時: YYYY-MM-DD HH:MM
- 方式: 敵対的較正・<3>レーン並列（A: 仕様の確からしさ / B: 網羅とスコープ / C: 異常系）
- 総合判定: PASS（Critical 0・Major 0）/ FAIL

## サマリー

| Severity | 件数 |
| -------- | ---- |
| Critical | N    |
| Major    | N    |
| Minor    | N    |

## Findings

### Critical

#### F-001: <短い見出し>
- **観点 / レーン**: <観点>（レーン<X>）
- **該当箇所**: <設計書のセクション名・行番号>
- **問題**: / **影響**: / **推奨対応**:
- **仕様決定の要否**: 要 / 不要

### Major
（同上）

### Minor（1行のみ）
- F-XXX: <見出し>（<該当節>）

## レビュー観点ごとの判定

| 観点 | レーン | 判定 | 裏付け |
| ---- | ---- | ---- | ---- |
| 仕様の曖昧性 | A | PASS / FAIL | |
| 受け入れ条件の検証可能性 | A | PASS / FAIL | |
| 要件の網羅性 | B | PASS / FAIL | |
| 非ゴールの明確性 | B | PASS / FAIL | |
| 設計書フォーマット準拠 | B | PASS / FAIL | |
| エッジケース | C | PASS / FAIL | |
```

Round 2 以降は前回分を上書きせず、「Round N」の節として追記する（前回の指摘と解消状況を追える形にする）。

### Step 6: 収束ループ（Critical / Major がゼロになるまで）

**収束条件：Critical 0 件 かつ Major 0 件。**Minor は収束条件に含めない（findings に1行で記録して通過してよい）。

収束していない場合、次を繰り返す：

1. **findings の仕分け**
   - 「仕様決定の要否 = 不要」のもの → 司令塔が設計書を修正する（設計書・要件メモ内の既存の記述を根拠にできるもの）
   - 「仕様決定の要否 = 要」のもの → **その周のうちにユーザーへまとめて質問する**（1件ずつ小出しにしない）。推奨案を理由付きで添え、回答を得てから設計書に反映する。AI が仕様を推測して埋めてはならない
2. **設計書の修正**（司令塔）。修正した箇所と対応した FIND-ID を記録する
3. **差分再レビュー（Round N+1）**：`flow-review-policy` 4.4 に従い、次に限定して Adversary を再起動する
   - 前回 findings の解消確認（1件ずつ「解消 / 未解消 / 部分的」を判定）
   - 修正差分に含まれる新規欠陥
   - must-catch チェック（毎周必須）
   - **例外**：設計方針そのものが変わるなど修正が広範囲に波及した場合は、司令塔の判断でフルレビュー（3レーン並列）に戻してよい。その旨を review-log に記録する
4. 収束するまで 1〜3 を繰り返す

**ループを抜けて人間へ即エスカレーションする条件（`flow-review-policy` 4.3）：**

- 要件そのものの見直しが必要（要件メモの前提が崩れている）→ `flow-kickoff` / Phase 1 の再実施を提案する
- スコープの拡大を伴う
- 同一 finding が2周連続で解消されない／修正のたびに新規 Critical が発生する（振動）
- 収束ループ上限（既定5周）に到達

### Step 7: 収束ログの記録

`docs/設計/<機能名>/_review/spec/review-log.md` に `flow-review-policy` 4.5 の様式で各 Round の記録を残す（Round ごとの件数・解消数・新規数・判定、修正内容、ユーザーに質問して確定した仕様、エスカレーションの有無）。

### Step 8: 完了通知と次フェーズ案内

```
Phase 2（設計書 敵対的レビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/spec/findings.md
- 収束ログ: docs/設計/<機能名>/_review/spec/review-log.md
- 収束: Round N で Critical 0・Major 0（Minor N 件は記録のみ）
- レビュー方式: 敵対的較正・3レーン並列 ／ 差分レビュー N 周
- ループ中にユーザーへ確認して確定した仕様: N 件

次は Phase 3（人間レビュー・設計書承認ゲート）です。※このゲートはスキップできません。
findings と設計書をご確認の上、以下のいずれかをお伝えください：
  - 「設計書を修正して」 → Phase 1 に戻り、ご指摘を反映
  - 「設計書を承認します」 → ステータスを「合意済」に更新し、Phase 4（実装計画書作成）へ
```

**収束せずにエスカレーションした場合：**

```
Phase 2 の収束ループを中断しました（理由: <上限到達 / 振動 / 仕様の見直しが必要 / スコープ拡大>）。
- 残 findings: Critical N 件・Major N 件
- 各周で試みた修正: <要約>
- 司令塔の見立て: <原因の仮説と対応案>
ご判断をお願いします。
```

## 禁止事項

- **Adversary をメイン会話のAIとして実行しない**（必ず fresh context のサブエージェントとして起動）
- **較正を下げて時間短縮しない**（「批判的観点を外す」「観点を減らす」等。短縮は分割・並列化・出力粒度・差分レビューで行う）
- must-catch チェックを差分レビューを理由に省略しない
- Adversary に Write を強要しない（Adversary は Read 専用。findings 書き出しは司令塔の責務）
- 各レーンの指摘を司令塔が要約・軟化・削除しない
- 「全体的によい」「特に問題なし」だけのfindingsを許容しない（観点ごとに具体的な評価と裏付けを要求）
- **1回のレビューで打ち切らない**（Critical/Major が残った状態で Phase 3 へ進めない）
- **仕様決定が必要な finding を AI が推測で埋めない**（ユーザーに質問する）

## 補足：Adversary の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/adversarial-reviewer.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・出力形式に完全に従うこと」を指示する。読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。**レーン並列時は、レーンごとに別のサブエージェントを同一メッセージ内でまとめて起動する。**

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

# Phase 2: 設計書レビュー（レビュー・修正ループ）

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 2** を担当するスキル。Phase 1 で作成された設計書を、司令塔（メイン会話のAI）と分離された **fresh context** の `reviewer` サブエージェントがレビューし、Critical / Major の findings があれば **fresh context の `fix-builder`** が修正 → **別の fresh context の `reviewer`** が再レビュー、を Critical / Major が 0 件になるまで繰り返す。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典。Phase 2 の位置づけと出力要件を理解する
2. `docs/開発プロセス/フロー運用設定.md` — Phase 3（人間承認）の要否設定（存在しない場合は「承認必要」として扱う）
3. `docs/設計/設計書フォーマット.md` — 設計書のベースフォーマット。レビューの基準として使用
4. `docs/設計/共通機能設計書.md` — システム共通仕様。レビュー時の判定基準として使用（存在する場合のみ）

## 重要な前提（必ず守ること）

1. **Reviewer / Fix Builder は毎回 fresh context で起動する**

   - `reviewer` 役割・`fix-builder` 役割のサブエージェントを **毎回新規エージェントとして** 起動する（起動方法は末尾「補足」参照）
   - 司令塔（メイン会話）の文脈・反論を引き継がない。設計書ファイルは **disk から読ませる**（会話履歴経由ではない）
   - **同一インスタンスの使い回し禁止**：再レビューは前回のレビュワーとは別の新規エージェント、修正は初回作成者（Phase 1 の司令塔）とは別の新規エージェントが行う

2. **findings の disk 書き出しは司令塔（本skillの実行AI）が担当する**

   - Reviewer は Read 専用エージェントであり、findings は最終応答テキストとして返却する
   - 司令塔は Reviewer の応答テキストを `_review/spec/findings.md` に Write する

3. **severity は Critical / Major / Minor の3段階**

   - Critical / Major は修正ループの対象（修正必須）。Minor は記録のみで通過可（対応は任意）
   - findings には必ず該当箇所（ファイル名・該当節・該当行）を明記させる。「全体的によい」だけの報告は禁止

4. **修正は fix-builder に委譲する**

   - 司令塔がメイン会話で設計書を直接修正しない
   - fix-builder には「指定 findings（Critical / Major）のみ修正・関係ない箇所は変更しない（デグレ防止）」を課す（役割ファイルで担保）

5. **ループの安全弁**
   - レビュー → 修正 → 再レビューのサイクルは **最大3回** まで。3回目の再レビューでも Critical / Major が残る場合はループを打ち切り、残 findings と経緯をユーザーに報告して判断を仰ぐ

## 実行手順

### Step 1: レビュー対象の確認

ユーザーから以下を確認する（既に提示されていれば省略）：

- レビュー対象の設計書パス（例: `docs/設計/<機能名>/<機能名>_設計書.md`）
- 関連資料（HTMLモック、機能候補一覧、利用フロー等）のパス

### Step 2: 必須参照ファイルの読み込み

上記「必須参照ファイル」を読む。`フロー運用設定.md` から Phase 3（人間承認）の要否を確認しておく。

### Step 3: 出力先ディレクトリの作成

レビュー対象の設計書と同じディレクトリに `_review/spec/` を作成する。

- 設計書: `docs/設計/<機能名>/<機能名>_設計書.md`
- 出力先: `docs/設計/<機能名>/_review/spec/findings.md`

### Step 4: Reviewer サブエージェントの起動（第1回・フルレビュー）

`reviewer` 役割のサブエージェントを fresh context として起動する（起動方法は末尾「補足」参照）。

**プロンプトに含める内容：**

- （汎用サブエージェント起動の場合）役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
- レビュー対象設計書の絶対パス
- 関連資料（フォーマット・共通機能設計書・要件ドキュメント等）の絶対パス
- レビューモード：「初回（フルレビュー）」
- レビュー観点（下記）
- 出力形式（下記）
- **findings は最終応答テキストとして返却することを明記**（disk への書き出しは司令塔が後で実施する）

**Reviewer に伝えるレビュー観点（6つ）：**

1. **仕様の曖昧性** — 解釈の余地が残る記述、複数の実装が成立しうる箇所
2. **要件の網羅性** — 受け入れ条件・対象外・未決事項の網羅。抜けがないか。**テストの期待値を左右する未決事項（DBカラム名・デフォルト orderBy・enum フォールバック・エラーコード等）が残っている場合は Critical とする**
3. **エッジケース** — 例外系・境界値・異常系・空状態の検討漏れ
4. **受け入れ条件の検証可能性** — 「動作する」など曖昧な表現でなく、テストで判定できる形になっているか
5. **非ゴールの明確性** — スコープ外が明示されているか、暗黙的なスコープが残っていないか
6. **設計書フォーマット準拠** — 必須項目（基本情報・要件・業務フロー・影響を受ける実装済み機能など）が記載されているか

**Reviewer に出力させる形式（findings.md）：**

```markdown
# 設計書レビュー結果（Phase 2 第N回）

- 対象: <設計書のパス>
- レビュー日時: YYYY-MM-DD HH:MM
- レビューモード: 初回（フルレビュー）/ 再レビュー（解消確認＋修正差分）
- 総合判定: PASS / FAIL（Critical または Major が1件でもあれば FAIL）

## サマリー

| Severity | 件数 |
| -------- | ---- |
| Critical | N    |
| Major    | N    |
| Minor    | N    |

## Findings

### Critical

#### F-001: <短い見出し>

- **該当箇所**: <設計書のセクション名・行番号>
- **問題**: <具体的な問題点>
- **失敗シナリオ**: <この問題が解決されないと何が起きるか（1文）>
- **推奨対応**: <修正方針>

（以下、Critical findings 全て）

### Major

#### F-XXX: ...

### Minor

#### F-XXX: ...

## レビュー観点ごとの判定

| 観点                     | 判定        | 補足 |
| ------------------------ | ----------- | ---- |
| 仕様の曖昧性             | PASS / FAIL |      |
| 要件の網羅性             | PASS / FAIL |      |
| エッジケース             | PASS / FAIL |      |
| 受け入れ条件の検証可能性 | PASS / FAIL |      |
| 非ゴールの明確性         | PASS / FAIL |      |
| 設計書フォーマット準拠   | PASS / FAIL |      |
```

### Step 5: findings の disk 書き出し（司令塔の責務）

Reviewer の応答テキストを受け取ったら、司令塔が `Write` ツールで `docs/設計/<機能名>/_review/spec/findings.md` に保存する。

**書き出し時の留意点：**

- findings 本文部分をそのまま書き出す（冒頭のメタ説明・末尾の重複サマリーは整理してよい）
- 修正ループの2周目以降は前回分を上書きせず、「第N回」としてファイル内に追記する（ループの経緯が追えるようにする）

### Step 6: 判定と修正ループ

**Critical / Major が 0 件の場合** → Step 7（完了通知）へ。

**Critical / Major が 1 件以上の場合** → 以下の修正ループを実行する：

1. **fix-builder の起動（fresh context）**：`fix-builder` 役割のサブエージェントを新規起動する。プロンプトに含める内容：
   - 役割ファイルの絶対パスと「最初に読み、以後その役割に完全に従う」指示
   - 成果物種別：**設計書（ドキュメント）**
   - 修正対象の findings（Critical / Major の全文。Minor は渡さない）
   - 設計書・関連資料の絶対パス
   - **指定 findings 以外の箇所を変更しないこと（デグレ防止）** を明記
2. **修正結果の確認（司令塔）**：fix-builder の最終応答（findings 対応記録・変更ファイル一覧・デグレ確認）を確認する。`git diff` で修正差分が findings の範囲に収まっていることを検証する。仕様判断が必要として中断された finding があれば、ループを一時停止してユーザーに判断を仰ぐ
3. **再レビュー（別の fresh context の Reviewer）**：`reviewer` 役割のサブエージェントを**新規に**起動する。プロンプトに含める内容：
   - レビューモード：「再レビュー」
   - 前回 findings（Critical / Major）の一覧と、修正差分の範囲（変更ファイル・セクション）
   - 「前回 findings の解消確認＋修正差分に混入した新規欠陥の検出に限定。修正されていない箇所への新規のフル指摘はしない」ことを明記
4. 再レビューの findings を Step 5 の要領で「第N回」として追記し、本 Step の判定に戻る

**ループ上限**：修正サイクルは最大3回。超えたら残 findings・経緯・推奨対応をユーザーに報告して判断を仰ぐ。

### Step 7: 完了通知と次フェーズ案内

`フロー運用設定.md` の Phase 3 設定に応じて分岐する。

**Phase 3（人間承認）が必要な場合：**

```
Phase 2（設計書レビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/spec/findings.md
- レビュー・修正ループ: N 回で収束（Critical 0 件・Major 0 件・Minor N 件）
- Minor findings: <見出し一覧（あれば）>

次は Phase 3（人間レビュー）です。
設計書と findings をご確認の上、以下のいずれかをお伝えください：
  - 「設計書を承認します」 → 設計書ステータスを「合意済」に更新し、Phase 4（実装計画書作成）に進む
  - 「○○を修正して」 → 指摘内容を反映後、Phase 2 を再実行
```

承認の発話を受けたら、司令塔は設計書ステータスを「合意済」に更新し、findings.md に「Phase 3 人間レビュー判定」節（承認判定・Minor の取り扱い方針）を追記する。

**Phase 3 が不要（スキップ設定）の場合：**

司令塔は設計書ステータスを「合意済」に更新し、findings.md に「Phase 3 スキップ（フロー運用設定による自動承認）」の記録を追記した上で通知する：

```
Phase 2（設計書レビュー）が完了しました。
- findings: docs/設計/<機能名>/_review/spec/findings.md
- レビュー・修正ループ: N 回で収束（Critical 0 件・Major 0 件・Minor N 件）
- Phase 3（人間承認）はフロー運用設定によりスキップし、設計書を「合意済」としました。

次は Phase 4（実装計画書作成）です（簡単な機能ならスキップして Phase 5 へ）。
「実装計画書を作って」または「テストを書いて」とお声がけください。
```

## 禁止事項

- **Reviewer / fix-builder をメイン会話のAIとして実行しない**（必ず fresh context のサブエージェントとして起動）
- **再レビューに前回と同一のレビュワーインスタンスを使わない**（毎回新規起動）
- Reviewer に Write を強要しない（Reviewer は Read 専用。findings 書き出しは司令塔の責務）
- 「全体的によい」「特に問題なし」だけの findings を許容しない（観点ごとに具体的な評価を要求）
- 司令塔がメイン会話で設計書を直接修正しない（修正は fix-builder に委譲）
- Critical / Major を残したまま次フェーズに進まない（ループ上限到達時はユーザー判断を仰ぐ）
- Phase 3 が必要な設定のとき、人間の承認なしに設計書を「合意済」にしない

## 補足：Reviewer / Fix Builder の起動方法（役割ファイル方式）

役割定義の正本は `flow-agent-roles/roles/reviewer.md`・`flow-agent-roles/roles/fix-builder.md`（本 skill と同じ skills ディレクトリ内。使用時は絶対パスに解決する）。

ツールの汎用サブエージェント起動機能で新規サブエージェントを fresh context で起動し、プロンプトの冒頭で「まず役割ファイル（絶対パス）を読み、以後その役割・制約・出力形式に完全に従うこと」を指示する。Reviewer の読み取り専用（Read / Glob / Grep 相当のみ）の制約は役割ファイル内の指示で担保する。

起動できない場合はユーザーに環境設定の確認を求める。メイン会話で役割を代行してはならない。

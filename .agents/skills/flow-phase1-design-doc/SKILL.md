# Phase 1: 設計書作成

新規機能開発の標準10フェーズフロー（`docs/開発プロセス/設計から実装までのフロー.md` 参照）の **Phase 1** を担当するスキル。設計書のみを作成し、レビュー・実装計画書作成は別フェーズの別skillが担当する。

## 必須参照ファイル（スキル起動時に必ず読む）

1. `docs/開発プロセス/設計から実装までのフロー.md` — 開発フローの正典。本スキルの位置づけと次フェーズへの遷移を理解する
2. `docs/設計/設計書フォーマット.md` — 設計書のベースフォーマットと格納ルール
3. `docs/設計/共通機能設計書.md` — システム共通仕様（エラー処理等）。設計書では共通仕様と異なる場合のみ明記する（存在する場合のみ）
4. `docs/開発プロセス/テストレベル選定トリガー表.md` — Step 6「テストレベル判定」の記載基準
5. 関連する要件ドキュメント（`docs/要件/` 配下）があれば読む

## 重要な前提（必ず守ること）

1. **ベースフォーマットは「最低限の必須項目」である**
   - フォーマットは土台。全項目を網羅することが目的ではなく、対象機能を正しく伝えることが目的

2. **AIは項目を追加・分割・粒度調整する裁量を持つ**
   - 機能特性に応じて最適な項目を判断する
   - ベースに無くても、その機能の理解に必要な項目は積極的に追記する
   - 対象機能に明らかに不要な項目は省略・統合してよい

3. **「設計書は様式に流し込むもの」ではなく「機能を正確に伝えるもの」**
   - 様式の体裁を守ることより、実装者が迷わず実装できる情報密度を優先する

4. **このskillは設計書作成のみを行う**
   - レビューは Phase 2（`flow-phase2-spec-review`）の責務
   - 実装計画書作成は Phase 4（`flow-phase4-impl-plan`）の責務
   - これらをこのskill内で実施しない

## 単発利用 vs フロー利用の判定

スキル起動時にまずユーザーに確認する：

- **フロー利用**：新規機能開発の一環として作成（10フェーズフロー全体を実施する想定）
- **単発利用**：既存機能の修正・補完で設計書だけ必要（レビュー・実装計画書はスキップする）

フロー利用の場合は完了時に Phase 2 案内を出す。単発利用の場合は次フェーズ案内を簡略化する。

## 実行手順

### Step 1: 単発／フロー判定

ユーザーに「フロー全体の一部として作成しますか？それとも単発の作成ですか？」と確認する。

### Step 2: 対象機能のヒアリング・確認

ユーザーから以下を確認する（既に提示されていれば省略）：

- 画面名／機能名
- 機能の目的・利用ユーザー
- 関連する要件ドキュメントの有無
- 画面イメージ（モック・ワイヤー）の有無と配置先

### Step 3: ベースフォーマット・共通仕様の読み込み

上記「必須参照ファイル」を読み、プロジェクトの設計書ルールを把握する。

### Step 4: 機能特性の分析と項目構成の決定

対象機能の特性を分析し、設計書の項目構成を決定する。

- ベースフォーマットの項目をそのまま採用するか
- 追加すべき項目はあるか（例：API仕様、状態遷移、権限制御、非同期処理、エラーケース、パフォーマンス要件、アクセシビリティ等）
- 統合・省略してよい項目はあるか

決定した構成は、設計書本体を書く前にユーザーへ簡潔に提示し、合意を取ること。

### Step 5: 設計書の作成

格納ルールに従って配置する。

- 配置先：`docs/設計/<画面名>/`
- ファイル名：`<画面名>_設計書.md`
- 画面イメージがあれば同フォルダに `<画面名>_画面イメージ.<ext>`（複数ある場合は `_番号` サフィックス）

冒頭の「ステータス」フィールドは「未着手」または「レビュー中」とする（「合意済」にするのは Phase 3 の人間承認後。フロー運用設定で Phase 3 が不要の場合は Phase 2 のレビュー・修正ループ収束後）。

### Step 6: テストレベル判定の記載（2026-07-12 追加）

`docs/開発プロセス/テストレベル選定トリガー表.md` と対象機能を突き合わせ、設計書に「テストレベル判定」節を追加する。

- **影響度トリガー**（認可境界・PII取扱い・認証セッション・不可逆操作・クリティカルパス業務・金銭契約）の該当有無と理由
- **発生可能性トリガー**（DB制約依存・実JOINクエリ・トランザクション・複雑な状態遷移）の該当有無と理由
- 画面操作を伴う機能由来のシナリオを洗い出す（クリティカルパス該当有無を問わず列挙する）
  - クリティカルパス業務トリガーに該当するもの → Phase 5 で E2E自動化（Playwrightコード化）の対象とする
  - 該当しないもの → Phase 5 で `docs/開発プロセス/E2E候補カタログ.md` に追記する候補として、設計書上にも一覧化しておく

判定内容は Phase 2（Reviewer レビュー）・Phase 3（人間承認。設定により省略可）で見落としがないか確認される。

### Step 7: 自己レビュー（最終チェック）

書き終えたら、以下を自己チェックする。

- [ ] 実装者がこの設計書だけを見て実装できるか（曖昧表現が残っていないか）
- [ ] 共通機能設計書と矛盾する記述がある場合、その理由が明記されているか
- [ ] 機能特有の論点（エッジケース、エラー、権限、空状態等）が拾えているか
- [ ] ベースに無いが必要な項目を追記したか／不要な項目を惰性で残していないか
- [ ] ステータスフィールドが「レビュー中」になっているか
- [ ] テストレベル判定（影響度トリガー・発生可能性トリガーの該当有無と理由）が記載されているか

### Step 8: 完了通知と次フェーズ案内

ユーザーに以下を出力する。

**フロー利用の場合：**

```
Phase 1（設計書作成）が完了しました。
- 設計書: docs/設計/<画面名>/<画面名>_設計書.md
- 画面イメージ: docs/設計/<画面名>/<画面名>_画面イメージ.<ext>（あれば）
- ステータス: レビュー中

次は Phase 2（設計書レビュー・修正ループ）です。
準備ができたら「設計書のレビューして」とお声がけください。
（flow-phase2-spec-review skill が起動します）
```

**単発利用の場合：**

```
設計書を作成しました。
- パス: docs/設計/<画面名>/<画面名>_設計書.md

単発利用のため、レビューと実装計画書作成はスキップしました。
必要に応じて「設計書のレビューして」「実装計画書を作って」とお声がけください。
```

## 禁止事項

- ベースフォーマットの全項目を機械的に埋めて「項目があるから書いた」式の空疎な記述を残さない（例：「特になし」の羅列）
- 共通機能設計書と重複する内容を再記述しない（例外仕様の場合のみ明記）
- ヒアリング不足のまま想像で埋めない。不明点はユーザーに質問する
- **このスキル内でレビュー・実装計画書作成を実施しない**（Phase 2/Phase 4 の責務）

## 補足：項目追加の発想例

機能タイプ別に追加検討すべき項目の例。網羅ではなく発想のヒント。

- 一覧／検索系：検索条件、ソート、ページング、絞り込み保持、空結果UI
- 入力フォーム系：バリデーション規則、送信フロー、下書き保存、離脱警告、確認ダイアログ
- 詳細表示系：取得失敗時の表示、削除済み・権限なしの扱い、関連情報の遅延読み込み
- 一括操作系：選択UI、確認ステップ、部分失敗時のロールバック方針
- 認証・権限系：未ログイン時の挙動、ロール別の表示差分、CSRF・認可境界
- 非同期処理系：状態遷移図、ポーリング／WebSocket、タイムアウト、リトライ方針
